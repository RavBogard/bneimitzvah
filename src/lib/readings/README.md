# Reading proposal boundary

`leyning.mjs` copies the unchanged pure selection section (through `selectTorah`, source lines 1–142) of `RavBogard/haftarah` `scripts/leyning.mjs` at `5b2530f72c544a9dab028d73076d47744b8252dc`. It excludes the sheet's console/Markdown presentation functions. This code is carried under this project's MIT code licence; Hebcal calendar data remains credited to [Hebcal](https://www.hebcal.com), CC BY 4.0. No text payloads are included. The original source checkout was read only.

The original permissive helpers preserve source behavior. Application callers use the typed boundaries in `ranges.ts` and `proposals.ts`, which validate inputs and calendar data before selecting anything. The unchanged helpers do not themselves establish canonical book, verse, or date validity.

- `parseCeremonyDate(value)` accepts a Gregorian date only, using calendar arithmetic without a time zone or timestamp conversion.
- `expandReadingRanges(refs, kind, verseCounts)` validates exact catalog book names, chapter/verse boundaries, order, duplicates, and a maximum 1,000 verses before expansion. A reading is an ordered list of segments, each one forward range inside one book; `readingSegments(ref)` splits a stored or calendar reference ("Isaiah 27:6-28:13; Isaiah 29:22-23") into them. Torah segments must follow one another inside one book. A haftarah's segments may cross books or return to an earlier chapter (Shabbat Shuva; Mishpatim's Jeremiah 34:8-22 then 33:25-26), and are read in the order given; no verse may repeat. Blessings share the future assignment-kind union but require a separate liturgical definition; they are not fabricated scripture ranges.
- `createHebcalReader({fetch, cache, verseCounts, now?, timeoutMs?})` returns an injected server-fetch/cache operation. It builds only the official HTTPS `/leyning` endpoint, refuses redirects, uses no credentials, bounds responses to 128 KiB and at most ten seconds, validates dates/calendar/ranges, and retains only approved fields. Cache entries receive the same validation as upstream responses, with a 24-hour lifetime and date/calendar/version keys containing no identity or student fields. A haftarah Hebcal gives as several ranges (`haft` as an array) is kept whole as its segments joined by "; "; a haftarah that fails validation is dropped on its own (`haftarah: null`) and never takes the Torah reading with it. Version 2 preserves an explicit regular/holiday/multiple/nonregular/missing classification; only explicit Shabbat `parshaNum` metadata establishes a regular portion (including double portions). Multiple results yield manual fallback without selecting the first item; the one exception is an eve or afternoon reading Hebcal lists beside the day's own (names beginning "Erev " or ending "(Mincha)": Erev Purim beside Shabbat Zachor, Yom Kippur's Mincha, Erev Simchat Torah), which is set aside, and if exactly one reading is left it is the day's. A festival on Shabbat is classified `holiday`, and the signed-out reading shows its joined Torah range (the aliyot as one gapless range, or none). Hebcal's `v` verse count for Numbers 25:10-26:4 is one more than the catalog's; that one overcount is accepted and the catalog's count is kept, and every other mismatch is still refused. The two-year reference table (T10, diaspora) is replayed in `tests/app/public-reading-calendar.test.ts` from `tests/fixtures/portal/public-reading-*.json`. Every stored payload additionally carries a required normalized `{version,date,calendar}` binding, even when its items are empty. Cache reads reject missing or mismatched bindings independently of the lookup key. Cache writes are through the injected interface only; this module has no database or routes.
- `proposeReading(snapshot, verseCounts, {pick?, confirmed?})` produces an unconfirmed Torah proposal separately from the unchanged confirmed reading. Date changes set `confirmedDateChanged`; they do not replace its ranges or revision. Selection is custom-first: no helper is chosen by default; staff must opt into full/triennial/aliyah suggestions explicitly. Empty dates have no invented parashah; an explicit validated custom Torah range can still be proposed on them. Full/triennial/aliyah selection requires a calendar reading. Special maftir is kept separate. Gapped or overlapping automatic joins are refused. CRC `torah`, `entryCap`, and `nusach` remain `toConfirm`.

`verseCounts` is a mandatory trusted metadata dependency: canonical book identifiers mapped to numeric per-chapter verse counts. There is no full catalog in this slice. The later Sefaria/text integration must provide reviewed chapter-length metadata using the same versification, never user-supplied counts or translation text. Tests use a tiny synthetic catalog to exercise real boundaries. Torah and optional haftarah references validate against it; missing metadata denies use.

An expired entry is not served as a usable proposal when upstream fails. `ReadingUnavailable.cachedAt` lets a caller explain the stale-cache date without exposing or accepting old ranges. Errors contain no raw response bodies. No ceremony dates were sent to a live API during implementation; all fetch tests are offline.

The canonical official documentation is [Leyning API](https://www.hebcal.com/home/4277/leyning-torah-reading-api); the old `/home/1959/` link in the planning documents was inaccessible. Documented parameters are `cfg=json`, `date=YYYY-MM-DD`, `i=off|on`, and triennial data enabled by default. The adapter explicitly requests `triennial=on`. Weekday and holiday items may lack a numbered weekly parashah/triennial block; this is a selection case, not an error to repair with a guessed weekly reading.

`readingDate(ceremonyDate, serviceSlot)` derives only Saturday morning (same date) or Saturday Havdalah (exactly seven days later). Unknown slots and non-Saturday dates require manual references; it never advances past a holiday. Staff preparation binds ceremony date, slot, derived date, student/assignment revisions and current authority to the explicit confirmation.
