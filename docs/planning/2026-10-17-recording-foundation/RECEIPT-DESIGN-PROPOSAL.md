# Media receipt and admission proposal

Design proposal for root decision, not schema/runtime approval. Targeted source: recordings authority, registration, data, retention and current practice/access lock contracts, plus the private-media spec (SHA256 de949fea7c5802a4206e60a7d84eb1b728387782f8d8c58249fb31280a124479) and independent MEDIA-DESIGN-REVIEW. No source, schema, provider, credential or private-data operation. Provider remains undecided; this proposal makes no new price or bill-cap claim. Keep0020 immutable and add a later reviewed migration. Revision incorporates root's larger capacity bounds and rejects permanent full-size quarantine as the normal cleanup path. Grant-after-local-stop, same-transaction original-ID registration and minimal original-ID tombstones have root's high-level acceptance; other mechanics below remain proposed.

## Smallest durable model

Use one **recording asset/receipt row**, which later becomes its cleanup tombstone, rather than separate upload/event/job histories. Store:

- Immutable tenant/student, client request UUID, server capture/asset UUID and original recording UUID; unique(tenant,student,request UUID), globally unique asset UUID and recording UUID. Derive the sole object key from asset UUID; never accept/store a client URL/path. Bind an opaque server-configured store generation so a later configuration change cannot retarget old objects.
- Immutable original selected mode, user/membership/grant/session IDs and relevant authority/grant/link revisions; exact child context ID/expiry when applicable. Existing authority checks remain necessary; stored bindings are never grants. Do not cascade-delete this row with a session, account or membership.
- Revision, state (`pending`, `verifying`, `registered`, `deleting`, `purged`), creation, fixed grant/finalize deadlines, database-enforced retention deadline, grant-attempt count, verification-attempt count and immutable upload byte ceiling. Derive separate active-upload, registered-byte, unresolved-cleanup exposure and compact-tombstone classifications; do not equate all non-forgotten keys with pending uploads. Pending is private quarantine, never playable. A registered row binds its original ledger ID through a nullable composite FK; no retarget/revival transitions.
- Bounded internal verified facts only when obtained: ETag/version, SHA256, byte/frame count, duration and canonical type. Verification/cleanup claims contain an opaque nonce, lease expiry and revision; cleanup additionally records next attempt and provisional/confirmed absence. No signed URL/token, raw error, body or public DTO contains these facts.

Add one **tenant admission serialization row**. Derive pending/object/count/charged-byte totals from indexed receipt rows while holding that row, avoiding duplicate mutable accounting counters. All operations that create/release a reservation obey the same lock. Add a small operator-managed **cleanup scope** mapping the actual cleanup login principal to allowed tenants; it has no user-role dependency. These are three proposed tables, including the receipt itself. Ordinary recording DTOs remain unchanged.

After terminal deletion, compact operational facts: preserve only original request/capture/asset/recording identity, scope, terminal state and the grant/cleanup facts still needed to prevent replay/reappearance. Clear creator/context bindings, media hash/size/duration and exact capture times once no longer needed for live work/rate windows. Keep minimal original identity with the student's existing ledger namespace; do not automatically forget it and treat an old UUID as new. Audio is never in a tombstone. If physically deleted ledger rows are removed too, a worker-only DELETE gate must require terminal asset confirmation and preserve the opaque original-ID tombstone; runtime DELETE remains forbidden. Root must settle this metadata compaction versus retaining the existing deleting ledger row.

## Begin, finalization and unknown outcomes

**Issue the five-minute write grant only after explicit local stop/save**, as root settled. A ten-minute microphone take cannot consume a five-minute grant in advance. The browser uses existing requestPortal and the exact practice header; admission failure can therefore occur after local capture, with no hidden upload/retry.

1. Fresh `createRecordingAuthority` write authorization, current not-due student and immutable actor/context binding; then admission lock and scoped request lookup. Insert the original IDs and reservation atomically, before any signing. Propose a closed declared byte length from the stopped local Blob, constrained to a possible nonempty canonical length (even data, at most28,800,044 total bytes under the ten-minute bound, also below32MiB), used ONLY as a restrictive signed upload ceiling/reservation; it is not trusted media proof. Actual verifier length must equal that immutable declaration. A dishonest larger declaration consumes that larger quota; a smaller one must be enforced by storage before accepting bytes. If an adapter cannot enforce the narrower ceiling, conservatively reserve32MiB and account for the capacity consequence below. Only a positively acknowledged DB commit allows signing. An unknown begin commit is reconciled by the same request UUID, never a fresh asset by default.
2. Record a grant attempt under CAS, then sign outside SQL locks. At most two signing attempts, always the same exact nonoverwriting key/cap/type and original expiry. Expiry is at most five minutes from first admission, clipped by session, child-context and recording retention. A second attempt never resets it. No bearer URL is persisted. Fresh authorization and receipt CAS after signing decide whether to disclose the capability. Revocation during signing leaves only bounded quarantine; it cannot undo an already disclosed PUT capability.
3. Explicit finalize claims the pending receipt with expected revision and a60-second lease, clipped by its fixed15-minute finalization deadline and authority expiry. At most three verification attempts; concurrent claims conflict. Commit this short transaction, then fetch/verify immutable bytes outside SQL locks under a30-second total I/O/verifier budget. Provider path/ETag and accepted WAV facts, not browser metadata, are the evidence.
4. Open a NEW authorized transaction. Revalidate exact original binding, current session/context/link, student retention, receipt revision/nonce/lease, object identity and all verified facts. Atomically insert the original ledger ID, write the existing create audit once and consume the receipt. Any failure rolls back all three. A lost acknowledgement is unknown; an explicit scoped receipt reconciliation read must precede another mutation. Stale expected revisions conflict, including no-ops. A registered receipt reconciles to the original ID/current ledger state, without reupload, re-registration or duplicate audit; deleting/purged never revives. Expired/revoked original context cannot be silently adopted by a new session. Freshly authorized ordinary ledger listing remains the way to find an already registered recording after relogin.

Expose only fixed status/revision/original recording ID where current authority and retention permit; no creator IDs, storage locator, hash or provider error. Unrelated/foreign receipts share404; selected parent/staff modes cannot begin/finalize. Same UUID with mismatched immutable scope/binding is a generic conflict, never a replacement. An uncertain PUT is checked by finalization against the original path; a browser success/failure response is not persistence proof.

The narrow registrar refactor is `registerVerifiedInTransaction(tx, actor, fresh, originalRecordingId, verifiedDescriptor)` in the existing internal registration module, callable only from trusted composition. It uses the caller's transaction and immutable original ID; it does not open nested authority transactions. Existing data.insert currently generates a UUID and registrar.register opens its own transaction, so calling those unchanged would break receipt atomicity. Keep registration absent from runtime/HTTP; do not expose arbitrary IDs/descriptors as request data.

## Initial engineering bounds for approval

| Limit | Proposed initial value |
| --- | --- |
| One object |32MiB; canonical24kHz mono PCM16; ten minutes |
| Active pending/verifying uploads |2 per student,2 per originating actor across sessions/roles,8 per tenant; a durable terminal cleanup transition leaves this pipeline count, but not its unresolved byte liability |
| Media capacity including active reservations and unresolved exposure |10GiB per student,256GiB per tenant; root-proposed engineering bounds, not Daniel-approved spending caps |
| Registered/retained audio objects |1000 per student,20000 per tenant; queued deletion still occupies a slot until safely terminal, compact tombstones do not |
| Indeterminate provider cleanup outcomes |Initially8 per student,64 per tenant, separately tracked; pause new grants at this fault ceiling and drain/alert. An ordinary queued deletion awaiting its first bounded attempt is not itself a failed/unknown provider outcome |
| New admissions |4/hour and8/rolling24h per student and originating actor;16/hour and64/rolling24h per tenant |
| Retained original-ID rows |4096 per student,65536 per tenant; fail closed at ceiling rather than silently forgetting IDs |
| Attempts |2 grant signatures and3 verification claims per receipt; no automatic new receipt after failure |

Retries of the exact existing request do not consume another admission or reservation; new signing/verification attempts still consume their own limits. Count admissions across aborted/failed captures too. Keep the minimal rate facts for at least48hours before compaction; use server clock, not caller timestamps. Actor limits use stable tenant+user/membership, not session/context alone. Student/tenant limits survive role/account changes.

Root's planning workload is approximately34 students×3 takes/week×4.33 weeks/month×21 months=9275 files/80GB, about273 takes/student. The previous1000-tenant-object/8GiB limits were inadequate. The proposed20000 objects/256GiB supports that ordinary retained workload with headroom; the per-student1000 objects/10GiB is also above it. These are capacity choices, not a cost estimate or bill cap.

Admission sums active reservations + registered/queued-deletion bytes + indeterminate cleanup exposure, without counting a compact terminal key as stored audio or counting any receipt twice. An anniversary cohort can create a normal queued deletion backlog without immediately classifying thousands of objects as failed provider attempts; that backlog remains charged and occupies audio-object slots until drained. While a grant might still recreate an object, charge at least its immutable enforced ceiling, not a smaller claimed/observed size. A verified registered object with exact declared/verifier byte equality is charged once at that ceiling, not as both a pending take and a registered object. After a proven safe terminal transition, retain the compact identity/marker and release its media charge; tombstone object/storage-operation costs remain separate. A metadata count ceiling bounds eventual original-ID growth without forgetting keys.

Exposure is explicit: if every ordinary9275 request permanently reserved32MiB, the total is about290GiB, exceeding even the new256GiB tenant ceiling. At most8192 such unresolved32MiB paths fit256GiB, and320 fit a10GiB student ceiling. Reserving an enforceable honest per-take byte ceiling would put the ordinary example near80GB, but does not solve indefinite accumulation across cohorts. Therefore neither larger quotas nor narrower declarations substitute for a viable terminal cleanup protocol. The proposed64-terminal-unknown ceiling bounds that transient exceptional pool to at most2GiB tenant-wide (8/student at most256MiB), in addition to the8 active uploads at most256MiB tenant-wide. These amounts count inside, not above, the aggregate media capacity. It is an outage/fault containment limit, not the normal destination of every deleted recording.

The operationally live normal path should release media liability through a provider-proven terminal mechanism, with the same-key sentinel candidate below preferred for investigation. Without one, permanent accounting pressure is a concrete unresolved protocol defect; do not activate an implementation that merely waits indefinitely and calls that healthy. Ordinary retry/cleanup UX, throughput and alert thresholds still need root acceptance. Playback traffic and storage operation charges are outside these byte limits.

## Lock order and ceremony changes

Preserve existing tenant→user→session→membership→grant→student→link→context authority order. Never upgrade the already-held tenant/student SHARE locks to serialize admission. Append the dedicated tenant admission row, then **existing ledger row→receipt**. No provider call occurs in any SQL transaction. Avoid acquiring a second student's authority locks while holding admission. A single tenant serialization row is enough for these bounded totals; no per-student lock hierarchy is necessary.

First registration is a real exception, not a claim that SELECT locks a missing row: there is no ledger row to lock, so it locks the receipt then INSERTs the reserved original ID. Safety requires all receipt-backed ledger creation and cleanup transactions to hold the same admission row BEFORE checking current ledger existence; reread after obtaining it, not from an earlier candidate snapshot. This serializes absent-row creation against workers/other finalizers. The existing registrar must not independently create a receipt-owned asset outside this seam. If an implementation encounters a newly existing ledger after taking a receipt first, it rolls back/restarts in ledger→receipt order rather than acquiring that existing row under the receipt lock. Keep each claim/confirmation transaction to one student/object; a batch is a sequence of short transactions, not a collection of differently ordered row locks.

Ceremony changes cannot overlap first registration's student SHARE lock: either registration commits first and the date transaction sees/stages its ledger and receipt, or the date transaction commits first and fresh finalization is rejected. A worker must not acquire student locks; it uses admission→existing ledger(if any)→receipt and enforced deadlines. The date trigger uses student UPDATE→ledger→receipt, but never admission. Thus a worker waiting on a date-held ledger does not already hold its receipt, and the date writer never waits for the worker's admission lock. Existing user submit/delete can use ledger→receipt without admission when they do not create/release a reservation; they must never acquire admission afterward. FK-trigger locks and multi-row trigger ordering also belong in the native race proof. This is a proposed invariant requiring review/tests, not an assertion already established by current code.

This ledger-before-receipt order matches the existing0020 ceremony trigger, which locks/stages ledger rows while the student UPDATE is held. A later media AFTER-ceremony trigger should stage related receipts when OLD OR NEW anniversary is due at actual clock after waits; it must not acquire admission locks or release charges. For future→future rescheduling it updates only the SQL-derived retention deadline. An expired old deadline/deleting state cannot be extended or revived, including pending captures with no ledger row. Rollback includes date, ledger and receipt transitions; automatic cleanup invents no user audit.

Make the receipt deadline a DB-enforced projection, not client/cache authority: insertion and any permitted date change must equal the shared Chicago/calendar-year arithmetic, including Feb29→Feb28 and internal year10000. The receipt transition trigger refuses renewal of an already due deadline. This lets the cleanup role stage actually due rows using trusted receipt deadlines without SELECT access to names, contacts or ceremony dates. Fresh user finalization still checks current student through existing authority/retention. Tests must demonstrate the trigger projection and all race orderings before relying on it.

## Account-independent cleanup authority

A separate restricted login/group, no runtime membership, owner URL, BYPASSRLS, CREATEROLE or SECURITY DEFINER, receives tenant RLS through the operator-managed cleanup scope. Scope lookup uses actual session_user, not a caller-set boolean/GUC. It remains valid when tenant.enabled, users, memberships or relationships are disabled. Give column SELECT only for opaque IDs/key/store binding, state/revision, enforced deadlines and claim/retry/absence fields; no audio bodies, names, contacts, actor/session bindings or hashes.

Worker SQL may claim/update cleanup fields and stage a ledger/receipt only if the database predicate proves: already user-deleting, actual retention deadline reached, or unregistered admission/finalize deadline expired. Separate transition guards apply to worker writes; granting UPDATE(state) alone would otherwise permit arbitrary early deletion. It has no registration/submit/create permission and cannot release reservations merely by setting a flag. Runtime has no physical-confirmation, compaction or cleanup-scope privileges. Candidate selection is an unlocked bounded projection; claim transactions use admission→ledger→receipt and **do not acquire student/user/session locks**. Eligibility comes from enforced deadlines; ceremony writers already preserve the old-or-new due latch. This avoids worker receipt→student inversion against ordinary authority/student UPDATE. Recheck eligibility and actual time after each wait.

Use CAS claim nonce/revision with120-second leases, bounded provider terminalization/absence checks outside SQL, then a fresh claim/eligibility transaction. Absence after a timeout is provisional; duplicate/missing-object results are safe, but never imply no late writer. Back off1,5,15,60minutes, then hourly with capped jitter; exhausted/repeated failures enter the separately bounded unresolved pool and alert, rather than permanently consuming active-upload slots. Their possible bytes remain accounted until safe. Propose hourly kickoff, each run <=60seconds/100 objects, at most4 concurrent operations, <=5seconds per provider operation; stop admitting work before its deadline and leave a durable more-work indication. Physical cleanup latency includes backlog/provider failures and is not claimed instantaneous or within one hour. Return aggregate results only.

**Live terminalization candidate, pending research/proof:** replace the audio with a permanent zero-byte/non-audio sentinel at the SAME opaque key. If the provider actually enforces atomic create-only conditions at completion, every earlier nonoverwriting PUT must then lose against the existing sentinel; audio cannot reappear merely because the upload grant remains valid. This would allow a permanent compact receipt/key while releasing its audio reservation, without inventing a maximum in-flight duration. The marker is not playable, never has a ledger read grant, and does not count as a registered recording. Root has suggested R2/S3 If-None-Match:* and asks whether Blob allowOverwrite:false proves the required equivalent semantics; neither is asserted here as an accepted provider guarantee.

The proof must cover a PUT held before/through terminalization, evaluation at commit rather than only request start, marker installation racing late completion, concurrent workers, marker overwrite/deletion protection and all old object versions/multipart remnants. If the object is initially absent, or replacement is not atomic, installing a marker alone is not completion: a racing late audio object must be conditionally replaced/reconciled until a durable winning sentinel is established. Hidden old audio versions are not physical deletion. If selected, root must explicitly revise “confirmed object absence” to verified audio erasure plus a durable non-audio blocking marker; the key intentionally continues to exist. Worker rights need only the exact scoped conditional terminalization operations, not a general overwrite path available to users.

An adapter-proven per-upload revocation plus removal/abort of every in-flight write, or a documented and live-tested finite completion bound, is an alternative. Simple expiry, a single DELETE/HEAD, an arbitrary safety delay or merely moving the bytes elsewhere is not. While outcome is unknown, preserve the opaque tombstone, account the possible bytes in the exceptional pool and reconcile with bounded HEAD/delete/terminalization attempts; no access or registration is revived. Do not retain a full-size pending reservation forever as the planned steady state. Any inventory/orphan recovery stays within the dedicated opaque prefix/store, bounded and independently reviewed. Sol1's provider research must resolve this mechanism before root approves the activation contract, not as a postlaunch liveness follow-up.

## Decisions for root

1. Root accepts minimal original-ID retention, grant-after-stop and atomic original-ID registration at high level. Approve/tune the larger root-proposed capacity limits, separate exceptional cleanup pool, optional enforceable declared byte ceiling and later deleting-ledger compaction. These engineering limits do not approve provider spending. A day-key alternative would let a caller change expectedDay after midnight and reuse a forgotten UUID: the old body would be rejected, but original-ID idempotency would be lost. Lost first responses before/after midnight must instead find the same original receipt with its original deadline. A truly forgetting design needs a separate server-issued signed expiring namespace/capture nonce that a client cannot retimestamp; it changes the API and still must define lost nonce versus lost admission responses. No such extra protocol is recommended here.
2. Approve the ledger→receipt/admission lock order, new AFTER-date projection trigger and worker-only eligibility/compaction grants. Native race tests must prove no cross-student/date/claim deadlock and no arbitrary worker write.
3. Choose the researched live terminal mechanism: same-key permanent sentinel with proven atomic create-only semantics, or a defensible revocation/completion alternative. Validate scoped worker capabilities and throughput/backlog recovery against ordinary volume and outage limits. Neither a speculative tombstone TTL nor larger quotas cures the liveness issue. Store choice and paid provisioning remain root/Daniel decisions.
