# Single-key read diagnostic design review

Accepted for the bounded implementation described in `docs/superpowers/specs/2026-10-17-single-write-read-diagnostic-design.md`, reviewed Git blob `d2916493e02644f3b6859055ccfe82a78f356826` against source checkpoint `8caaeda2e24269f4c3b8d872a69d4942931371f2`. This is design acceptance, not implementation or native-provider acceptance.

The diagnostic has a useful, narrow purpose: collect the current response facts for the existing synthetic normal key without replaying the failed writer. Selecting exact `read-only-v1` in the CLI before the existing writer is sufficient; the writer's own selection must continue refusing that mode. All-absent silence, partial/unknown/combined-flag rejection before credential/SDK/network access, and zero access to mutation SDK members remain required. The derived normal key, fixed store, GET-only capability and confined private origin prevent this from becoming an arbitrary object reader.

The added precision resolves the consequential interpretation questions. HEAD classes describe size metadata only; body identity requires complete EOF and an exact generated-body hash. `contentLengthExpected` refers to U1MiB even when a known P31 or R33 body is observed. Only GET200, a nonempty confined response URL, a completed bounded known body, and both actual metadata checks can produce `observed`. Header booleans describe observations: absent or compressed-wire Content-Length, encoding presence, normalized URL inequality, and HEAD/GET disagreement must not silently become evidence that the old write proof passed. Unknown bodies and failed authorization, transport, bounds or context checks remain failures.

The one-key/eight-call/60-second/1MiB limits are adequate for this diagnosis. Implementation must enforce monotonic deadlines after settlement, byte-progress idle rather than empty-read progress, the 64-empty bound, early declared-length rejection, bounded or cancelled error bodies, and cleanup of late streams. Reusing native context and actual permission checks before and after I/O preserves current identity freshness; the SDK control-JSON exception remains the existing synthetic hosting trust decision.

The separate result schema and root-only fresh read round preserve the failed native round and its journal. Diagnostic success cannot prove the historical ETag, historical response headers, retirement, held-race behavior, or safe normal publication. The root operator must distinguish fresh operation identity from the fixed old target-run key and reject mixed write/read/older-probe output. No replay, cleanup, promotion, or receipt/runtime activation follows this review.

No design blocker remains. Focused implementation and independent tests should verify exact dispatch/no mutation reachability, diagnostic header variants, full-body classification, stale context and deadline/late-result behavior. This review used only the spec and targeted source reads; no tests, provider operations, credentials, or operational journals were accessed. Root and author working files were preserved.
