# Original-ID registration — independent design review

Reviewed only the bounded registrar contract `docs/superpowers/specs/2026-10-17-recording-original-id-registration-design.md` against source38d5a1d213058044a01272d2813b30267f2bc390. No implementation, tests, database/provider/credential/private-state operations or unrelated source edits. Root retains architecture approval.

The proposed scope is appropriate: one existing recording-authority transaction, closure-bound exact-ID registration, unchanged legacy random-ID/asset replay, no runtime/HTTP exposure or receipt/schema/WAV/provider expansion. Exact scoped original ID plus all immutable asset facts distinguishes replay from both ID and global asset collision. Private/submitted replay returns the current receipt without another audit; deleting never revives. Reuse of existing selected student/child authority, final freshness after the entire callback, and atomic audit/earlier caller writes is required. No new grant path is implied by exposing the real trusted internal transaction.

Two necessary implementation-contract clarifications:

1. **Drain pending work before transaction exit.** If the caller returns/throws while registration is pending, synchronously mark the scope closed/poisoned, then observe/drain the already-started registration promise INSIDE the authorized transaction before throwing the terminal failure. Every continuation checks active/freshness after its awaited SQL and cannot begin another SQL operation once closed. Merely throwing immediately on a pending-return fence can race rollback/connection reuse with an in-flight query or its later continuation. Observe rejection without an unhandled-rejection leak. A later closure call issues zero SQL and cannot revive the scope. The bound protects registration's closure; this is not a sandbox preventing trusted callback code from retaining the independently exposed tx.

2. **Preserve the closed collision signal through existing error masking.** `src/server/access/identity.ts` catches unknown errors and converts them to AccessUnavailable503; only AccessDenied subclasses survive. Choose a narrowly identifiable compatible internal sentinel or equivalent local mechanism, without changing the shared authority layer or translating unrelated auth/SQL/audit failures. Only that exact collision is converted to legacy generic conflict AFTER rollback. Invalidity, expiry, callback/audit/DB failure still rejects/rolls back; no catch-all conflict conversion or partial success. Poison state is recorded before returning/rejecting each failed or repeated invocation, even when caller code catches it.

These clarify the proposed fences rather than expand scope. After incorporation the bounded contract is acceptable for implementation; no other architecture blocker found. Callback zero-registration behavior may remain ordinary authorized internal composition; the stated maximum one invocation is sufficient. Pending-return detection means actual unresolved work, not an unverifiable claim that JavaScript can detect whether an already-settled promise was awaited.

Focused future evidence should include an actually held native insert/audit with early callback return: no premature transaction exit, no later SQL continuation, eventual rollback of caller/ledger/audit rows and no unhandled rejection. Also test caught invalid/repeated/concurrent failure poisons the whole callback; exact-ID+asset collision races; late escaped invocation has zero SQL; ordinary legacy exact asset replay remains unchanged. Existing unchanged auth/retention/privacy evidence can be reused. This review does not authorize implementation or release on its own.
