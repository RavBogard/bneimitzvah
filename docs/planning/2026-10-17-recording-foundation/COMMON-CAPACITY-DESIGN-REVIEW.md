# Common capacity design review

Accepted for bounded implementation with the two root-settled precisions below. This is a design judgment against the merged receipt/transport integration at `4530225`, not implementation acceptance or permission to activate media. No tests, database/provider operations, or source changes were performed for this review.

The selected gate closes the demonstrated bypass across the reviewed application insertion paths without claiming to constrain arbitrary SQL privileges. It needs no DDL, actor backfill, provider operation, finalizer or new callback capability. Existing legacy rows have no receipt actor/rate provenance: charging their immutable bytes, takes and original identities is appropriate; inventing admission-rate facts is not. Receipt pipeline/rate predicates remain receipt-specific.

## Required corrections, settled by root

1. Choose exactly one new legacy ledger UUID under the tenant mutex, before checking receipt-reserved IDs, and pass that same ID explicitly to the low-level insertion primitive. Current `data/recordings.ts:35` generates the UUID inside `insert`, so checking only the asset before calling it would miss the planned identity. An unused generating wrapper may be removed. No collision or unknown outcome permits selecting another UUID/retrying insertion. An existing asset replay uses that row's actual ID instead of inventing a new one.
2. A retained receipt reservation matching the ledger ID or asset wins over otherwise-exact replay. Refuse the overlap even when the ledger descriptor matches. There is no accepted consumed/finalized relationship in this slice. Only nonoverlapping exact replay gets the historical-over-cap exemption. Do not adopt, subtract, terminalize or silently consume a receipt.

These decisions resolve the two ambiguities found in the draft; incorporate them in the implementation contract before authoring code.

## Source-grounded acceptance boundaries

- `src/server/recordings/registration.ts:34` contains the two reviewed ledger insertion branches. `src/server/data/recordings.ts:34` and `:38` implement their random-ID/exact-ID INSERTs. Targeted insertion/callsite searches found no additional application ledger insertion path; `recordings/service.ts` changes existing immutable-size rows. A narrow regression should keep this fact reviewable. It cannot revoke runtime SQL INSERT privilege, nor protect against arbitrary trusted SQL issued through the exposed callback transaction.
- `registration.ts:59` currently enters the caller callback without acquiring admission. The new mutex must be acquired inside the existing authority transaction before callback entry, lookup or insert. Adding it only inside `registerVerified` would allow callback ledger locks first. Preserve authority/student locks → admission → at most one actual matching ledger → receipt/slots, no absent-row lock, later authority acquisition or multi-head work. Existing date processing does not acquire admission; maintenance must not acquire student locks after admission.
- `data/recording-receipts.ts:48` already reads primary receipt/slot/ledger liabilities with bigint arithmetic. All ledger states count; unreleased receipt bytes/takes are additive even when identities overlap, while original IDs are a distinct union. Slot marker allowance remains separate and retained. A genuinely new, noncolliding ledger adds exact descriptor bytes, one take and one ID to student and tenant; it adds no receipt slot, active count, marker or rate fact. Extract common retained-capacity predicates from `recordings/receipts.ts:36` without changing receipt active/rate limits.
- Preserve exact descriptor/state replay in `registration.ts:25`, including refusal to revive deleting rows. Freshly authorized, noncolliding replay above historical caps causes no insertion/audit or new liability. A new row must pass projected limits under the shared mutex using current primary facts. Recheck authority after waits and each await; no lossy bigint conversion or stale prefetched aggregate.
- Preserve the private exact-identity conflict bridge at `registration.ts:52`/`:99`; use a distinct private exact-identity limit bridge through the unchanged sanitizer. Ordinary AccessDenied, SQL/unique errors and audit failures cannot become quota/conflict signals. The one-shot scope, synchronous closure, caught-failure poison, pending-operation drain inside the authority transaction and final callback freshness at `registration.ts:62–97` remain mandatory for limit/collision failures too.

The accepted admission contract's receipt-only guarantee and activation blocker (`recording-receipt-admission-design.md:68–77`, `:99`, `:121`) are the baseline being strengthened; unrelated receipt authorization, date staging and commit-before-opening guarantees remain intact.

## Required implementation evidence

Exercise both registrar APIs and exact replay above limits; student/tenant byte, take and ID boundaries with deleting ledger and retained receipt usage; reservation overlap on exact replay; single UUID/collision refusal; no new audit on denial/replay; post-wait expiry; ordinary-error identity and caught/unawaited/escaped callback rollback. Native independent connections must measure receipt-first and registrar-first waits with capacity changing while blocked, plus mutex-before-callback entry. Replace only the old deliberate bypass assertion with observable serialization and a fresh post-wait decision; retain its independent retention race. Preserve date/one-head maintenance lock order and test rollback, not merely successful lock acquisition.

No source-level capacity guarantee is accepted until implementation and independent app/native regressions demonstrate these properties. Provider/route/worker/finalization activation remains outside this checkpoint.
