## Product and privacy boundary

- Keep raw details for **90 rolling 24-hour periods**, then dates practiced only, with all history ending at the authoritative ceremony's calendar-year anniversary. Submitted-recording retention is separate.
- **Raw detail reads: explicit student mode, own live student identity only.** Root corrected its preliminary linked-child raw-read suggestion: child practice can write and see the quiet dates calendar, but cannot read raw activity. Parent/tutor/admin modes also receive only dates, even when that user holds additional roles. The recording-specific linked-child playback exception is not a raw-activity exception. No existing child feature requires raw history.
- Event writes use explicit student or live linked-child `practice-write`; days reads use the existing selected-mode read capability. A role, request UUID, date, target selector or old context never creates access. No cross-student endpoint/report, leaderboard, durations, automated assessment, notifications or provider operation.
- An action kind (`visit`, `play`, `record`) is a client-reported practice action on currently authorized material. It does not prove listening, upload, capture, effort or mastery, grant recording/audio access, or bypass generated-chant release gates. A GET never manufactures a visit.

## Recommended online contract

Separate the APIs and DTOs: bounded per-student calendar reads return dates plus `serverDay`; raw event reads are a different student-only endpoint; event creation is student/child only. Propose raw page size 50 and calendar query windows of at most 366 days. Cursor/date selectors grant no authority. Days DTOs contain no counts, kinds, event IDs, targets, actors or precise timestamps. Raw DTOs may contain the student's own current-window event ID/day, server receipt time, action and historical target metadata, without writer/session/context identifiers, audio URLs or licensed text.

Create body is closed: selected mode, client UUID, `expectedDay`, action kind and a discriminated current-material binding. No client timestamp/timezone, duration, score, actor or arbitrary past date. `expectedDay` must equal the server-derived current `America/Chicago` date, obtainable from a calendar read; this is an online day fence, not a read-issued authorization token. No offline lease, queue, automatic next-day replay or service worker is introduced.

Dedup namespace is **tenant/student/serverPracticeDay/clientUUID**, not globally unique UUID. The first raw row wins and is immutable. After fresh current authority/day/material checks, both exact repeats and different-writer/payload reuse receive the **same day-only acknowledgement**, without modifying or exposing the old raw row. This promises the date marker, not per-event storage or a receipt; silently retaining the first report is therefore not an integrity failure. It avoids a child-visible raw-existence bit or new actor-bound receipt semantics. Reusing a UUID on another day is a new intent; do not claim global dedup. An old body's day can never become eligible after the 90-day raw purge. No indefinite per-event receipt, hash or audit entry is needed.

After every authority/material/day/unique/database wait and before any successful, replay, conflict, quota or write result, recheck real session/context expiry, expected day and overall retention cutoff. Midnight invalidates an outstanding write and rolls back raw plus date-marker changes. Reads must also filter against fresh response-time retention bounds after delayed queries, rather than projecting rows that expired while a query/result was held.

## Minimal persistence and bounded eventing

- `practice_event`: scoped UUID/day key, immutable server receipt instant, action and canonical historical material identifiers. Root approved only a server-derived source-mode flag for attribution, without user/session/membership/grant/context IDs. All detail expires together; no full payload history or parallel audit receipt survives it. Avoid an assignment-verse UUID FK: current confirmation recreates those UUIDs. Store historical assignment/ref or service-plan/unit metadata without retaining passage/feed text or resolving withdrawn content on history reads.
- `practice_day`: **tenant/student/date only**, unique per day. No count, minutes, first/last time, actor, event ID or receipt hash. Insert the raw event and date marker atomically; a nightly rollup is unnecessary. Clearing raw details preserves the marker until overall expiry. Reads do not write.
- Root approved **512 raw events per student per Chicago day**, shared across writers. Insert/find the day marker, lock that day row, then derive the count from current-day raw rows under that serialization. If below the cap, insert raw with scoped `ON CONFLICT DO NOTHING`; at the cap omit additional detail. Existing same-ID reports still acknowledge at the cap, without needing a public replay lookup/flag. Never store a daily count. The rolling UTC window can intersect more than 90 Chicago date buckets because of partial dates/DST; do not advertise `90 × 512` as an exact maximum.

**Root approved uniform quota acknowledgement:** `{ok:true,practiceDay}`, with no raw-stored/count/replay flag, equally for student and child writes. A child-facing “512 events reached” response would leak a raw-count threshold. The acknowledgement promises the date marker, not storage of every event; the student's separate raw endpoint shows only bounded persisted reports. Root also prefers uniform same-ID mismatch acknowledgement, which this independent review endorses: collisions cannot overwrite action, target, time or attribution, and do not produce inferred assessment. ## Retention, rescheduling and cleanup

Use a validated server instant and fixed Chicago calendar helper. Raw visibility is `receivedAt > now - 90 * 24 hours`; delete at or below that bound, additionally constrained by the overall cutoff. Overall expiry begins at **00:00 Chicago on the calendar-year anniversary**: current local date at or beyond ceremony plus one year. Clamp February 29 to February 28 in a nonleap target year, matching the accepted recording policy's anniversary convention. Existing real-date validation accepts years 0001..9999; recommend internal numeric anniversary parts allowing year10000 for the last input year, without exposing a five-digit cutoff DTO. SQL date arithmetic can compare this internally. Do not blindly inherit the recording helper's four-digit-output limitation or silently retain forever on overflow. Do not use client timezone, a cached deadline, transaction-start `CURRENT_DATE` or `now()` after a lock wait.

Root chose a narrow **SECURITY INVOKER ceremony-date-change trigger**, with tenant-RLS-scoped DELETE grants on the two practice tables, rather than a privileged definer function. The student UPDATE already holds its row lock; evaluate actual `clock_timestamp()` after that lock. If **either previous or replacement** anniversary has already expired, delete raw and date rows for that exact tenant/student in the same transaction. This covers current roster updates and all future/import/direct-SQL writers, prevents postponed ceremonies from revealing overdue rows missed by maintenance, and rolls back with the date/audit if the enclosing operation fails. If neither deadline is due, the current ceremony governs future retention; deleted data is never reconstructed. This is a practice-history rule, not a change to submitted-recording retention.

Provide testable internal bounded maintenance for raw cutoff/all-history cutoff, under consistent student locking and actual post-lock time. It must physically remove expired detail and expired dates; immediate read filtering protects privacy while a sweep is delayed. No public cleanup endpoint, scheduler deployment, provider job or production operation is part of this slice. DELETE grants are solely database privileges used by reviewed retention paths, never a new user-facing erase capability; RLS and exact tenant/student predicates remain mandatory.
