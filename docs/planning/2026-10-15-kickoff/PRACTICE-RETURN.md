# Per-tab child practice service checkpoint

Built on published `18918c0`. This is a bounded backend service; routes, UI/sessionStorage, translation drafts, recordings and live providers are not implemented here. Independent adversarial review and primary integration remain required.

Files owned: `src/server/practice/{service,handles,types}.ts`, `src/server/data/practice.ts`, narrow `src/server/access/{types,identity,service}.ts` changes, `tests/app/practice{.test,-fixture}.ts`, this note. No migrations/dependencies, changes to published SQL, roster/runtime-worker files or Git operations.

`createPracticeService({ access })` exposes:

- `enter(POST, { studentId })`: requires no context header and returns the private `{ handle, context }` response. The 32 random bytes are hashed with SHA-256; only that hash is stored. Context metadata is `{ id, authorityRevision, studentId, studentRevision, expiresAt }`.
- `switch(POST, { studentId })`: requires the previous tab's `X-Practice-Context`; authorizes the new child before atomically closing the supplied old context and creating its successor. It never changes other tabs. An already-closed old handle cannot initiate another switch.
- `exit(POST)`: closes only the supplied context bound to the actual user/session/tenant/membership. A bound expired context or revoked old guardian/grant does not prevent cleanup; already-closed bound handles return `closed` without another audit.
- `read(request, { mode: 'child-practice' | 'student', studentId })`: returns safe student metadata and context identity/revisions, never the handle. Own-student mode is explicit and headerless, using the existing live student-identity path.
- **Internal composition only** `withPracticeCapability(request, { mode, studentId, capability: 'read' | 'practice-write' }, callback)`: a trusted server operation chooses the literal capability/callback. This does not expose a caller-selected arbitrary database operation. No future translation/audio feature is claimed.

All mutations, including future practice-write callbacks, require exact POST/Origin against independently resolved tenant origin. Cookie/session authentication remains mandatory; no handle in a URL is accepted. Child practice requires live verified user/session, enabled tenant/membership/student, exact active parent grant and practice-enabled live guardian, matching context target/session/grant/guardian/revision, no revocation, and strict unexpired context. Expiry is `min(now + 60 minutes, locked live auth session expiry)`. Changes are rechecked on every action. The shared identity now exposes locked `sessionExpiresAt` and rejects any context header by default; practice alone explicitly opts in. Base-role capabilities reject the header too, including blank values, so a parent+tutor's child request cannot silently acquire tutor/admin capability. An intentional headerless staff request still requires its independently selected real staff grant; there is no global active-mode cookie. Auth SDK logout is untouched.

Lock order is tenant → auth user → auth session → membership → parent grant → new/target student → exact guardian → practice context. Reads and ordinary practice writes hold SHARE authority/context locks until the callback transaction completes; enter/switch/exit take UPDATE from the outset. Thus an already-authorized write may finish before a switch/revoke, while a switch/revoke that commits first makes later old-handle writes fail. Switching authorizes the new child before mutating the prior context; its old relationship is checked only as immutable actor/session/tenant/membership provenance. Exit can use that provenance without requiring the old relationship still active. Context enter/exit changes and append-only audits are atomic; audits retain actor, parent grant, guardian and acting child directly even if logout removes the session/context later.

The future UI must keep the handle only in tab sessionStorage, send it only in the private header, never put it in URLs/logs/referrers/share links, and apply `no-store` to private creation/data responses. It must compare returned context ID/authority revision/student revision with the current request generation and abort/discard late old-child responses. Server denial of old-handle writes after switching is already implemented; browser response-generation handling is not.

## Physical PostgreSQL switch/write ordering

Added only `tests/postgres/access.integration.ts` and opt-in practice fixture additions in `tests/postgres/access-fixture.ts`; production practice/runtime code was not changed during independent review. The fixture uses actual Better Auth magic-link cookies, a parent+tutor identity with separately checked parent grant, two siblings, current published migrations, a generated restricted LOGIN inheriting only `portal_runtime`, and two max-one-client pools whose distinct physical backend PIDs are verified.

- **Write acquires authority first:** the internal old-child practice-write callback performs a real synthetic audit INSERT and pauses after PostgreSQL acknowledges it, retaining SHARE authority/context locks. The sibling switch on backend B is observed blocked by backend A through `pg_blocking_pids`. After release/commit, an interceptor immediately before the switch's real context UPDATE verifies the committed write is visible from the separate owner connection. The switch completes, the old handle fails, and the other tab and newly created handle both read their intended child successfully.
- **Switch acquires authority first:** backend B executes and acknowledges the old-context UPDATE while holding UPDATE authority locks, then pauses. Backend A's old-handle write is observed blocked by B. After switch release/commit, A returns the fixed 404 without ever entering its callback or inserting its synthetic audit. The closed old context is confirmed, and both the independent tab and new handle remain usable.

Interceptors delay actual driver operations and return actual results; no library internals, authentication proofs or query results are fabricated. Assertions require observed database lock edges, not elapsed sleeps. Barriers release in `finally`, operation rejection handlers attach immediately, and bounded settling/fixture cleanup drops only generated test databases/logins. Synthetic audit rows are transaction side effects standing in for a future separately-reviewed practice feature, not implemented translation or recording functionality.

Verification: Windows Node client against disposable WSL **PostgreSQL 16.15**, loopback port 55439; `npm run test:postgres:access` passed **7/7**, including the two new deterministic practice interleavings and all five existing access/invitation/reading tests. Typecheck passed. The reused disposable cluster was started for this run, used a fresh private in-memory test-only owner password (never printed), and stopped in `finally`; stopped status was checked afterward. Evidence logs: ignored `.local-logs/practice-postgres-races.log` and `.local-logs/practice-postgres-typecheck.log`. No production URLs, providers, student/family data, credentials in output, migrations or Git operations.

This establishes the application/SQL lock contract over physical PostgreSQL TCP connections. It does not establish live Neon WebSocket/pool behavior, hosted PostgreSQL 17 CI results, UI response-generation handling or any future practice data feature; primary integration owns those later gates.
