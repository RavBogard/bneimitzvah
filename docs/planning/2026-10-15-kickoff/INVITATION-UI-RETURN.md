## Surface and behavior

`/workspace/admin/invitations` links with the existing admin roster. It requires the explicit admin workspace and uses only reviewed admin invitation endpoints. Parent/student/tutor modes do not gain access through a role union. Private recipient contacts appear only in this authorized admin surface; no identity search or direct role/link granting is introduced.

This is a code-first Operate extension of the existing Annotated score workspace: flat white surface, fine rules, restrained color, existing system typography and ordinary labeled controls. The form, separate action review and invitation records keep different tasks visible without a modal or a new visual world. Phone fields/record details stack. No context/init/chooser round was repeated.

The form requires an explicit parent/student/tutor role and recipient. Parent/student invitations select one active roster student; sibling invitations remain separate even with the same parent mailbox. Student invites reject a matching parent contact locally, with final eligibility enforced by the server. Tutor invitations carry no student target. Account access is granted only by the existing verified explicit acceptance flow, never by typed contact data.

Review is memory-only. Any input edit clears it. Its fingerprint includes exact recipient/role/target and relevant student revision, name/date/contact/disabled state; row actions include the immutable invitation ID and its current lifecycle/delivery fields. Focus revalidation hides/inerts private content through the existing provider; same-session drafts remain mounted, changed binding discards them. Changed target fingerprints invalidate review. Before sending any action, the client re-reads the current authorized invitation page and complete bounded roster and compares the captured review again. Missing/out-of-page or changed targets require reload and a new review; no silent retargeting or binding is performed.

Sending, reissuing and revoking have distinct explicit confirmations and a synchronous single-flight guard. Reissue targets exactly the reviewed old ID; server-side logic rotates the token and revokes the old record. The UI updates no lifecycle optimistically. Only a fresh list establishes accepted/revoked/expired/pending status; a replacement can be on another ID-sorted page. Revoking an invitation is explicitly separate from revoking already accepted access.

Lifecycle and mail outcome are separate. Durable list delivery permits only pending/sent/failed; pending means unconfirmed, with no background queue claim. Sent means the mail request was accepted, not proven inbox receipt. Action receipts can additionally report unknown; that receipt remains separate from list state. A lost mutation response may represent a completed action. Unknown/rejected outcomes block further actions until explicit reload/review, survive ordinary focus refresh, and never automatically retry. A403 honestly describes possible fresh-sign-in, current-access or recipient-rule requirements, without claiming which private condition failed.
