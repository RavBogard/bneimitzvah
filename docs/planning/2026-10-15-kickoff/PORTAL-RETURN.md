`createPortalService({ access, practice })` exposes:

- `sessionSummary(request)` returns `{ membershipAvailable, roles }` through the real verified-identity boundary and locked active tenant grants. No email, user/session/grant IDs, credentials/provider objects or automatically selected mode. Verified uninvited identities get `false, []`; disabled membership remains denied. A context header, including blank, is denied.
- `assignedReading(request, { mode, studentId })` returns `{ student, mode, context, readings }`. Base modes use the existing explicit-role read capability; child-practice uses its live matching handle/session callback. Safe student/context identity and revisions are retained. Missing confirmed assignments return an empty list. Only confirmed Torah/haftarah rows appear, explicitly Torah first. Assignments are locked SHARE in deterministic database kind order before querying verses by ordinal, preventing concurrent replacement from mixing assignment revisions and verse sets. Queries cap at three assignments (two expected plus failure sentinel) and 1001 verses (1000 allowed). Canonical range expansion must exactly match the ordered stored verses.

Reading DTOs whitelist assignment ID/status/kind/basis/revision, references/verses, confirmation date, review marker, source status/fetched timestamp/date/calendar and recognized fixed Hebcal attribution. No contacts, author/audit IDs, licensed text or raw proposal snapshots are projected. Unknown provenance stays null/unknown; attribution requires the stored recognized `source.reading.source === 'Hebcal'` marker. Missing review provenance or a confirmation/current ceremony-date mismatch requires review. Editing the ceremony date preserves confirmed references/source date and exposes the existing needs-review marker and updated revisions; it never silently recomputes the assignment. Inconsistent stored references/verses fail through the fixed service-unavailable boundary.

Invitation additions:

- `preview(request, { token })` accepts the raw token **only as internal input** from the future encrypted pending cookie. Requires actual verified matching mailbox, exact tenant and usable unconsumed/unrevoked/unexpired invitation. It checks recipient-role eligibility, active target and shared relationship-history/occupancy validation under SHARE locks, including target identity history when the recipient has no grant. GET never creates membership/grants/links, consumes tokens or appends acceptance audits. DTO: `{ role, student: { firstName, lastName } | null, expiresAt, requiresConfirmation: true, reviewBinding }`.
- `acceptReviewed(POSTRequest, { token, reviewBinding })` is the **exclusive future HTTP acceptance path**. It shares the locked `acceptCore` transaction with existing private `accept` compatibility callers and rechecks all eligibility/atomic-consumption rules. Preview is neither a grant nor a reservation. The common read-only `eligibleInvitedStudentLink` helper uses SHARE for preview and UPDATE for acceptance; no preview mutation or lock upgrade occurs.

Review binding is opaque `expiry.HMAC`, not readable signed JSON. A purpose-derived key from private `throttleSecret` covers server-recomputed invitation hash, session/user, tenant/origin, intended role/target and invitation expiry. Lifetime is min(five minutes, invite expiry, live session expiry). Acceptance verifies bounds and constant-time digest equality **inside the locked transaction**. Replacing the shared pending cookie from another tab cannot cause a reviewed token/child to change. Different session/origin, tampering, expiry and replay fail closed. No raw token/hash/mail/session fields are exposed in the binding. Future HTTP receives only the client review binding and internally decrypted token; raw request body/query tokens must not select acceptance. Foundation received these factory/signature contracts for later composition.

## Portal HTTP adapter and opaque student reviews

Files added: `src/server/http/portal.ts`, `tests/app/portal-routes{.test,-fixture}.ts`, `tests/app/student-bindings.test.ts`. Approved narrow protocol change: `src/server/students/bindings.ts`. Foundation separately owns auth, runtime composition, dispatcher, pending-cookie helpers and thin Next routes; those files were not edited here.

`handlePortalRequest(Request, HttpRuntime): Promise<Response | null>` returns null outside portal-owned prefixes, fixed private 404 for unknown owned routes and 405 with Allow for known wrong methods. `portalRouteMethods(pathname)` supplies the static method map before provider/runtime setup. Dispatcher must first resolve the actual incoming host; services independently repeat authorization. Exact route contracts:

- GET `/api/session`; GET `/api/students?mode&afterId&limit`; GET `/api/students/:id?mode`; GET `/api/students/:id/reading?mode`.
- GET `/api/practice/read?mode&studentId`; POST `/api/practice/enter` and `/switch` with `{ studentId }`; POST `/api/practice/exit` with `{}`. Parent handles use only X-Practice-Context. Enter/switch creation responses alone return the private raw handle; reads never do. Assigned-reading GET explicitly allows child-practice headers through to mode/target authorization, while base modes still reject them.
- GET/POST `/api/admin/students`; POST `/api/admin/students/:id/edit` with `{ expectedRevision, student }`; POST `/disable` with `{ expectedRevision }`; POST `/api/admin/students/import/preview` with `{ csv, allowDuplicates }` and `/confirm` adding `binding`. The admin URL explicitly selects literal admin capability. GET roster does not impose a mutation CSRF check; its underlying service checks the admin capability and returns contacts only there.
- POST `/api/students/:id/reading/prepare` with explicit `{ mode: 'admin' | 'tutor', kind?, pick?, ranges? }`; POST `/confirm` with `{ mode, binding }`.
- POST `/api/admin/invitations` with `{ role, email, studentId? }`; POST `/api/admin/invitations/:id/reissue` or `/revoke` with `{}`. Delivery status is sent/failed/unknown, never fabricated from a provider exception; 201 means the invitation row committed, not that mail necessarily arrived.
- GET `/api/invitations/pending` reads the raw token only internally from the encrypted pending cookie, then invokes verified preview. POST `/api/invitations/accept` accepts only `{ reviewBinding }`, reads that cookie internally and exclusively calls `acceptReviewed`. Direct token body/query inputs are rejected. Success clears the pending cookie; known invalid cookie decryption or preview404 clears it. Reviewed accept404 preserves it because review expiry/mismatch can be recovered through a fresh preview and another tab may hold a valid newer invitation. Authentication401/service503 are preserved; no CSRF error is treated as link invalidity.

Every POST, including import/reading preparation, requires exact resolved-Origin POST before body parsing. Inputs have closed fields, explicit types and bounded JSON/CSV/binding/query profiles; client tenant/actor/grant/callback claims, duplicate/unknown query fields, URL bindings/handles and unsupported modes are rejected. Responses project known DTO fields, convert admin dates explicitly, retain private no-store/no-referrer/nosniff headers, map stale revisions to409, and collapse unrecognized runtime diagnostics to fixed503. Parent/tutor modes never union, and practice headers cannot silently grant base/staff/invitation capabilities.

Before exposing staff/import reviews, primary approved replacing their readable signed JSON with **versioned AES-256-GCM** envelopes. Sign/verify callers remain unchanged; fresh 96-bit nonces, purpose-derived keys/AAD, authentication tags, strict canonical base64url, 32KB plaintext/48KB envelope bounds and existing five-minute expiry/actor checks apply. Legacy readable bindings are rejected; no live users/providers require compatibility. Private session/user/grant claims remain encrypted rather than appearing in preparation/import responses. No dependency or migration was added. This protocol change requires independent review alongside the HTTP adapter.
