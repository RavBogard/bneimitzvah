# HTTP/auth proposal — 2026-10-15

Status: architecture approved by Astra for staged execution. HTTP boundary and encrypted pending-cookie primitives are now implemented; routes/dispatcher/harness remain proposed work, not implemented. No dependency, provider setup or Git change in this worker slice. Reviewed current runtime/access/invitation/student/practice factories, auth-tenancy spec host/invitation/harness sections, pinned Better Auth endpoint implementations, Next/Playwright setup and disposable PostgreSQL fixtures.

## Implemented primitive checkpoint

- `src/server/http/body.ts`: `readJsonBody(request, profile?, deadlineMs?)`, fixed ordinary/binding/CSV byte caps of 16 KiB/64 KiB/2 MiB, streaming UTF-8 decoding and actual byte counts, strict JSON/UTF-8 media and identity encoding, length sanity/mismatch checks, 5-second maximum deadline (tests may shorten it), cancellation/abort-safe cleanup and fresh fixed diagnostics. Locked, malformed and failing sources never expose their errors.
- `query.ts`: `closedObject(value,required,optional?)` returns plain data from own descriptors, rejects extra/accessor/prototype/symbol fields; `uniqueQuery(url,allowedKeys)` enforces 2048-character URL bound, unique decoded keys, valid encoding, no controls/credentials/fragments, closed keys and no practice/session handles in URLs even if a caller lists such a key.
- `responses.ts`: `privateJson`, `privateRedirect`, `errorResponse`, `privateHeaders` provide fixed no-store/referrer/nosniff headers and fresh closed error payloads. JSON serialization copies plain data without invoking toJSON/accessors or serializing errors. Caller still deliberately selects its safe DTO; this is not an arbitrary object redactor. `appendSdkCookies` copies only bounded reviewed SDK cookie fields, preserving separate Set-Cookie and Expires commas; rejects domains, incorrect secure/name/path/SameSite/HttpOnly flags and unknown attributes. It copies no SDK body, Location or other headers. Both `state` (database strategy) and `oauth_state` (cookie strategy) are supported; pinned stateful SDK defaults to database.
- `pending-invitations.ts`: `createPendingInvitations({secret,origin,environment,now?})` exposes `exchange(Request)` for the exact token landing GET, `read(Request)` only for pending-preview GET/reviewed-accept POST, and `clear()` for deletion Set-Cookie. AES-256-GCM uses a fresh 12-byte nonce, authenticated origin, purpose/environment/origin-separated HMAC key and fixed 10-minute envelope. Canonical 256-bit token remains server-internal; no token JSON/localStorage route. Local cookie name is `portal_pending_invitation`; HTTPS uses `__Host-portal_pending_invitation`, Secure, HttpOnly, SameSite=Lax and Path=/ without Domain. Duplicate cookies, shadowing alternate names, malformed/oversized ciphertext, tampering, expiry, future-issued envelope, wrong origins and URL/header practice contexts deny fixed404. Actual tenant-host resolution and mutation Origin guard must still run in the future dispatcher before these helpers.

Twelve focused tests in `tests/app/http-boundaries.test.ts` and `pending-invitations.test.ts` pass; typecheck and repository guard pass. They cover multibyte chunk boundaries, false/missing size headers, stalled cancellation, abort and private stream diagnostics; closed authority/query fields; response serialization and leak sentinels; cookie encryption/nonce/binding/expiry/shadowing; and real `createAuthStack` Google initiation for local and canonical HTTPS origins, proving pinned `better-auth.state` projection with zero fetch calls. No actual Google callback/Neon/email/provider success is claimed. Detailed logs stay ignored in `.local-logs/http-*`.

Auth owner coordinated stable contracts: `createPortalService({access,practice})` exposes sessionSummary/assignedReading; invitation `preview` returns a five-minute `expiry.HMAC` review binding (also bounded by invite/session expiry); `acceptReviewed(request,{token,reviewBinding})` is the sole planned HTTP acceptance entry. Transport will pass only the decrypted cookie token internally and accept only `reviewBinding` from the client. Existing bare `accept` remains a private compatibility service, never an HTTP action.

## Chosen arrangement

Build one server-only `createHttpHandlers({withRuntime, pendingInvitations})` Request/Response dispatcher with explicit operation schemas. Thin Next App Router files export only supported methods, use Node runtime/dynamic execution and invoke that dispatcher with the real request-scoped runtime. Production composition stays private and never imports tests. Every dispatch resolves the **actual incoming** URL/headers using `runtime.resolveHost(request)` before SDK invocation or application service calls; checking only configured origin during runtime construction is insufficient. Existing live service capability checks remain authoritative.

Use Route Handlers first, avoiding duplicate Server Action transports. Do not mount the whole Better Auth catch-all with unrestricted `toNextJsHandler`: its session/read endpoints can expose fields the portal does not need. Preserve the SDK's actual handler for selected auth operations so its Set-Cookie, state/PKCE, origin checks and session lifecycle remain intact. The wrapper fixes input/redirect destinations and projects responses instead of forwarding arbitrary SDK JSON/errors. Pinned `better-auth@1.7.10` code confirms `/sign-in/social`, `/callback/:id`, `/sign-in/magic-link`, `/magic-link/verify`, `/sign-out`, `/get-session`, `/list-sessions` and revoke-session APIs. Google authorization endpoint is exactly `https://accounts.google.com/o/oauth2/v2/auth` in the pinned provider.

Bounded generic 429/503 as appropriate. |

| GET `/api/auth/magic-link/verify` | Exact pinned 32-letter token; unique allowed SDK query keys and fixed allowlisted callback paths. | POST `/api/auth/sign-out` | Empty bounded JSON; exact-Origin guard, SDK logout. | Empty success/generic denial; preserve only necessary cookie deletion. |
| GET `/api/session` | New safe session-summary service, not public SDK `/get-session`. | POST `/api/admin/students/{create,edit,disable,import-preview,import-confirm}` | Existing roster service, explicit admin mode and typed revisions/CSV binding. | Project existing IDs/revisions/preview validation; contact details only authorized admin roster endpoint. | POST `/api/students/:id/reading/{prepare,confirm}` | Explicit admin/tutor mode, existing preparation/confirmation service; no raw provider payload accepted. | Existing signed preparation/review or confirmed revision. Explicit confirmation stays separate; typed stale result becomes 409. |
| POST `/api/admin/invitations/{issue,reissue,revoke}` | Existing invitation service; fresh admin session, exact-Origin POST. | Invite ID and durable delivery classification only; no recipient/link/token. |
| GET `/invitations/accept?token=…`; GET `/api/invitations/pending`; POST `/api/invitations/accept` | Pending-cookie exchange, new recipient preview, existing explicit accept. Details below. | Clean redirect, verified preview and explicit acceptance; never raw invitation token. |

Unknown methods/operations are fixed 404/405. Do not publicly mount SDK get-session/list-sessions/revoke-session/profile/link-account or password endpoints. Logout is included; session-list/revoke-other-session management can follow as a separately projected identity-only endpoint using opaque IDs, because pinned SDK revoke-session accepts a raw session token. No current feature needs that token-bearing transport.

Ordinary JSON bodies: 16 KiB streaming cap, deadline and valid JSON media type; reading confirmation/preparation bindings: 64 KiB cap; CSV JSON transport: 2 MiB encoded cap plus the existing service's 1 MiB decoded CSV/500-row limits. Content-Length is an early rejection only; cap bytes actually read. Explicit closed object keys/types, finite bounded integers, max string/list lengths, unique allowlisted query keys, bounded URL/query length, reject unexpected bodies and content encoding; no generic object spreading into service options. Routine reads remain GET; preparation/import preview are POST because they consume bounded request inputs and signed state. Every cookie mutation retains exact Origin and existing Sec-Fetch-Site checks. OAuth/magic-link callback exceptions are narrow method/path contracts, not blanket CSRF opt-outs.

All private/auth responses, redirects and denials carry `Cache-Control: private, no-store`, `Referrer-Policy: no-referrer`, and `X-Content-Type-Options: nosniff`. Token landing/callback pages have no third-party scripts and no reflected query. Build safe response bodies/statuses explicitly; whitelist response headers and preserve each necessary SDK Set-Cookie separately, never copying arbitrary SDK headers/body/cause. Error redirects have one fixed generic error code, no provider text. Apply the existing fresh-error boundary so mutated errors cannot carry diagnostics. Preserve OAuth state cookies and the real SDK session cookie; do not synthesize authentication or copy a token into browser JSON. Platform/CDN access-log query redaction remains an operator setup gate beyond application logging.

## Pending invitation flow

Landing GET performs exact host resolution and syntactic token validation only; **no acceptance, grant, relation or identity lookup**. Encrypt `{version,token,origin,issuedAt,expiresAt}` with purpose-separated AES-256-GCM and fresh nonce, using an HMAC-derived key distinct from other bindings. Set a bounded 10-minute host-only HttpOnly SameSite=Lax cookie with Path=/; deployed name uses `__Host-` and Secure, local HTTP uses a separate nonprefixed name. Return 303 to `/invitations/accept` without query. Reject duplicate cookies, malformed/oversized ciphertext, wrong origin/version, tampering or expiry uniformly. No raw token in browser JS/localStorage, URLs after landing or logs. One pending invitation per browser cookie is explicit; a later landing replaces it.

Before authentication the clean page can offer sign-in but no family name, email or relationship preview. New `invitations.preview(request,{token})` must use live verified identity with no membership requirement, matching recipient/tenant and all current expiry/revoked/accepted/student-disabled checks; return only intended role and minimal authenticated target label. It must not mutate/consume the invite or create a grant. Reuse a shared eligibility predicate with accept to avoid drifting checks, while retaining transactional revalidation on POST.

Preview additionally produces a short-lived signed review binding to the pending token hash, current auth session, tenant/origin and intended role/target. POST `/api/invitations/accept` accepts that binding **without a token field**, decrypts the pending cookie, verifies its binding matches the current session and pending invitation, then invokes the existing transactional accept. This prevents another tab replacing the pending cookie between preview and confirmation from silently changing the accepted relationship. Clear pending cookie after success/terminal invalidity; cross-site GET, scanners and OAuth callbacks cannot accept. Cookie encryption is confidentiality/authenticity, not a substitute for database one-time redemption.

## Missing narrow service contracts

1. `session.summary(request)`: live identity plus available active grants projected to explicit modes; no default role, email, session token or provider profile. New data-layer grant lookup required. Auth-only verified users can see that they need an invitation; disabled/revoked membership remains denied. Child-context headers must not silently turn this into a staff summary.
2. `invitations.preview`: recipient-bound read above, plus signed preview binding issuance/verification through the pending transport boundary. Existing `accept` remains final authority.
3. A safe assignment read projection for the study page is still absent: `access.readStudent` currently returns demographics/date/revision only. Add it when the authorized reading page is built, with confirmed assignment snapshot/exact verses and needs-review marker under the same capability transaction; routes must not query assignment tables directly. This proposal does not invent study/progress write endpoints or authority-mutation callbacks.

## Isolated browser harness

Use a **test-only Vitest process** hosting a custom Next **development** server plus the same HTTP dispatcher, and launch Chromium using the already pinned Playwright package. Vitest already provides TypeScript loading and a module-local `server-only` test alias; do not globally set React's `react-server` condition or introduce tsx/esbuild merely to run the harness. Keep every custom server/bootstrap/capture file under tests, outside the production import graph. This is a test runner, not a custom production server; Vercel retains normal Next routes.

The custom server intercepts only the same approved application/auth URLs and calls the identical dispatcher with explicitly supplied test runtime components. Other URLs go through Next's real dev request handler. Its Node adapter must preserve actual Host/raw duplicate-header semantics, reject ambiguous URLs/hosts, stream bounded bodies, preserve separate Set-Cookie headers and sanitize errors. Production route wrappers get focused thin-adapter tests plus actual `next start` checks; custom dispatch does not prove framework wrapper behavior alone. Client role pages later consume these same HTTP APIs; server-rendered protected data needs its own real wrapper tests, not an undocumented injected global.

Harness startup requires all of: nonproduction NODE_ENV/build, explicit test-only invocation, no Vercel/deployment indicators, bind `127.0.0.1` only on a fixed tested port, and opt-in disposable PostgreSQL credentials validated by the existing fixture rules. It creates one uniquely named synthetic database and restricted LOGIN, migrates with the separate fixture owner, seeds exact test-host mappings and synthetic identities/grants, and gives handler components only the restricted connection. Reuse fixture provisioning/cleanup primitives rather than its existing automatic sign-in, so the browser actually initiates magic links through HTTP and consumes real SDK cookies. No app DATABASE_URL is read. Cleanup closes checked-out clients/server/browser and drops only names generated by this fixture, including failure paths.

Mail transport is a closure/in-memory queue accessible only to the **test process**, correlated to a synthetic recipient and drained by the test after the browser's real request. The test navigates the captured real verification link; it does not install a fake session or add `x-test-user`. No capture/list-token/sign-in helper endpoint exists on HTTP, including loopback. The dispatcher has no test flags or alternate identity path. Synthetic Hebcal transport is explicitly injected and provider egress is blocked; Google round trips remain unavailable until configured.

Use a separate explicit `test:http:browser` command/config so default `npm test` remains offline and existing production placeholder browser checks remain. Real-PG CI service supplies disposable synthetic credentials, then this command; no provider setup or new dependencies anticipated. Disable traces/HAR/network dumps/video for the private auth suite (existing smoke config retains traces); auth/cookie/link values must never reach test reporters or retained artifacts. Catch navigation/network/fixture failures and throw fixed diagnostics; assert booleans/statuses rather than letting matchers print captured mail, URL, headers or database rows.

Production denial proof runs the **actual built app** with `next start`, isolated empty provider configuration and attempted test flags/headers: proposed capture/helper URLs must return 404 and arbitrary test identity headers cannot create a session or authorize data. Local-mode flags under NODE_ENV=production fail closed. Assert the production import graph/bundle excludes test bootstrap/capture code and that no production branch imports it. No public endpoint is added just to prove denial. A deployed preview cannot activate the test server: it is a separately invoked tests-only process, refuses deployment indicators, and is outside runtime imports.

## Acceptance and staged implementation

First implement body/query/response boundary + pending-cookie primitives and the two missing read services; independent review before exposing auth. Then thin routes with real pinned SDK cookies and in-process request tests. Finally add the disposable real-PG/custom-dev-server browser suite and production-build denial checks. Keep each ownership slice bounded; root decides exact assignments.

Required checks: incoming unknown/forwarded/foreign host denies **before SDK or mail call**; redirect/PKCE/state protections preserved; bounded bodies/queries and unknown fields denied; no raw session/mail/token/provider diagnostics in JSON/logs; cookie Path/HttpOnly/SameSite/Secure and encrypted pending tamper/expiry/origin binding; landing GET never accepts; verified-recipient preview followed by explicit POST; preview/pending replacement mismatch denied; invitation replay and revoked links/session denied; admin/tutor/parent/student explicit modes plus cross-tenant and two-tab child-context isolation using actual handlers; actual session-cookie logout and missing-config failures; production build cannot enable a harness. Existing actual PG concurrency gates remain separate evidence, not replaced by browser Promise.all tests.

Risks/limits: custom-server interception covers shared handlers rather than Next route loading; thin production-wrapper probes are mandatory. No Google/Neon-WebSocket/Resend-provider proof comes from injected local components. OAuth success flow cannot be claimed without a configured provider; adversarial malformed callback/state behavior can be covered locally. Pending cookie allows one current invitation per browser; preview binding prevents cross-tab wrong-target confirmation. Platform access logs require redaction outside app code. No feature is released to students by this proposal.

Pinned local implementations were used for exact endpoint/provider assumptions. No documentation example's unrestricted SDK mounting is adopted as a security contract.
