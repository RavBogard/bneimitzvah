# Query-free authentication architecture review — 2026-10-16

**Disposition: architecture accepted for bounded implementation with the two contract corrections below. Current query-based authentication enabling remains blocked.** This is a source/design review, not implementation acceptance, observed Google delivery, or approval to enable production authentication. ## Required contract corrections

1. **Preserve the existing verified same-email linking policy.** Acceptance item 6 of the proposed spec says “same-email/different-provider policy refusal.” That is not the current policy. `tests/app/auth-stack.test.ts` explicitly requires verified magic-link → Google linking without a second user, and verified Google → magic-link identity reuse. The pinned `oauth2/link-account.mjs` permits implicit linking when the provider email and local email are verified; `trustedProviders: []` does not disable verified same-email linking. Root confirmed this correction during review: retain that behavior, reject unverified/different-email linking, and prove no role or student-relationship grant occurs. Do not change account-linking settings to satisfy the erroneous blanket-refusal assertion.

2. **Specify logout cleanup and its limit.** Expire the Google browser-binding cookie on acknowledged sign-out and invalidate the current UI attempt with a generation barrier, including late GIS callbacks. Keep that cookie after successful sign-in so a successful tab does not invalidate another outstanding tab. Test that a callback arriving after acknowledged logout cannot redeem its old unconsumed challenge with the browser's current cookies. Clearing a cookie cannot revoke an already-in-flight request that captured the old cookie; this is not a promise of global cancellation or login/logout race linearization. Any stronger requirement needs an explicit server-side invalidation/locking design. Root agreed to this bounded contract; no new infrastructure is necessary.

These are precise acceptance/lifecycle corrections, not grounds to replace the selected transport architecture. Apply them to the spec before assigning implementation.

### Blocking corrections

1. **Recheck the challenge deadline after obtaining its row lock.** In `google-challenge.ts`, `consume` captures `current` before entering the transaction/`SELECT … FOR UPDATE` and uses only that snapshot for expiry validation. A request waiting on a held row across its deadline can consume an expired challenge. Re-read the clock after the lock returns and require `expiresAt >` the fresh value, preserving the exact five-minute issuedAt/expiry binding before deletion. Add a regression that holds consumption, advances the injected clock across the deadline, releases the row and requires denial without an SDK call. Root reports that the author independently identified the same defect and authorized a narrow repair; this review has not yet accepted that repair.

2. **Rejected SDK outcomes must not propagate session-establishing cookies.** `auth.ts`'s Google final branch calls `cookies(response, sdk, …)` even for unexpected redirects/non-success. `magicResponse` also copies cookies when Location/status validation fails. An SDK response with a syntactically valid session Set-Cookie and a rejected Location can therefore return fixed HTTP 400 while still authenticating the browser. The projection contract requires unexpected outcomes to fail closed. Copy session-establishing SDK cookies only for an accepted successful outcome; preserve intentional sign-out clearing in its separate path. Add an adversarial projection case with a valid-shaped session cookie plus an unexpected redirect/Location and assert no session cookie escapes. The current mocked diagnostic cases omit Set-Cookie and do not exercise this boundary.

### Other bounded corrections and acceptance gaps

- The issuance origin budget key is the literal `portal-google-budget:v1:origin:<minute>`; it is not namespaced by configured origin/environment. Different configured origins sharing this auth table would exhaust one budget. Use the same purpose/origin separation as the HMAC-derived browser bucket and test independent origins. This is an availability/scope correction, not evidence of an authority leak. Stable origin → browser lock ordering and transactional atomic increments are otherwise appropriate.
- The stage-1 “late” logout test creates its challenge after logout, then omits its cookie. That proves ordinary missing-cookie denial rather than the required outstanding pre-logout callback ordering. Add the pre-logout issue → acknowledged logout/returned-cookie application → late callback sequence in the browser/HTTP checks, together with the client generation barrier. Retain the documented limit for an already-in-flight request carrying its old cookie.
- PGlite contention across repository instances is useful but does not establish cross-process PostgreSQL behavior. Root retains the real row-lock/concurrent nonce-consumption and SDK token-expiry/replay gates.

The resolver's authority parsing, actual-host comparison, Forwarded refusal, forwarded consistency checks, directory query and fixed AccessDenied(404) behavior remain unchanged. The patch adds a lexical stage selected from eleven fixed strings and a separately allowlisted frame. It does not interpolate a URL, host, header, tenant-directory value, error, stack, cause or provider payload into an event. `hostDenialEvent` checks both unknown dimensions are primitive strings and exact set members before interpolation; object/proxy/String-wrapper/symbol inputs cannot enter that operation through coercion. The logger independently accepts only its enumerated complete events and existing status vocabulary, then serializes only event, status and a newly generated request UUID.

Hostile URL/header getters or a rejected database operation still reach the same broad resolver catch. That catch does not inspect or serialize the thrown value, including a hostile proxy/error. Both logger construction and emission are inside a defensive wrapper; the logger also contains sink failures. A diagnostic failure therefore cannot replace the existing 404 with a construction/sink exception or expose its diagnostic text. No diagnostic code is returned in the HTTP response.

The three frames have distinct call sites: runtime preflight explicitly passes `configured` for its configured-origin request with empty headers; the HTTP dispatcher's actual request uses runtime `resolveHost`'s `incoming` default; direct capability resolution uses `resolveTenantHost`'s `service` default. A configured preflight pass therefore does not imply acceptance of the later incoming headers. Stage codes describe the check where denial occurred; they do not reveal a rejected value or prove which ingress intermediary supplied it. Each resolver diagnostic has its own generated UUID, rather than promising correlation with the outer runtime's request UUID.
