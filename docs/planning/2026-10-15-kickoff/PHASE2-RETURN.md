## Second backend slice — exact hosts and core access (2026-10-15)

Implemented on the published `2795dcc` prerequisite checkpoint. No routes, UI, invitations, owner bootstrap or child-practice issuance/redemption were added.

Files: `src/server/tenancy/resolve.ts`; `src/server/access/{types,errors,service}.ts`; `src/server/data/{tenant-hosts,authority,students}.ts`; `tests/app/access.test.ts` and `tests/app/access-fixture.ts`; exact `server-only@0.0.1` package/lock addition. Necessary reviewed database changes are `src/server/db/runtime.ts` and new journaled `0003_tenant_lock_permission.sql`; pushed migrations 0000–0002 are unchanged.

- Host resolution accepts only a normalized exact host+origin+environment+deployment directory mapping. Unknown/malformed hosts, the Vercel placeholder alias, wrong preview/deployment/port and ambiguous/mismatched forwarded headers fail with the same fixed 404. No forwarded header selects a tenant; no CRC fallback exists. Loopback HTTP is local/test only, and production/preview loopback is denied. Directory lookup reads no family/content table.
- `createAccessService({ db, auth, deployment })` exposes `readStudent` and bounded/keyset `listStudents`, plus **internal server composition** callbacks `withStudentCapability(..., { mode, studentId, capability }, callback)` and `withAdminCapability(..., { mode, capability }, callback)`. A trusted operation chooses its literal capability/callback; never pass a transport-supplied capability or arbitrary client callback. Student capabilities are `read` and `set-reading`; only assigned tutor/admin modes permit the latter. Admin capabilities cover student management, invitations, relationships and defaults; invitation/relationship authority requires a sign-in within fifteen minutes. Actual action services still need input/CSRF checks, target-specific writes and same-transaction audits.
- The mode is an untrusted selector, not a role claim: one matching live grant is required. Parent+tutor permissions never union. Own students require their individual live identity link; parents can read only linked children; tutors see assigned learners; admins see active learners in their congregation. Child-practice is rejected until its separate handle implementation exists. Student DTOs omit contacts, credentials and internal authority fields.
- The real Better Auth API verifies the signed cookie with caching/refresh disabled. In the same restricted tenant transaction, the service locks/rechecks tenant enabled status, live verified user, exact session/user/token binding and expiry, membership status, selected role grant, target student status and the current link. Foreign, absent, malformed, unrelated and disabled targets receive indistinguishable 404s. No actor header bypass is provided. The stale-proof regression uses the real public auth API, mutates the actual database after its valid proof, then returns that unchanged proof; the later locked checks still deny access.
- Lock order is tenant → auth user → auth session → membership → selected grant → student → relationship. Read/ordinary reading-write capabilities hold SHARE authority locks; authority-write callbacks take UPDATE from the outset, avoiding shared-lock upgrades. Admin callback capabilities currently use authority-write locking. Lists lock candidate student rows in ID order before rechecking/locking their links. Future revocation/context/invite services must compose under this ordering and cannot introduce multi-tenant work or authority upgrades inside ordinary callbacks. Callback writes/audit use the supplied transaction; rollback tests confirm both inserts completed before forced failure and neither persists.
- PostgreSQL requires an UPDATE privilege for SHARE row locking. Astra explicitly approved migration 0003 granting **only `UPDATE(customs)` on tenant** for that lock and future authorized congregation defaults. Runtime cannot change `enabled`, `id` or `tenant_host`; customs updates remain tenant-RLS scoped and require application admin authority. Negative tests exercise each boundary.
- Runtime validation additionally rejects unexpected transitive memberships outside `{session_user, portal_runtime}` and requires the active role to be the session user or `portal_runtime`. This catches misconfigured built-in groups such as `pg_write_all_data`, including after an explicit `SET ROLE` into that group. It complements the existing current/session role flags and owner-membership checks; it does not provision credentials.
- `server-only` marks each new server module. Tests mock only that inert marker inside `access.test.ts`; no production environment flag or identity bypass is introduced.
