Implemented on the published `2795dcc` prerequisite checkpoint. No routes, UI, invitations, owner bootstrap or child-practice issuance/redemption were added.

Necessary reviewed database changes are `src/server/db/runtime.ts` and new journaled `0003_tenant_lock_permission.sql`; pushed migrations 0000–0002 are unchanged.

- Host resolution accepts only a normalized exact host+origin+environment+deployment directory mapping. Unknown/malformed hosts, the Vercel placeholder alias, wrong preview/deployment/port and ambiguous/mismatched forwarded headers fail with the same fixed 404. No forwarded header selects a tenant; no CRC fallback exists. Loopback HTTP is local/test only, and production/preview loopback is denied. Directory lookup reads no family/content table.
- `createAccessService({ db, auth, deployment })` exposes `readStudent` and bounded/keyset `listStudents`, plus **internal server composition** callbacks `withStudentCapability(..., { mode, studentId, capability }, callback)` and `withAdminCapability(..., { mode, capability }, callback)`. A trusted operation chooses its literal capability/callback; never pass a transport-supplied capability or arbitrary client callback. Student capabilities are `read` and `set-reading`; only assigned tutor/admin modes permit the latter. Admin capabilities cover student management, invitations, relationships and defaults; invitation/relationship authority requires a sign-in within fifteen minutes. Actual action services still need input/CSRF checks, target-specific writes and same-transaction audits.
- The mode is an untrusted selector, not a role claim: one matching live grant is required. Parent+tutor permissions never union. Own students require their individual live identity link; parents can read only linked children; tutors see assigned learners; admins see active learners in their congregation. Child-practice is rejected until its separate handle implementation exists. Student DTOs omit contacts, credentials and internal authority fields.
- The real Better Auth API verifies the signed cookie with caching/refresh disabled. In the same restricted tenant transaction, the service locks/rechecks tenant enabled status, live verified user, exact session/user/token binding and expiry, membership status, selected role grant, target student status and the current link. Foreign, absent, malformed, unrelated and disabled targets receive indistinguishable 404s. No actor header bypass is provided. The stale-proof regression uses the real public auth API, mutates the actual database after its valid proof, then returns that unchanged proof; the later locked checks still deny access.
- Lock order is tenant → auth user → auth session → membership → selected grant → student → relationship. Read/ordinary reading-write capabilities hold SHARE authority locks; authority-write callbacks take UPDATE from the outset, avoiding shared-lock upgrades. Admin callback capabilities currently use authority-write locking. Lists lock candidate student rows in ID order before rechecking/locking their links. Future revocation/context/invite services must compose under this ordering and cannot introduce multi-tenant work or authority upgrades inside ordinary callbacks. Callback writes/audit use the supplied transaction; rollback tests confirm both inserts completed before forced failure and neither persists.
- PostgreSQL requires an UPDATE privilege for SHARE row locking. Astra explicitly approved migration 0003 granting **only `UPDATE(customs)` on tenant** for that lock and future authorized congregation defaults. Runtime cannot change `enabled`, `id` or `tenant_host`; customs updates remain tenant-RLS scoped and require application admin authority. Negative tests exercise each boundary.
- Runtime validation additionally rejects unexpected transitive memberships outside `{session_user, portal_runtime}` and requires the active role to be the session user or `portal_runtime`. This catches misconfigured built-in groups such as `pg_write_all_data`, including after an explicit `SET ROLE` into that group. It complements the existing current/session role flags and owner-membership checks; it does not provision credentials.
- `server-only` marks each new server module. Tests mock only that inert marker inside `access.test.ts`; no production environment flag or identity bypass is introduced.

## Third backend slice — explicit invitations and private bootstrap (2026-10-15)

Built on published `643eb0c`/`346ab44` prerequisites. Files: `src/server/invitations/{tokens,service}.ts`, `src/server/data/invitations.ts`, `src/server/http/mutations.ts`, shared `src/server/access/{identity,service,types}.ts` and narrow `data/authority.ts` extraction; `scripts/bootstrap-owner.{mjs,d.mts}`; `tests/app/invites{.test,-fixture}.ts`, `tests/app/bootstrap.test.ts`. New `src/server/db/invitation-schema.ts`, index export and journaled **0004_fat_swarm** add only invitation delivery counters with FORCE RLS. Published migrations remain unchanged. Foundation independently owns assignment-uniqueness 0005 and its journal/snapshot changes; primary must separate staging coherently.

`createInvitationService({ db, access, transport, throttleSecret })` implements issue/revoke/reissue/accept. Issuing administrative calls require the fresh admin `manage-invites` capability. Acceptance requires actual Better Auth authentication, a live verified matching mailbox, exact tenant and a secret token; an absent membership is allowed only here, while an existing disabled membership fails closed. Shared `withVerifiedIdentity` locks/rechecks tenant/user/session/membership in the restricted transaction; existing capability behavior is retained. Each invitation mutation requires POST plus exact same-origin against the independently resolved host origin; absent/null/foreign Origin and cross-site Fetch Metadata fail closed. GET never consumes a token. MCP token authentication remains a separate future contract.

Tokens contain 32 random bytes, are SHA-256 hashed in the database, expire after 72 hours and are conditionally consumed once. Replay, wrong mailbox/tenant, expired/revoked/rotated links fail. Reissue revokes an active old invitation and creates its successor atomically; reusing the already-revoked predecessor ID cannot create parallel successors. Parent siblings share one verified identity/parent grant with separate exact guardian links. Explicit parent+tutor invitations add separate mode grants without union permissions. Student invitations reject parent-contact mailboxes and existing parent identities; active identity uniqueness remains enforced. An invitation predating a role/guardian/student-identity revocation cannot silently restore that authority; a fresh explicit invitation can establish a new link after revocation.

Delivery is an injected private transport **after transaction commit**. New migration **0006_public_talisman** adds durable `pending`/`sent`/`failed` status, private outcome timestamp and explicit `invite.delivery-sent`/`invite.delivery-failed` audits. After transport, a separate restricted tenant transaction locks tenant then exact invitation, checks immutable issued-row fields and historical actor/grant binding, and conditionally records only delivery fields plus audit. This provenance check deliberately allows logout/revocation during transport and never restores authority. A terminal outcome cannot be overwritten (pending-only update plus database trigger). An audit/write failure rolls back the receipt and returns `unknown`; an interruption after issuance leaves `pending`, rather than fabricated failure. Results contain only invitation ID and confirmed `sent`/`failed` or `unknown`; tokens/recipient/URL/provider errors are never returned or logged. Recovery always uses explicit reissue/token rotation, not plaintext retry. No outbox or external delivery infrastructure was introduced. Private transport input uses the resolved origin and a fixed future landing path; landing UI, clean-token exchange and actual provider sending are not implemented here.

The separate tenant-scoped counter table is necessary because Better Auth's global auth counter cleanup would erase longer invitation budgets. Defaults are **20 issued/reissued messages per actor/hour and 5 per recipient/hour**. HMAC keys include tenant/action/scope namespace; no raw mailbox is in a key. Counter changes and the invitation/audit commit together; committed delivery attempts (including transport failure) retain their budget, and rejected over-budget issuance never commits or sends. RLS and column-level counter grants are included in 0004. The constructor requires a private `throttleSecret`; no secret is provided or stored in source.

Private operator bootstrap checks a direct owner connection, uses fixed `SET LOCAL ROLE portal_runtime` and transaction-local CRC context under a serialized tenant lock, then grants CRC admin only to one explicitly configured, already-verified identity. The append-only `owner-bootstrap` audit durably binds the initial identity; revoking its admin cannot enable a different configured identity to bootstrap later. Repeated active-owner execution is idempotent only with a matching durable bootstrap binding; preexisting unbound admin history (active or revoked), disabled/revoked authority and a different initial owner fail closed. There is no public route or email-based auto-admin hook. All failures are fixed messages without driver causes, identities or connection configuration.

Operator invocation, once private setup exists: `node --env-file=.env.local scripts/bootstrap-owner.mjs --confirm`, with private `DATABASE_MIGRATION_URL` and `BOOTSTRAP_OWNER_EMAIL`. The owner connection must own the protected tables and be permitted to SET ROLE to the fixed privilege group; normal runtime credentials are rejected. Remove `BOOTSTRAP_OWNER_EMAIL` after success, keep elevated migration credentials outside the deployed app environment, and do not enable bootstrap as an application startup hook. This command was **not** run against real data or a provider.
