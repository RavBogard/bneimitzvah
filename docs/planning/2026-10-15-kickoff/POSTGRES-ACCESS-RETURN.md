## Evidence

- Runtime reads/writes use the real capability API, including role-mode separation, wrong-tenant target/host denial, and SQL permission denial for tenant enabled/ID and host-directory changes under migration `0003`.
- A failing callback inserts an assignment and its audit record in the same actual transaction; both roll back, and the service returns its sanitized unavailable error.
- For each of tutor-link, role-grant and auth-session revocation, an authorized callback first holds its transaction. `pg_blocking_pids` proves the second runtime connection is blocked. Releasing the writer allows it to commit; the revocation callback verifies its committed audit is visible before revoking. The next read and write deny access.
- The reverse ordering holds the authority-revocation transaction first. PostgreSQL lock observation proves the competing access transaction waits. After revocation commits, its callback never writes and both assignment/audit tables remain empty. Next actions remain denied.
- Barrier entry waits race against operation completion/failure and a bounded deadline. Every race releases its latch in an encompassing `finally`, then bounds settlement. Fixture cleanup can destroy its own checked-out clients, so an assertion/entry failure cannot leave `pool.end` waiting on a latch forever.
- Local combined run passed six existing SQL tests plus three access tests; after the failure-path review fix, the focused access suite passed 3/3 again. Typecheck and repository guard passed. The earlier Windows fixture-concurrency fix (`maxWorkers=2`, 20-second test budget) separately passed all 45 offline app tests; short fetch deadlines remain asserted independently.
