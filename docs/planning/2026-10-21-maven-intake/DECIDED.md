# Maven roster intake through the portal MCP — decided here (2026-10-21)

Daniel, 2026-10-21: Maven, CRC's Salesforce, reaches the portal through Cowork. Claude reads Maven with Daniel's existing Maven connector (`maven_run_soql`) and proposes roster changes through the portal MCP. The portal stores no Maven credential and never calls Maven. MISSION ruling 4 (amended, rulings 41–42) holds: read-only Maven, never write back; identity is the stable source record id within tenant and namespace; a name and date may suggest a reconciliation but never establish one; an imported slot is unknown until the rabbi sets it.

## The flow

1. `get_maven_roster_query` (admin, `portal:roster`): the exact SOQL from `mavenRosterQuery` for a ceremony-date window. Default: the congregation's local today through 730 days ahead (731 inclusive days, inside `MAVEN_ROSTER_LIMITS.windowDays`). Both dates or neither.
2. Claude runs it with the Maven connector and passes the structured result unchanged.
3. `propose_roster_changes` (admin, `portal:roster`; writes nothing): decodes with `decodeMavenRosterContacts`, reads the tenant's students and Maven identities inside the live-authority transaction, runs `planExternalRoster`, and returns one reviewable row per changed or new Maven row (unchanged rows by number only) plus a signed plan token.
4. Claude shows the rabbi the table; nothing is applied until the rabbi says which rows.
5. `apply_roster_changes` (admin, `portal:roster`, which a scheduled routine can never hold): the same window and Maven result, the token, and explicit per-row choices. Rechecked live and applied in one transaction. Sends no invitations and no e-mail.

## Decisions

- **A separate roster consent (Daniel, 2026-10-21).** All three tools need `portal:roster`; a connection without it sees none of them in tools/list and cannot call them. The scope is granted only to an admin membership, only when the client asks for it, and never to a connection marked as a scheduled routine: left out of the grant at consent, refused by the `mcp_connection_scope` check (widened in 0031), and dropped from the live authority behind every token issue, refresh and call even if a row somehow held it. Existing connections keep exactly their scopes; there is no automatic upgrade, so the rabbi reconnects Claude to add the roster. Asking for `portal:read portal:roster` grants no study scope. The 401 challenge and both metadata documents list all three scopes. Because the 401 challenge lists all three scopes, an attended admin connecting Claude after this deploy will in practice be offered the roster line; there is no way to decline roster but keep study except ticking the routine box. The consent page line, shown only when the scope is requested and granted and the routine box is unticked: "Add students from Maven and update their names and ceremony dates. It never sends invitations."
- GATE: roster writes use a separate portal:roster consent — Daniel 2026-10-21.
- **Residual risk.** The Maven result is supplied by the Claude session; the server checks its shape and that it answers the exact SOQL, but cannot prove it came from Maven. A misled session could propose invented rows, including a child whose parent address is not the family's. Mitigations: the admin reviews every proposed row and chooses what to apply; roster writes need their own consent, never held by a routine; nothing ever sends an invitation automatically; and the admin sees the full parent address on the portal's invite form before sending one.
- **What Maven may change.** For a linked student: first name, last name, ceremony date, and the Hebrew name when Maven has one (Maven's null or blank never clears the portal's). Kind, slot, contacts, second parent and rehearsals are never changed by Maven; they stay the portal's. A ceremony-date change goes through the portal's own update path, so readings and the service plan go to review exactly as a portal edit does, and a date that would fall before a saved rehearsal is blocked (`rehearsal-after-new-ceremony-date`).
- **A new student's contacts.** The rabbi chooses child or adult per row. A child's parent address is the household's primary contact (`Account.npe01__One2OneContact__r.Email`) only when that contact is someone other than the student; a child's own address is left empty. An adult's own address is their Contact `Email`. The proposal reports which kinds are creatable (`canCreateAs`) and contact presence as booleans only. Setting an address creates no guardian: a guardian link still needs an invitation the rabbi sends and the family accepts in the portal. Daniel may want to look at this rule (see Open items).
- **Rows that cannot be planned** are reported, not allowed to fail the whole plan: `not-importable` (`missing-name`, `invalid-field`, `no-email-on-file`) and `linked-student-disabled`. A Maven row with no usable address for either kind can still be linked to a student already in the portal whose name and date match (a `reconcile` row with `canCreateAs: []`).
- **Not having a ceremony.** A Maven Contact marked `Not_Having_Beit_Mitzvah__c` is shown with the note `maven-records-no-ceremony`; it can still be created or updated if the rabbi chooses it.
- **Names with an at sign.** The transport withholds any result containing an address. A name containing `@` is shown as withheld for that row alone, so one odd record cannot hide the whole proposal.
- **Absence is not removal.** A portal student missing from the Maven result is left alone; the intake never disables anyone.
- **Reconcile.** Suggestions are the planner's name-and-date matches. Linking to a disabled student, or to a student already linked to another Maven Contact, is blocked. "New" on a reconcile row creates a separate student.
- **Plan token.** HMAC-signed with the MCP secret under its own kind (`rp`, beside `mc` and `mr` in `oauth.ts`), 30 minutes, bound to tenant, connection id, window, a SHA-256 digest of the decoded facts, and an 8-hex-character digest per row of its expected state (kind, student, revision, changed fields, suggestions with their revisions, creatable kinds). The token carries no names or addresses. Apply needs the Maven result again because the portal keeps none of it.
- **Conflicts and atomicity.** Apply rebuilds the plan from the live roster and compares each chosen row's digest. Any changed row (`conflict`), any choice that does not fit its row (`invalid-choice`), or any revision that moved while the students are locked `FOR UPDATE` (in id order) refuses the whole apply before the first write; every row reports its outcome. All writes are one transaction under `withLive("data-write")`, the rabbi's admin grant re-locked with `lockRabbi` (the save_guide precedent), and a per-tenant advisory lock so two applies serialize.
- **Idempotent re-apply.** Source identities are insert-only and record how they were made (`link_kind`: `created` or `linked`). A chosen row that is now unchanged and linked as chosen is reported `already-applied` and not written again; a `create` counts as done only when the intake created that student for the record, so a row linked instead is a conflict, never a false success.
- **Same write paths as the portal.** `writeNewStudent` (row, ceremony schedule, audit) and `writeStudentEdit` (row lock, revision, contact and rehearsal checks, review marks, audit) were extracted from the student service and are now used by the portal's create, edit and CSV import and by the intake. Created students are audited `student.import`, updates `student.update`. A link with nothing to change writes no student revision; the identity row (who, which grant, which MCP connection, when) is its record. Ceremony scheduling is left to the existing daily drain rather than dispatched after commit.
- **Identity table.** `student_source_identity` (migration `0031_student_source_identity`, after the settings PR's `0030_congregation_settings`): unique on (tenant, namespace, record) and (tenant, namespace, student); namespace closed to `maven` with an 18-character Contact id; creator bound to the membership, the admin grant (typed by role) and the MCP connection; RLS forced with `tenant_isolation`; the runtime role has SELECT and INSERT only.
- **Size.** The MCP request body limit stays 512 KiB. A realistic CRC window is far below it; a 500-contact result may exceed it, in which case narrow the window.

## Open items that wait on Daniel

- **Undoing a wrong link.** Identities are insert-only and there is no unlink tool or screen. A wrong link (or a link to a student later disabled) can only be removed by the database owner; every later proposal would offer that Contact's changes to the wrong student. An unlink path (a revoked-at column and an admin action) is a follow-up.

- The child's parent address comes from the Maven household's primary contact. If CRC's households often list someone else first, Daniel may prefer to type parent addresses in the portal for children; the tool then still creates adults and links existing students.
- Inviting the families of newly created students is his separate step in the portal; nothing here invites.
