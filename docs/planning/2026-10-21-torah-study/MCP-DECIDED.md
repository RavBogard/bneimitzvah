# Portal MCP — decided here (2026-10-21)

Daniel, 2026-10-21: "There's already google oauth. This should be easy." The MCP therefore reuses the portal's existing Google sign-in and the OAuth pattern of the haftarah connector he already uses from Claude, instead of the Better Auth `mcp()` plugin composition the 2026-10-18 read-foundation design chose. That design's binding rulings (Google-authenticated, staff only, live roles and relationships authoritative, no tokens in logs or results, closed projections, JSON only) all hold; its library choice and its five activation gates are replaced by the contracts below.

## What Daniel does once

In Claude (claude.ai or the desktop app): Settings → Connectors → Add custom connector → URL `https://beitmitzvah.centralreform.org/api/mcp`. Claude registers itself, opens the portal's "Connect Claude" page, he confirms with Google and chooses Allow. A scheduled routine gets its own connection with "scheduled routine" ticked, so it can never mark a guide reviewed.

## Contracts

- **Clients.** Dynamic registration of public clients only (`token_endpoint_auth_method: none`), redirects held to `https://claude.ai/api/mcp/auth_callback`, `https://claude.com/api/mcp/auth_callback` or an http loopback. The client id is an HMAC-signed record; nothing is stored at registration.
- **Consent.** `/api/oauth/authorize` validates the request and hands a signed, 10-minute pending request to `/connect` in the URL fragment (never in a log, a Referer or a request line). The page shows the client, the return host and what the connection may do. Allow is a same-origin, cookie-authenticated POST that requires a session Better Auth created from a Google sign-in: a verified Google ID token or, since 2026-10-21, the redirect-mode authorization-code callback (`session.google_authenticated_at`, set only by the session-create hook, immutable). A magic-link session, a linked Google account or an older session is not enough.
- **Who.** Staff only: an admin grant (all students; the study tools) or a tutor grant (own students; read tools). Parents and students cannot consent. Only an admin grant carries `portal:study` (S21).
- **Tokens.** Authorization code (5 minutes, single use, PKCE S256), access token (1 hour), rotating refresh token, all random and stored only as SHA-256 hashes in `mcp_token`. A connection (`mcp_connection`) lasts at most 30 days from consent; no token outlives it. Replaying a used code or refresh token revokes the whole connection. RFC 7009 revocation of any token ends the connection.
- **Live authority.** Every MCP request and every tool call re-locks, inside its tenant transaction: tenant enabled, connection not revoked or expired, user verified, membership enabled with the same authority revision, and the same role grant (id and revision) unrevoked. A revoked grant or a reissued one ends the connection at once. Study writes additionally re-lock the rabbi's admin grant bound to the consented revision (`lockRabbi`). `mayReview` is false for an unattended routine or a read-only connection (S25).
- **Transport.** Stateless JSON-RPC over POST, one request per POST, JSON responses only: no SSE, no batch, no server-initiated messages. Protocol versions 2025-11-25, 2025-06-18, 2025-03-26. A missing or bad bearer gets 401 with `WWW-Authenticate: Bearer resource_metadata=…`. Tools appear only for the connection's role and scopes. Results are capped at 200,000 characters and withheld if they would contain an e-mail address, a bearer-shaped secret or a connection string.
- **Off by default.** The routes do not exist unless `PORTAL_MCP_ENABLED=true`. Enabling follows the second-agent adversarial review (plan Task 9) and deletes the operator bridge in the same change (HANDOFF §5a).
- **Tools.** `list_students`, `get_student` (admin and tutor); `get_study_voice`, `save_study_voice`, `list_guide_work`, `get_reading_for_guide`, `get_guide`, `save_guide`, `publish_guide`, `get_student_guide`, `save_student_guide` (rabbi only; writes need `portal:study`). Roster tools for the Maven-through-Cowork intake (Daniel, 2026-10-21): `get_maven_roster_query`, `propose_roster_changes` and `apply_roster_changes`, all needing the separate admin-only `portal:roster` consent that a scheduled routine never holds, decided in [Maven intake](../2026-10-21-maven-intake/DECIDED.md).

## Connecting from a phone (decided here, 2026-10-21)

Daniel could not connect from the Claude Android app. Its Custom Tab would not open the Google popup; "Try Google again" reloaded the page; and the reload lost the request the page had already taken out of the address bar, so it said the request had expired. The popup-only Google sign-in then failed on his phone even in regular Chrome, so the fix may not depend on the popup.

- **Redirect-mode Google, beside the popup.** Every Google sign-in (the sign-in page and the consent page) shows "Continue with Google in this window" under the Google button, prominently once the popup attempt fails. It POSTs the same-origin, cookie-mutation-checked `/api/auth/google/redirect` with `{next?: "connect" | "account"}`, which spends the popup challenge's origin and browser budget, then asks Better Auth's standard authorization-code flow (`sign-in/social` with no ID token, `disableRedirect`) for Google's URL. The return path comes only from a fixed list (`/`, `/account`, `/invitations/accept` when an invitation is pending, `/connect`), with `errorCallbackURL` `/sign-in`; the browser is handed the URL only if it is `https://accounts.google.com/o/oauth2/v2/auth`. Better Auth keeps the sign-in state as a signed cookie (5 minutes) plus a stored, single-use verification (10 minutes) that also holds the PKCE S256 verifier; only its reviewed cookies pass the cookie filter. A small `portal_google_return` cookie (callback path only, 10 minutes) remembers whether the person started from Connect Claude, the account page or sign-in.
- **The callback.** `GET /api/auth/callback/google` is routed again under Daniel's log exception (MISSION amendment 2026-10-21: Google's code and state may appear in Vercel request logs for this route only, while he is the sole Vercel team member). It is registered on Daniel's Google OAuth client. Only `code`, `state`, `error`, `error_description` and `iss` reach the SDK. Before the SDK, the portal checks that this browser holds the SDK's own signed state cookie for exactly this state (same HMAC). If not, it deletes that stored state and stops. The pinned SDK checks the cookie only after reading the state and leaves it in place on failure. Without this step, a code read from a log could be replayed later with the starter's cookie; now the PKCE verifier is gone. The state is read first, so every other refusal on this route consumes it as well. A duplicated cookie name counts as unbound, and the dispatcher relaxes its 2048-character URL limit (Google echoes scopes) and its duplicate-cookie refusal for this one route, so neither can stop the consumption. Accepted: an unsigned return still costs one indexed delete with no throttle; a flood can no longer lock anyone out. Signed returns go to the SDK with a rate-limit bucket derived from their own state, so a flood can exhaust only its own state's budget. Unsigned returns never reach the SDK. The response is a 303 to one of the fixed paths with the SDK's reviewed cookies. Any failure, including an unavailable runtime, is a 303 with no session cookie back to where the person started: `/connect?google=failed` (the page says "Google sign-in didn't finish. Try again." and recovers the request from this tab), `/sign-in?intent=account&error=authentication` or `/sign-in?error=authentication`. The SDK's own Location is never relayed.
- **The Google marker.** The session-create hook sets `google_authenticated_at` for the SDK's `GET /callback/:id` with id `google` as well as the ID-token POST. In the pinned SDK (1.7.10) that INSERT happens only after the state check, the PKCE code exchange with the client secret at Google's token endpoint, and resolving the Google user. Magic links, linking and every other path still never set it. Google may return a different account than the one signed in; the callback then makes a new session for that account, and the consent page shows and binds Allow to whichever account it shows (the viewer check is unchanged).
- **Retry in place.** "Try Google again" starts a fresh popup attempt (new challenge and nonce) without reloading. The old attempt's scope is retired first, so its callback can never post a credential.
- **The pending request survives a reload and the Google round trip.** The consent page still strips `#request=` from the address bar at once. It keeps the signed request in this tab's `sessionStorage` (one fixed key, with the time it was stored), which survives a reload and the redirect to Google and back. Only once Google sign-in has failed on the page does it also copy the request to `localStorage`, so Android's ⋮ "Open in Chrome" (another tab of the same browser) finds it. A copy is used only when a load has no fragment, and only while it is under ten minutes old (the server's `TTL.request`). It is removed when found stale, and on Allow, Cancel, an "expired" answer, a new fragment and sign-out. On iOS the in-app browser's storage may not carry over to Safari, which is acceptable.
- **Why storing it is acceptable.** The copy is a signed, ten-minute pending OAuth request, no more than the fragment already carried. Approving it still needs a staff session that Google created in that browser within the last 15 minutes, the viewer binding the page showed, and Allow. The code goes only to the client's registered Claude redirect, and only the holder of the PKCE verifier (the Claude that started) can exchange it. The server verifies signature and expiry every time, so the stored copy is a convenience, never an authority. Approval of one pending request is not single-use on the server (already true before this change); a second Allow mints an orphan connection whose code only the original Claude could exchange.
- **No email promise on the consent page.** Connecting needs a Google session, so the consent page says "Google sign-in didn't open here." It then offers "Continue with Google in this window" and two lines of phone help: open this page in Chrome (or Safari) from the ⋮ menu, or in Chrome sign out of the portal, sign in again with Google, and choose Connect again in Claude within 15 minutes. Custom Tabs share Chrome's cookies, and only a session Google created in the last 15 minutes counts. The sign-in page keeps its email wording.
