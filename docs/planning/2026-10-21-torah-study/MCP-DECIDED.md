# Portal MCP — decided here (2026-10-21)

Daniel, 2026-10-21: "There's already google oauth. This should be easy." The MCP therefore reuses the portal's existing Google sign-in and the OAuth pattern of the haftarah connector he already uses from Claude, instead of the Better Auth `mcp()` plugin composition the 2026-10-18 read-foundation design chose. That design's binding rulings (Google-authenticated, staff only, live roles and relationships authoritative, no tokens in logs or results, closed projections, JSON only) all hold; its library choice and its five activation gates are replaced by the contracts below.

## What Daniel does once

In Claude (claude.ai or the desktop app): Settings → Connectors → Add custom connector → URL `https://beitmitzvah.centralreform.org/api/mcp`. Claude registers itself, opens the portal's "Connect Claude" page, he confirms with Google and chooses Allow. A scheduled routine gets its own connection with "scheduled routine" ticked, so it can never mark a guide reviewed.

## Contracts

- **Clients.** Dynamic registration of public clients only (`token_endpoint_auth_method: none`), redirects held to `https://claude.ai/api/mcp/auth_callback`, `https://claude.com/api/mcp/auth_callback` or an http loopback. The client id is an HMAC-signed record; nothing is stored at registration.
- **Consent.** `/api/oauth/authorize` validates the request and hands a signed, 10-minute pending request to `/connect` in the URL fragment (never in a log, a Referer or a request line). The page shows the client, the return host and what the connection may do. Allow is a same-origin, cookie-authenticated POST that requires a session Better Auth created from a verified Google ID token (`session.google_authenticated_at`, set only by the session-create hook, immutable). A magic-link session, a linked Google account or an older session is not enough.
- **Who.** Staff only: an admin grant (all students; the study tools) or a tutor grant (own students; read tools). Parents and students cannot consent. Only an admin grant carries `portal:study` (S21).
- **Tokens.** Authorization code (5 minutes, single use, PKCE S256), access token (1 hour), rotating refresh token, all random and stored only as SHA-256 hashes in `mcp_token`. A connection (`mcp_connection`) lasts at most 30 days from consent; no token outlives it. Replaying a used code or refresh token revokes the whole connection. RFC 7009 revocation of any token ends the connection.
- **Live authority.** Every MCP request and every tool call re-locks, inside its tenant transaction: tenant enabled, connection not revoked or expired, user verified, membership enabled with the same authority revision, and the same role grant (id and revision) unrevoked. A revoked grant or a reissued one ends the connection at once. Study writes additionally re-lock the rabbi's admin grant bound to the consented revision (`lockRabbi`). `mayReview` is false for an unattended routine or a read-only connection (S25).
- **Transport.** Stateless JSON-RPC over POST, one request per POST, JSON responses only: no SSE, no batch, no server-initiated messages. Protocol versions 2025-11-25, 2025-06-18, 2025-03-26. A missing or bad bearer gets 401 with `WWW-Authenticate: Bearer resource_metadata=…`. Tools appear only for the connection's role and scopes. Results are capped at 200,000 characters and withheld if they would contain an e-mail address, a bearer-shaped secret or a connection string.
- **Off by default.** The routes do not exist unless `PORTAL_MCP_ENABLED=true`. Enabling follows the second-agent adversarial review (plan Task 9) and deletes the operator bridge in the same change (HANDOFF §5a).
- **Tools.** `list_students`, `get_student` (admin and tutor); `get_study_voice`, `save_study_voice`, `list_guide_work`, `get_reading_for_guide`, `get_guide`, `save_guide`, `publish_guide`, `get_student_guide`, `save_student_guide` (rabbi only; writes need `portal:study`). Roster tools for the Maven-through-Cowork intake (Daniel, 2026-10-21): `get_maven_roster_query`, `propose_roster_changes` and `apply_roster_changes`, all needing the separate admin-only `portal:roster` consent that a scheduled routine never holds, decided in [Maven intake](../2026-10-21-maven-intake/DECIDED.md). Student setup under the same consent (Daniel, 2026-10-21: "Add setup + sources"): `list_tutors`, `get_student_setup`, `find_sources`, `preview_student_reading` (reads); `assign_sources`, `remove_source_assignment`, `set_student_reading`, `set_student_tutor`, `set_student_service` (writes), decided below.

## Decided here: student setup and sources (2026-10-21)

Daniel, 2026-10-21: "Add setup + sources". Claude gets admin-only tools to assign verse sources and to set a student's reading, tutors, service slot and rehearsals. Tutors stay read-only in Claude.

- GATE: setup and source tools share the portal:roster consent, whose line now names them — proceeded because Daniel ruled 'Add setup + sources' and has not yet granted roster, so one approval covers both.
- **No new scope, no migration.** The nine tools need role admin and `portal:roster`; without it they are absent from tools/list and a call is "Unknown tool". A scheduled routine never holds the scope (unchanged enforcement), and every write also refuses an unattended connection itself. The consent line, shown when roster is granted and the routine box is unticked, is now: "Add students from Maven and set up their readings, tutors, service and sources. It never sends invitations."
- **The portal's own write paths.** Each write runs the code the portal's routes run, with the MCP connection standing in for the cookie session: readings through `createReadingWork` (the reading editor's prepare and confirm, split out of the student service unchanged; the same signed preparation, revision checks and `reading.set` audit); verse sources through `replaceWith` in the source-assignment service (verse context, versions, mutation replay, catalog re-check, `source-assignment.set` audit); tutors through `writeTutorAssignment` / `writeTutorRevocation` (extracted from the relationship service; `tutor.assign` / `tutor.revoke`); slot and rehearsals through `writeStudentEdit` (`student.update`; a changed slot sends readings and the service plan to review). The authority is the admin path of `withStudentCapability` under `withLive`, with the admin grant re-locked by `lockRabbi` for every write, as `apply_roster_changes` does. The only new SQL is one read (`latestForAssignment`, the newest sources of each verse for the setup view).
- **One portal actor per connection.** `portalActor` now carries `mcp:<connection id>` as its session id, so a reading preparation signed under one connection is refused on any other.
- **Concurrency.** Readings take `expectedReadingRevision` (checked in the same transaction the preparation reads, then bound into the signed preparation); sources take the verse's `expectedVersion` and the reading's assignment id and revision; tutors take the whole expected list (`expectedTutorIds`) and the whole new list, applied in one transaction under the portal's lock order (tutor grants, then the student) and rechecked under those locks; slot and rehearsals take the student's `expectedRevision`. A mismatch is a `conflict` result and nothing is written.
- **Readings in one call.** `set_student_reading` prepares and confirms in one call (the portal's two steps, with the signed preparation passed between them on the server); `preview_student_reading` runs the preparation alone so Claude can show the rabbi first. The five-minute preparation window therefore never runs out between Claude's turns.
- **Tutor changes keep the portal's fresh sign-in rule (review finding M1, resolved).** The portal allows tutor changes only on a session under 15 minutes old (`manage-relationships`). Approving an MCP connection itself needs a Google sign-in within `GOOGLE_CONSENT_WINDOW_MS` (15 minutes), so `set_student_tutor` adds a tutor only while the live connection's stored approval time (`mcp_connection.created_at`, read from the database inside the write transaction, never from the client) is under 15 minutes old. Otherwise it refuses the whole change with "Adding a tutor needs a fresh sign-in. Reconnect Claude to the portal, then add the tutor within 15 minutes." Removing tutors stays allowed on an older connection, since it gives no one new access. The tool description and the server instructions tell Claude to say this to the rabbi. The audit rows still do not record the channel (that would need a migration).
- **Before the first roster grant.** The widened line applies to any connection already holding `portal:roster`. Daniel has not yet connected with it (STATE: "Daniel must reconnect Claude once"); confirm in production that no `mcp_connection.scope` contains `portal:roster` before this deploys.
- **Scheduling.** As for the roster intake, a slot change's ceremony schedule is left to the daily drain rather than dispatched after commit.
- **Reads.** `get_student_setup` gives contacts only as presence (like the roster's review rows); `list_tutors` gives tutor id and name only; `find_sources` searches the per-verse catalogue the portal's source panel shows (preferred works first) and returns its `catalogHash`. Nothing in these tools sends mail or creates an invitation.
