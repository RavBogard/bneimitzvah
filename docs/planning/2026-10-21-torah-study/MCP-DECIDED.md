# Portal MCP — decided here (2026-10-21)

Daniel, 2026-10-21: "There's already google oauth. This should be easy." The MCP therefore reuses the portal's existing Google sign-in and the OAuth pattern of the haftarah connector he already uses from Claude, instead of the Better Auth `mcp()` plugin composition the 2026-10-18 read-foundation design chose. That design's binding rulings (Google-authenticated, staff only, live roles and relationships authoritative, no tokens in logs or results, closed projections, JSON only) all hold; its library choice and its five activation gates are replaced by the contracts below.

## What Daniel does once

In Claude (claude.ai or the desktop app): Settings → Connectors → Add custom connector → URL `https://beitmitzvah.centralreform.org/api/mcp`. Claude registers itself, opens the portal's "Connect Claude" page, he confirms with Google and chooses Allow. A scheduled routine gets its own connection with "scheduled routine" ticked, so it can never mark a guide reviewed.

## Contracts

- **Clients.** Dynamic registration of public clients only (`token_endpoint_auth_method: none`), redirects held to `https://claude.ai/api/mcp/auth_callback`, `https://claude.com/api/mcp/auth_callback` or an http loopback. The client id is an HMAC-signed record; nothing is stored at registration.
- **Consent.** `/api/oauth/authorize` validates the request and hands a signed, 10-minute pending request to `/connect` in the URL fragment (never in a log, a Referer or a request line). The page shows the client, the return host and what the connection may do. Allow is a same-origin, cookie-authenticated POST that requires a session Better Auth created from a Google sign-in: a verified Google ID token or, since 2026-10-21, the redirect-mode authorization-code callback (`session.google_authenticated_at`, set only by the session-create hook, immutable). A magic-link session, a linked Google account or an older session is not enough.
- **Who.** Staff only: an admin grant (all students; the study tools) or a tutor grant (own students; read tools). Parents and students cannot consent. Only an admin grant carries `portal:study` (S21).
- **Tokens.** Authorization code (5 minutes, single use, PKCE S256), access token (1 hour), rotating refresh token, all random and stored only as SHA-256 hashes in `mcp_token`. A connection (`mcp_connection`) lasts at most 30 days from consent; no token outlives it. Replaying a used code or refresh token revokes the whole connection. RFC 7009 revocation of any token ends the connection.
- **Live authority.** Every MCP request and every tool call re-locks, inside its tenant transaction: tenant enabled, connection not revoked or expired, user verified, membership enabled with the same authority revision, and the same role grant (id and revision) unrevoked. A revoked grant or a reissued one ends the connection at once. Study writes additionally re-lock the rabbi's admin grant bound to the consented revision (`lockRabbi`). `mayReview` is false for an unattended routine or a read-only connection (S25).
- **Transport.** Stateless JSON-RPC over POST, one request per POST, JSON responses only: no SSE, no batch, no server-initiated messages. Protocol versions 2025-11-25, 2025-06-18, 2025-03-26; since 1.0.1 an `MCP-Protocol-Version` header naming any other version is a 400, and an `Origin` header other than the portal's own or Claude's is a 403 (see "1.0.1 hardening" below). A missing or bad bearer gets 401 with `WWW-Authenticate: Bearer resource_metadata=…`. Tools appear only for the connection's role and scopes. Results are capped at 200,000 characters and withheld if they would contain an e-mail address, a bearer-shaped secret or a connection string.
- **Off by default.** The routes do not exist unless `PORTAL_MCP_ENABLED=true`. Enabling follows the second-agent adversarial review (plan Task 9) and deletes the operator bridge in the same change (HANDOFF §5a).
- **Tools.** `list_students`, `get_student` (admin and tutor); `get_study_voice`, `save_study_voice`, `list_guide_work`, `get_reading_for_guide`, `get_guide`, `save_guide`, `publish_guide`, `get_student_guide`, `save_student_guide` (rabbi only; writes need `portal:study`). Roster tools for the Maven-through-Cowork intake (Daniel, 2026-10-21): `get_maven_roster_query`, `propose_roster_changes` and `apply_roster_changes`, all needing the separate admin-only `portal:roster` consent that a scheduled routine never holds, decided in [Maven intake](../2026-10-21-maven-intake/DECIDED.md). Student setup under the same consent (Daniel, 2026-10-21: "Add setup + sources"): `list_tutors`, `get_student_setup`, `find_sources`, `preview_student_reading` (reads); `assign_sources`, `remove_source_assignment`, `set_student_reading`, `set_student_tutor`, `set_student_service` (writes), decided below.

## Decided here: student setup and sources (2026-10-21)

Daniel, 2026-10-21: "Add setup + sources". Claude gets admin-only tools to assign verse sources and to set a student's reading, tutors, service slot and rehearsals. Tutors stay read-only in Claude.

- GATE: setup and source tools share the portal:roster consent, whose line now names them — proceeded because Daniel ruled 'Add setup + sources' and has not yet granted roster, so one approval covers both.
- **No new scope, no migration.** The nine tools need role admin and `portal:roster`; without it they are absent from tools/list and a call is "Unknown tool". A scheduled routine never holds the scope (unchanged enforcement), and every write also refuses an unattended connection itself. The consent line, shown when roster is granted and the routine box is unticked, is now: "Add students from Maven and set up their readings, tutors, service and sources. It never sends invitations."
- **The portal's own write paths.** Each write runs the code the portal's routes run, with the MCP connection standing in for the cookie session: readings through `createReadingWork` (the reading editor's prepare and confirm, split out of the student service unchanged; the same signed preparation, revision checks and `reading.set` audit); verse sources through `replaceWith` in the source-assignment service (verse context, versions, mutation replay, catalog re-check, `source-assignment.set` audit); tutors through `writeTutorAssignment` / `writeTutorRevocation` (extracted from the relationship service; `tutor.assign` / `tutor.revoke`); slot and rehearsals through `writeStudentEdit` (`student.update`; a changed slot sends readings and the service plan to review). The authority is the admin path of `withStudentCapability` under `withLive`, with the admin grant re-locked by `lockRabbi` for every write, as `apply_roster_changes` does. The only new SQL is one read (`latestForAssignment`, the newest sources of each verse for the setup view).
- **One portal actor per connection.** `portalActor` now carries `mcp:<connection id>` as its session id, so a reading preparation signed under one connection is refused on any other.
- **Concurrency.** Readings take `expectedReadingRevision` (checked in the same transaction the preparation reads, then bound into the signed preparation); sources take the verse's `expectedVersion` and the reading's assignment id and revision; tutors take the whole expected list (`expectedTutorIds`) and the whole new list, applied in one transaction under the portal's lock order (tutor grants, then the student) and rechecked under those locks; slot and rehearsals take the student's `expectedRevision`. A mismatch is a `conflict` result and nothing is written.
- **Readings in one call.** `set_student_reading` prepares and confirms in one call (the portal's two steps, with the signed preparation passed between them on the server); `preview_student_reading` runs the preparation alone so Claude can show the rabbi first. The five-minute preparation window therefore never runs out between Claude's turns.
- **Tutor changes keep the portal's fresh sign-in rule (review finding M1, resolved).** The portal allows tutor changes only on a session under 15 minutes old (`manage-relationships`). Approving an MCP connection itself needs a Google sign-in within `GOOGLE_CONSENT_WINDOW_MS` (15 minutes), so `set_student_tutor` adds a tutor only while the live connection's stored approval time (`mcp_connection.created_at`, read from the database inside the write transaction, never from the client) is under 15 minutes old. Because the window counts from the approval rather than from the Google sign-in, an addition can come up to about 30 minutes after that sign-in; counting from the sign-in itself would need its time stored on the connection (a migration). Otherwise it refuses the whole change with "Adding a tutor needs a fresh sign-in. Reconnect Claude to the portal, then add the tutor within 15 minutes." Removing tutors stays allowed on an older connection, since it gives no one new access (here the MCP is looser than the portal, which asks for a fresh sign-in for removals too). A change that both adds and removes counts as an addition and is refused whole. The tool description and the server instructions tell Claude to say this to the rabbi. The audit rows still do not record the channel (that would need a migration).
- **Before the first roster grant.** The widened line applies to any connection already holding `portal:roster`. Daniel has not yet connected with it (STATE: "Daniel must reconnect Claude once"); confirm in production that no `mcp_connection.scope` contains `portal:roster` before this deploys.
- **Scheduling.** As for the roster intake, a slot change's ceremony schedule is left to the daily drain rather than dispatched after commit.
- **Reads.** `get_student_setup` gives contacts only as presence (like the roster's review rows); `list_tutors` gives tutor id and name only; `find_sources` searches the per-verse catalogue the portal's source panel shows (preferred works first) and returns its `catalogHash`. Nothing in these tools sends mail or creates an invitation.

## Connecting from a phone (decided here, 2026-10-21)

Daniel could not connect from the Claude Android app. Its Custom Tab would not open the Google popup; "Try Google again" reloaded the page; and the reload lost the request the page had already taken out of the address bar, so it said the request had expired. The popup-only Google sign-in then failed on his phone even in regular Chrome, so the fix may not depend on the popup.

- **Redirect-mode Google, beside the popup.** Every Google sign-in (the sign-in page and the consent page) shows "Continue with Google in this window" under the Google button, prominently once the popup attempt fails. It POSTs the same-origin, cookie-mutation-checked `/api/auth/google/redirect` with `{next?: "connect" | "account"}`, which spends the popup challenge's origin and browser budget, then asks Better Auth's standard authorization-code flow (`sign-in/social` with no ID token, `disableRedirect`) for Google's URL. The return path comes only from a fixed list (`/`, `/account`, `/invitations/accept` when an invitation is pending, `/connect`), with `errorCallbackURL` `/sign-in`; the browser is handed the URL only if it is `https://accounts.google.com/o/oauth2/v2/auth`. Better Auth keeps the sign-in state as a signed cookie (5 minutes) plus a stored, single-use verification (10 minutes) that also holds the PKCE S256 verifier; only its reviewed cookies pass the cookie filter. A small `portal_google_return` cookie (callback path only, 10 minutes) remembers whether the person started from Connect Claude, the account page or sign-in.
- **The callback.** `GET /api/auth/callback/google` is routed again under Daniel's log exception (MISSION amendment 2026-10-21: Google's code and state may appear in Vercel request logs for this route only, while he is the sole Vercel team member). It is registered on Daniel's Google OAuth client. Only `code`, `state`, `error`, `error_description` and `iss` reach the SDK. Before the SDK, the portal checks that this browser holds the SDK's own signed state cookie for exactly this state (same HMAC). If not, it deletes that stored state and stops. The pinned SDK checks the cookie only after reading the state and leaves it in place on failure. Without this step, a code read from a log could be replayed later with the starter's cookie; now the PKCE verifier is gone. The state is read first, so every other refusal on this route consumes it as well. A duplicated cookie name counts as unbound, and the dispatcher relaxes its 2048-character URL limit (Google echoes scopes) and its duplicate-cookie refusal for this one route, so neither can stop the consumption. Accepted: an unsigned return still costs one indexed delete with no throttle; a flood can no longer lock anyone out. Signed returns go to the SDK with a rate-limit bucket derived from their own state, so a flood can exhaust only its own state's budget. Unsigned returns never reach the SDK. The response is a 303 to one of the fixed paths with the SDK's reviewed cookies. Any failure, including an unavailable runtime, is a 303 with no session cookie back to where the person started: `/connect?google=failed` (the page says "Google sign-in didn't finish. Try again." and recovers the request from this tab), `/sign-in?intent=account&error=authentication` or `/sign-in?error=authentication`. The SDK's own Location is never relayed.
- **The Google marker.** The session-create hook sets `google_authenticated_at` for the SDK's `GET /callback/:id` with id `google` as well as the ID-token POST. In the pinned SDK (1.7.10) that INSERT happens only after the state check, the PKCE code exchange with the client secret at Google's token endpoint, and resolving the Google user. Magic links, linking and every other path still never set it. Google may return a different account than the one signed in; the callback then makes a new session for that account, and the consent page shows and binds Allow to whichever account it shows (the viewer check is unchanged).
- **Retry in place.** "Try Google again" starts a fresh popup attempt (new challenge and nonce) without reloading. The old attempt's scope is retired first, so its callback can never post a credential.
- **The pending request survives a reload and the Google round trip.** The consent page still strips `#request=` from the address bar at once. It keeps the signed request in this tab's `sessionStorage` (one fixed key, with the time it was stored), which survives a reload and the redirect to Google and back. Only once Google sign-in has failed on the page does it also copy the request to `localStorage`, so Android's ⋮ "Open in Chrome" (another tab of the same browser) finds it. A copy is used only when a load has no fragment, and only while it is under ten minutes old (the server's `TTL.request`). It is removed when found stale, and on Allow, Cancel, an "expired" answer, a new fragment and sign-out. On iOS the in-app browser's storage may not carry over to Safari, which is acceptable.
- **Why storing it is acceptable.** The copy is a signed, ten-minute pending OAuth request, no more than the fragment already carried. Approving it still needs a staff session that Google created in that browser within the last 15 minutes, the viewer binding the page showed, and Allow. The code goes only to the client's registered Claude redirect, and only the holder of the PKCE verifier (the Claude that started) can exchange it. The server verifies signature and expiry every time, so the stored copy is a convenience, never an authority. Approval of one pending request was not single-use on the server when this was written (a second Allow minted an orphan connection whose code only the original Claude could exchange); since 1.0.1 it is (below).
- **No email promise on the consent page.** Connecting needs a Google session, so the consent page says "Google sign-in didn't open here." It then offers "Continue with Google in this window" and two lines of phone help: open this page in Chrome (or Safari) from the ⋮ menu, or in Chrome sign out of the portal, sign in again with Google, and choose Connect again in Claude within 15 minutes. Custom Tabs share Chrome's cookies, and only a session Google created in the last 15 minutes counts. The sign-in page keeps its email wording.

## Decided here: 1.0.1 hardening (2026-10-22)

Known non-blocking defects from the 1.0 audit, fixed for the 1.0.1 patch. No migration, no new scope, no change to what a connection may do.

- **One pending request, one connection.** The connection id is no longer random: it is derived from the signed pending request (HMAC under the MCP secret of the tenant and the exact request, shaped as a version-8 UUID), and Allow inserts it with `ON CONFLICT (id) DO NOTHING`. A second Allow of the same request (double tap, Back, a replay within its ten minutes, or another staff member) therefore inserts nothing and mints no code; a concurrent one waits on the first's uncommitted row and then inserts nothing. It answers `409 {"error":"used"}`. The id is unguessable without the server secret, and the pending request itself is already a secret held only by the consent page. The runtime role needs only its existing INSERT (and SELECT for RETURNING); the primary key is the unique key, so no migration. Verified on PGlite (sequential and same-connection double tap) and on two restricted PostgreSQL backends with an observed lock edge (`tests/postgres/mcp-consent.integration.ts`).
- **Cancel or a reload after Allow.** `consent/view` and `consent/deny` look the derived id up first and answer `409 {"error":"used"}` for a request already allowed: Cancel never revokes the connection Allow made and never sends Claude `access_denied` for it, and Back or a reload no longer offers Allow again. The page then shows "This request was already allowed" and "Go back to Claude. If it still asks you to connect, start again from Claude: open the connector and choose Connect. To disconnect, use Claude's connector settings." (staff-only wording, modelled on the existing "This request has expired" view), and forgets its stored copy. Not covered: Allow after Cancel. Cancel stores nothing, so a later Allow of the same request still makes one connection whose code Claude has already given up on; recording a cancel would need a row of its own (a migration). It is bounded by the ten-minute request and the same Google, staff and viewer checks as any Allow. The same bound covers two narrower cases the review noted: Cancel in one tab racing an Allow in another (Cancel's lookup cannot see an Allow not yet committed, so Claude may receive both answers for one state), and opening the same authorize URL twice, which signs two distinct pending requests (each carries its own issue time) and so allows two connections. In every case only the Claude holding the PKCE verifier can redeem a code, so the extra connection is an orphan with no tokens. A lost Allow response cannot be retried (a retry answers "used"); the page text sends the person back to Claude to start again.
- **Origin (DNS rebinding, MCP Streamable HTTP "Security Warning").** `/api/mcp` refuses with 403 any request whose `Origin` header is present and is not exactly the portal's own origin, `https://claude.ai` or `https://claude.com`, before the bearer is read (no 401 challenge). An absent Origin passes: Claude's connector, Claude Code and other server-to-server clients send none. Claude's origins are accepted because a browser could never use them anyway (`/api/mcp` sends no CORS headers and answers OPTIONS with 405, and the bearer is never a cookie), so allowing them costs nothing and keeps the live connector working if Claude's servers ever add the header. The OAuth and consent endpoints keep their own checks (consent: same-origin cookie mutation).
- **MCP-Protocol-Version.** Absent: accepted (the specification says to assume 2025-03-26, which is supported; this server behaves the same in every supported version, so there is nothing to downgrade). Present: it must be exactly one of the supported versions, else `400` with a JSON-RPC error naming them. `initialize` is exempt, as in the MCP TypeScript SDK, because its version is negotiated in the body: a client asking for a version this server does not know is offered 2025-06-18 and then sends that header. Not verified against live Claude traffic (no request headers are logged); the existing tests, Claude's SDK behaviour (header only after initialize, carrying the negotiated version) and this negotiation keep the current connection working. **Post-deploy check (required before calling 1.0.1 done):** make a fresh Connect from claude.ai (which exercises the one-use consent and its "used" handling live), then run a real tool call from claude.ai (and, if used, Claude Code) against production. If either fails, roll production back to the previous deployment: there is no migration, and the older code ignores the derived connection ids.
- **Expired token rows.** Every expired code, access token or refresh token is refused (`tests/app/mcp.test.ts`, "never accepts an expired …"): `authenticate` and the token endpoint compare `expires_at` with the clock before any use, and no token outlives its connection. Rows still accumulate, because the runtime role has no DELETE on the MCP tables and there is no existing SECURITY DEFINER or owner-run cleanup job to reuse. Proposed, not built (it would add a scheduled owner job or a migration, so it waits on Daniel): an operator task, below.
- **Operator task: prune dead MCP token rows** (the Neon owner connection, which has BYPASSRLS; never the runtime role. Owning the tables is not enough: both have FORCE ROW LEVEL SECURITY and their policies name only portal_runtime, so an owner without BYPASSRLS would silently delete nothing. Count first with the same WHERE clauses as a SELECT). Keep used codes and used refresh tokens of a live connection until it ends, because replaying one is how a leaked token is detected and the connection revoked. Connections themselves stay (roster provenance references them). Growth meanwhile is small: about two rows per hour of use per connection, and nothing after it ends. One consequence: once an access token's row is pruned, a revocation request presenting that (already expired) token no longer ends its connection; the refresh token, still kept, does.

  ```sql
  BEGIN;
  -- Every token of a connection that has ended (revoked, or expired more than a day ago).
  DELETE FROM mcp_token t USING mcp_connection c
   WHERE c.tenant_id = t.tenant_id AND c.id = t.connection_id
     AND (c.revoked_at IS NOT NULL OR c.expires_at < now() - interval '1 day');
  -- Access tokens are never replay-checked: drop them a day after they expire.
  DELETE FROM mcp_token WHERE kind = 'access' AND expires_at < now() - interval '1 day';
  COMMIT;
  ```
- **Parked student recordings routes (MISSION, 2026-10-17 revision).** The 1.0 audit found `/api/students/:id/recordings` (GET) and `…/recordings/:recordingId/submit|delete` (POST) still registered in the `/api` dispatcher. The runtime now builds no recordings service unless `PORTAL_RECORDINGS_ENABLED=true` (strictly `true` or `false`; anything else fails configuration closed, as `PORTAL_MCP_ENABLED` does), and while it is absent every recordings path is a 404 for every method and caller, without an `Allow` header, so a well-formed request cannot tell a parked route from a missing one (a malformed one, such as a duplicated cookie, still gets the dispatcher's 400 before the route answers, as the disabled MCP routes do; no data is reachable). The flag is unset in every Vercel environment and must stay so until Daniel reopens recordings. The parked code and its tests stay; the test fixtures build the service as if the flag were set. Recording registration was never reachable over HTTP, and no page calls these routes.
