# Private upload expiry, retirement and quiescence

2026-10-17. Bounded primary-source research and offline inspection of the already packed `@vercel/blob@2.8.2`; no provider/store/package/schema/code operation. Recommendation to root, not implementation approval. **Subsequent Daniel decision:** private Vercel Blob provisioning/synthetic testing is approved at the revised planning cost. This research does not authorize a switch to R2/S3 or skipping real-media acceptance gates.

**Finding:** no documented absolute completion bound for an already accepted single PUT was found for Blob, R2 or S3. Expiry, a client abort and a successful DELETE/404 must not be treated as that proof. R2 does document a stronger alternative: commit-time conditional creation. A permanent same-key empty sentinel can retire a path without waiting for old requests to finish. This is a substantive correctness/liveness advantage, separate from ordinary cost differences.

## Evidence and limits

| Service | Documented behavior | What remains unknown |
| --- | --- | --- |
| Blob | Signed URL constrains path/operation/expiry; PUT supports no-overwrite and ETag conditions. | No located public promise that no-overwrite is atomically checked at commit against an intervening overwrite, or a maximum accepted PUT lifetime/revocation cancellation guarantee. |
| R2 | Conditional PutObject checks committed state atomically; concurrent create-only writes cannot both succeed. A negative read does not settle an ambiguous earlier write. | No located absolute accepted single-PUT lifetime bound; expiration/credential revocation must not substitute for completion. |
| S3 general-purpose bucket | Conditional creation permits only the first finishing writer; existing current objects cause precondition failure. | No located absolute accepted single-PUT completion bound. Versioning/deletion semantics require care. |

**R2's decisive contract:** the [consistency page](https://developers.cloudflare.com/r2/reference/consistency/#conditional-writes), updated October 14, says conditions evaluate against committed state “at the moment the write commits.” Its negative-read section says: “Reads are never stale, but they do not wait for or cancel earlier writes.” Its [S3 extensions page](https://developers.cloudflare.com/r2/api/s3/extensions/#conditional-operations-in-putobject) separately documents atomic `If-None-Match: *`, with at most one success among concurrent creates. These statements support the barrier inference below; strong consistency alone would not.

**S3:** [conditional-write behavior](https://docs.aws.amazon.com/AmazonS3/latest/userguide/conditional-writes.html#conditional-write-behavior) documents first-finishing conditional success, later 412 failures, and races with DELETE producing conflicts. A current delete marker permits a new conditional create, so a delete marker is not a barrier. [Presigned expiry](https://docs.aws.amazon.com/AmazonS3/latest/userguide/using-presigned-url.html#PresignedUrl-Expiration) is checked when the request starts; AWS explicitly illustrates a download continuing beyond expiry. That example does not establish an upload lifetime bound. Credential revocation invalidates URL use but is not a documented cancellation acknowledgement for accepted PUTs.

**Blob:** [signed URL options](https://vercel.com/docs/vercel-blob/vercel-signed-urls#put---upload-a-blob) enforce upload shaping; [overwrite/conditional documentation](https://vercel.com/docs/vercel-blob#conditional-writes) describes no-overwrite and optimistic ETag writes. Offline SDK source signs `allowOverwrite` into URL options and passes abort signals to transport; it cannot establish the remote storage commit algorithm or durable cancellation. No per-URL cancellation/absolute in-flight limit was located in these sources. Blob's S3 backing is not evidence that its exposed API has S3's exact conditional ordering. The same sentinel strategy needs explicit equivalent semantics before relying on it for Blob.

## Minimal candidate: permanently occupied retired keys

This is a design inference from R2's commit-time contract, not a provider feature named “tombstone.” No proxy or new service is required for the barrier itself.

1. Mint only exact-key single `PutObject` grants whose signature binds `If-None-Match: *`. Never reuse a key or expose signing credentials. Clients receive no unconditional overwrite, copy, delete, multipart initiation or completion authority.
2. Once database retirement is irreversible, deny all playback/finalization immediately. The independent cleanup worker writes a zero-byte object to the **same key**, using its trusted unconditional overwrite authority. It never makes that key absent. Either an old conditional audio PUT commits first and the worker replaces it, or the sentinel commits first and the old PUT fails its condition. Both orderings end without a current audio object; request duration is irrelevant.
3. A lost worker acknowledgement is unknown, not failure. Retrying the identical empty overwrite is safe. Confirm a committed barrier through provider acknowledgement or authoritative origin HEAD of an existing zero-byte object. A 404 is insufficient. Ordinary job leases/CAS bound work per invocation; outages retain a recoverable cleanup backlog.
4. Keep the empty object and minimal opaque key tombstone permanently unless a separately proven retirement mechanism replaces them. No DELETE, lifecycle expiration, key reuse or restore operation may remove the barrier. Student/family identifiers need not be retained in its provider metadata. API-level removal is not a promise about instantaneous erasure of provider backups.

An unconditional worker overwrite is intentional only after terminal database retirement; it avoids an unnecessary HEAD/create race. A conditional alternative must retry if the audio wins first. Do not use an upload-permit placeholder and a retirement sentinel with the same ETag: that would permit an ABA error for old `If-Match` grants. The proposed student operation is create-only instead.

## Admission that recovers

Separate active upload slots, pending maximum-byte reservations, verified retained bytes, and unconfirmed retirement exposure. Successful verification converts one maximum reservation to actual bytes and frees its active slot: an existing object already blocks every duplicate conditional create. An expired/retired receipt stops occupying the active-eight category; its unresolved storage exposure remains separately accounted until the barrier is confirmed. Confirmation releases that audio-byte reservation, leaving only tiny sentinel/tombstone overhead. Thus eight ordinary completed/abandoned captures do not consume eight upload slots forever.

Set explicit backlog byte/count limits and retry budgets. A provider outage can pause admission while cleanup cannot confirm progress; the design must recover automatically when the barrier succeeds. It must not manufacture an expiry-plus-grace proof to release unknown exposure. Permanent zero-byte keys still incur metadata/database/operation/listing costs and grow with admitted captures; cap new grants per actor/student/tenant and budget that growth. This is bounded accounting per admitted key, not a lifetime constant-size database or a billing cap.

## Required constraints before adoption

- **Signed header and byte cap proof:** R2 [presigned examples](https://developers.cloudflare.com/r2/api/s3/presigned-urls/#generate-a-presigned-url) show SigV4 single PUT and signed Content-Type, while its extensions document conditional PUT. No combined official presigned `If-None-Match` example was located. [SigV4 query authentication](https://docs.aws.amazon.com/AmazonS3/latest/developerguide/sigv4-query-string-auth.html) supports signing additional headers. Require `if-none-match` in the actual signed-header set and reject removal/mutation. R2 presign has no proven equivalent here to Blob `maximumSizeInBytes`: exact signed Content-Length within the canonical cap, browser behavior and actual over/under/chunked body rejection need proof before direct upload activation. S3 [PutObject](https://docs.aws.amazon.com/AmazonS3/latest/API/API_PutObject.html#API_PutObject_RequestSyntax) defines Content-Length; that alone does not prove the R2/browser combination.
- **Versions and caches:** use authoritative private origin APIs, no public/CDN read capability. [S3 versioning](https://docs.aws.amazon.com/AmazonS3/latest/userguide/Versioning.html) retains overwritten audio as old versions; prefer a fresh never-versioned bucket, or explicitly remove all old versions while retaining the current sentinel. A suspended previously versioned bucket is not equivalent. R2's [compatibility table](https://developers.cloudflare.com/r2/api/s3/api/) does not expose S3 bucket-versioning APIs; do not import S3 versioning assumptions. Existing delivered bytes and caches cannot be remotely recalled; app authority must deny immediately independently of cleanup.
- **Keep multipart out of this first path:** these recordings fit ordinary single PUT. S3 [abort documentation](https://docs.aws.amazon.com/AmazonS3/latest/API/API_AbortMultipartUpload.html) warns in-flight parts can still succeed, requiring repeated abort/list-parts checks. Its conditional-completion support is documented, but that must not be assumed for R2 merely because R2 supports the endpoint. R2 [multipart APIs](https://developers.cloudflare.com/r2/api/workers/workers-api-reference/#r2multipartupload-definition) have explicit abort/completion and default seven-day incomplete expiry; that is not a single-PUT or instantaneous-part reclamation bound. Client AbortSignal is not a durable server abort protocol.
- **Abuse is separate:** R2 explicitly documents that a presigned URL is reusable until expiry. One committed object per key does not bound repeated in-flight transfer or operation charges. Application admission limits new grants; they do not throttle every direct replay. Test failures/late races, bound issuance and monitor/disable new issuance when exposure rises; do not label an application quota an enforced provider spend cap.

Root decision needed: prefer the documented R2/S3 conditional-barrier path, or obtain equivalent Blob semantics/change its upload protocol. Before implementation, pin the byte-cap/signature contract, irreversible retirement/accounting transitions and sentinel-preserving worker/configuration invariants. If Blob lacks the needed guarantee, periodic DELETE plus opaque database tombstones remains privacy-safe at the app layer but only best-effort physical reconciliation; it does not satisfy bounded terminal storage cleanup and should not be presented as equivalent.
