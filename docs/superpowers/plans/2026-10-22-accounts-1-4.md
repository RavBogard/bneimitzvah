## 0. Preconditions and three design choices

**What must land first.** The front door (0034 and 0035) and 1.2 must land first.
- PR 1 can save only the weekly reading until 1.3's text-by-range route lands.
- PR 3 needs 1.2's Study rows.

**Migration numbers.** Take the next free numbers. This plan says 0036 and 0037; if PR #22 is renumbered first, they shift up. `tests/migration-journal.test.mjs` enforces the order. (PR 2 landed as 0038, after #42 took 0037 for course progress.)

**A. No enum change.**
- "Member" is not a new `portal_role` value; members live in a new `tenant_member` table. Approvers live in a new `account_approver` table.
- Why: Drizzle applies all pending migrations in one transaction (`node_modules/drizzle-orm/pg-core/dialect.js:60`). Postgres refuses to use a newly added enum value inside the same transaction, so every fresh PGlite and CI database would fail.
- Widening the enum would also widen every role-typed column (invite.role, practice_context.role, notification_delivery.role, audit grant FKs).
- Keeping both concepts out of `role_grant` means `withActor` (`src/server/access/service.ts:39-55`) can never give a member or approver a workspace mode.

**B. Member features are worked out on every request, not granted.**
- A person is eligible if they have an active `tenant_member` row, or an active `role_grant` with a role in (parent, tutor, admin) for their membership. Eligibility is checked under a share lock on every request.
- There is no backfill and no copied grant.
- Revoking a person's last parent or tutor grant (`src/server/relationships/service.ts:134-146`) removes access on the next request. Their saved rows stay, unreachable, and reappear if eligibility returns.
- Students are not automatically eligible. Their workspace drafts stay tutor-visible as today, and they may request an account.

**C. "Only the owner reads" is enforced by RLS.**
- Every saved table has one forced policy, `owner_only`. It checks the tenant setting and a second transaction-local setting, `app.saved_owner` (a membership uuid).
- That setting is set in exactly one place, `src/server/saved/access.ts`, after session verification and the eligibility check.
- Staff routes, MCP, cron, the roster Sheet and notifications never set it, so they see zero rows even if a WHERE clause is forgotten.
- Honest limits:
  - A compromised runtime could call `set_config` itself.
  - The table-owning migration role (the Neon console) bypasses RLS.

## 1. Data model and migrations

Every table follows the 0032 recipe:
- Drizzle schema first, then `npm run db:generate`, then hand-appended RLS and grants.
- ENABLE plus FORCE row-level security; REVOKE ALL FROM PUBLIC and FROM portal_runtime; then narrow grants and one policy per table.
- No table-level UPDATE anywhere.
- `text` columns with CHECK constraints, never a new enum.

#### Policy on all four tables

```sql
CREATE POLICY owner_only ON <t> TO portal_runtime
  USING (tenant_id = nullif(current_setting('app.tenant_id', true), '')
     AND membership_id = nullif(current_setting('app.saved_owner', true), '')::uuid)
  WITH CHECK (tenant_id = nullif(current_setting('app.tenant_id', true), '')
     AND membership_id = nullif(current_setting('app.saved_owner', true), '')::uuid);
```

- If the owner setting is unset or empty, nothing matches. A malformed value throws, so it fails closed.
- No audit actions for saved-layer writes: audit rows are staff-queryable and would leak activity on private data.
- Learn-to-lein progress gets no table in 1.4 (no unused tables). 1.5 adds it with the same `owner_only` policy.

## 2. Server services, routes and authorization

### 2a. The saved layer (PR 1)

**`withSavedOwner(request, intent, action)`** in `src/server/saved/access.ts` runs these steps in order:
1. `withVerifiedIdentity(request, {intent, mutation: intent !== "read"})` (`src/server/access/identity.ts:15`). This refuses an `X-Practice-Context` header, an unverified user, a disabled membership or an expired session, and checks the cookie mutation.
2. Require `identity.membership`, otherwise 403.
3. `savedEligibility(...)` in `src/server/data/saved.ts` share-locks the first active grant in (parent, tutor, admin). PR 2 adds the active `tenant_member` check. If there is neither, 403.
4. `select set_config('app.saved_owner', <membershipId>, true)`.
5. Run the action with a frozen `SavedOwner`, then recheck session expiry after it, as in `src/server/student-work/service.ts:31-45`.

**Structural tests:**
- `app.saved_owner` appears only in `access.ts` and the migration.

### 2b. Accounts (PR 2)

The code lives in `src/server/accounts/{service,data,validation}.ts`.

**`withApprover(request, mode, intent, action)`:**
- **Admin mode:** the `withAdminCapability` pattern (`access/service.ts:89-96`) with new `adminRules` (`:15-26`):
  - `read-accounts`: read;
  - `manage-accounts`: authority-write, not fresh;
  - `manage-approvers`: authority-write, **fresh**.
- **Tutor mode:** the `withActor` tutor path, then a share lock on an active `account_approver` row for this membership whose `tutor_grant_id` is the actor's live tutor grant. If there is none, 403.
- Audit rows carry the real mode and grant.

**Request: `POST /api/account/request {name, purpose?}`**
- Runs under `withVerifiedIdentity({intent:"data-write", mutation:true})`. It works without a membership; a disabled membership is already 403 (`identity.ts:33`).
- An already eligible caller gets `{state:"member"}`.
- An existing request gets `{state:"pending"}`. This is idempotent, and no second email is sent.
- Throttles:
  - `account-request`: 3 a day per user, using an HMAC key as `consumeInvitationBudget` does (`src/server/data/invitations.ts:26-35`), with a new `purposeSecret(config, "account-throttle")`.
  - At most 50 pending requests per tenant, otherwise 429.
- After the insert, in the same transaction, consume the `account-mail` budget (12 request emails per tenant per hour).
  - Within budget: `notify_status='pending'`, and the recipients are collected.
  - Over budget: `'skipped'`. The request still appears in the list and the count.

**`GET /api/account/request`** returns `{state: "member"|"pending"|"requestable", suggestedName}`. `suggestedName` is the caller's own `user.name`.

**Recipients:**
- Users with an active admin grant, or an active designation backed by an active tutor grant.
- The membership must not be disabled, and the email must be verified.
- De-duplicate by user and cap at 20.
- Emails are read inside the transaction and held only in memory.

**Approve: `POST /api/accounts/requests/approve {mode, requestId}`**
1. Lock the request FOR UPDATE. If it is missing, 404; this is also what the losing side of a race sees.
2. Lock the requester's user and membership. If there is no membership, insert one (the `obtainMembership` pattern, `data/invitations.ts:74-78`). If the membership is disabled, 409 and the request is kept.
3. If there is no active `tenant_member` row, insert one with the request's `display_name`.
4. Delete the request and write the `account-request.approve` audit.
5. Never touch `role_grant`. A static test checks that `src/server/accounts/**` never inserts into or updates `s.roleGrant` and never imports `insertGrant`.

**Decline:** `POST /api/accounts/requests/decline` locks the request, deletes it and writes the `account-request.decline` audit. It sends nothing.

**Members (admin only):**
- `GET /api/accounts/members` returns `{id, name, since}` only. No email, no counts, nothing from saved tables.
- `POST /api/accounts/members/end {memberId}` sets `revoked_at` and writes the `member.revoke` audit. Access ends on the next request.

**Approvers (admin only):**
- `GET /api/accounts/approvers` returns `{admins:[name], designated:[{id,name}], candidates:[{tutorGrantId,name}]}`.
- `POST /api/accounts/approvers/add {tutorGrantId}` needs a **fresh** session. The target must have an active tutor grant, must not be an admin (admins already approve) and must not already be designated. It writes the `approver.designate` audit.
- `POST /api/accounts/approvers/remove {approverId}` does not need a fresh session. It writes the `approver.revoke` audit.

**The approval queue:**
- `GET /api/accounts/summary?mode=admin|tutor` returns `{requests:n}`.
- `GET /api/accounts/requests` returns `{id, name, purpose, email, requestedAt}`. The email is shown to approvers only.

**Session flags:** `sessionSummary` (`src/server/portal/service.ts:42-49`) gains `saved: boolean` and `approver: boolean`. The strict `parseSession` in `src/components/portal/api.ts` must be updated to accept them.

| | Signed out | No membership, or student only | Member, parent, tutor or admin | Designated approver (tutor) | Admin |
|---|---|---|---|---|---|
| Saved layer, own rows only | 401 | 403 | yes | yes | yes |
| Request an account | 401 | yes | returns `member` | — | — |
| List, approve, decline | 401 | 403 | 403 | yes (tutor mode) | yes |
| Members list, end membership | 401 | 403 | 403 | 403 | yes |
| Designate or remove approvers | 401 | 403 | 403 | 403 | yes (a fresh session to add) |

## 3. Auto-membership and revocation

- Eligibility follows choice B.
- Admins are automatically eligible.
- A parent or tutor who also has a `tenant_member` row keeps saved access after losing their grant.
- Ending a membership keeps the saved data but makes it unreachable. Deleting it is an operator action, on request.

## 4. Email: always-on transactional mail, no new switch

**Why no switch:**
- Daniel ruled these two emails on.
- Both are direct results of a person's own action.
- `PORTAL_NOTIFICATIONS_ENABLED` (`src/server/runtime/config.ts:86`) plus the congregation switch is a two-key system that is designed to stay off. A third switch would just be one more way for the promised emails to fail silently.
- The throttles are the guard against abuse.

**The transport:**
- `createAccountMailTransport(kind: "account-request"|"account-approved", to, tenant: {name, productName}, idempotencyKey)` sits beside `createMailTransport` (`src/server/mail/transport.ts:40-75`).
- The transport builds the whole text itself. Its only link is a fixed path on the configured origin (`/workspace/accounts` or `/`).
- It accepts no URL, name or purpose from callers, so requester-written text never reaches an inbox. That stops the request form relaying spam or phishing to staff.
- Resend's `idempotency-key` is a uuid derived from `sha256(requestId:recipientUserId)` for request emails, and the `tenant_member` id for the approval email.
- Send after commit, following the `deliver()` pattern (`src/server/invitations/service.ts:90-107`), and record the status in a second transaction.
- A failure logs only the existing field-less `mail.failed` event. There are no retries.

**Copy:**
- **Request email.**
  - Subject: "An account request for {productName}".
  - Body: "Someone has asked for a {productName} account. Review account requests: {origin}/workspace/accounts. You receive this because you approve accounts for {name}."
- **Approval email.**
  - Subject: "Your {productName} account is ready".
  - Body: "Your account request was approved. Sign in with this email address to save readings and keep your own translation and notes. {origin}/. If you did not ask for an account, you can ignore this email."

Decline sends nothing. No other email is turned on.

## 8. Threats for the adversarial reviewer

1. **Cross-tenant reads.** The tenant comes only from host resolution (`src/server/db/runtime.ts:47`). Check that every query filters by tenant and is under RLS, and that every composite FK includes `tenant_id`.

**Decided while building PR 1's server half (2026-10-22, `claude/accounts-saved`):**

**Decided after the PR 1 adversarial review (2026-10-22; no High findings):**

19. (Low 1) The 0036 CHECKs refuse an explicit, locale-independent class instead of `[[:cntrl:]]`, which depends on the database locale (glibc may match U+2028 and U+2029; PGlite is C locale).
