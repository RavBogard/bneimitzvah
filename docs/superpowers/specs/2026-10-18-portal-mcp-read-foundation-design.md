## Actual API findings and activation hold

The exact published-package inspection identifies seven OAuth models and continued use of the existing verification model. The earlier JWT profile additionally required `jwks`; the selected opaque profile does not. Real before-code verification-create hooks exist, but no automatic portal delegation or Google-session provenance. Returning false from the verification hook is insufficient; denial must throw.

The selected MCP plugin does not itself install the separate bearer-to-cookie plugin. Nevertheless, browser identity lookup must explicitly remove Authorization before invoking its cookie-session SDK. This prerequisite has passed real-library negative controls and independent review. If JWT is reconsidered later, its default session hook also requires an explicit header policy; it is absent from the selected opaque composition.

The first independently reviewable implementation is the browser cookie boundary. It does not enable MCP. Provider/schema/endpoint activation remains held until the following contracts and their actual-library synthetic tests are accepted:

- Persist real Google-session provenance at successful session creation; a linked Google account, verified email or recent session is insufficient. Existing unmarked sessions remain valid for the browser but cannot authorize a Google-only MCP connection.
- Establish the server-owned delegation identity before provider consent lookup, with an exact client/resource/session/tenant/staff-grant binding and lock order. Missing or stale mapping denies issuance and access. Separate adapter writes are not presumed atomic.
- Prove origin-session checks on refresh issuance and resource use. If that cannot be established through supported hooks, disable refresh issuance and its advertised grant for the first local proof; do not silently ship repeated 15-minute reconnection as the final experience.
- Resolve the preregistered public-client discovery mismatch: the installed provider omits `none` when both dynamic registration and client discovery are disabled. A closed metadata projection may describe the actual supported preregistered public-client method only after a real exchange proof. Opening registration or remote metadata fetching is not a workaround.
- Specify exact discovery/OAuth methods, parsing limits and response headers, plus the JSON-only MCP response and final authorization fence. No private result may escape through an unexamined SSE stream, batch, notification or delayed callback after its live checks.

The actual opaque validation seam is a custom `createAuthEndpoint` with `metadata.SERVER_ONLY:true`, invoked only through its real `auth.api` method. Its genuine SDK context calls exported `getOAuthProviderApi` with the exact normalized options from the single MCP provider instance. Use its supported active-token API and a closed server-owned issuer/resource/client/scope policy. An internal validator may not accept a caller-selected policy or fabricated SDK context. Public HTTP invocation must remain unavailable; it is not a public introspection endpoint. Project stored referenceId through the supported claims hook, then validate the resulting delegation against live portal records.

The built-in JWT revocation endpoint rejects individual JWT revocation. Opaque revocation deletes the actual token row and the supported active validator then denies it. Two SDK validation calls are not an atomic snapshot: the resource adapter still needs the accepted transaction, lock and final-expiry contract. Opaque refresh creation also does not run the earlier JWT issuance hook; refresh remains held until its own supported endpoint-hook and lifetime proof succeeds.

Five further independently reviewed memory cases establish a feasible opaque refresh seam: actual token-endpoint before/after hooks, supported provider token hashing, live originating-session/binding refusal before consumption, managed rotation and clamping the new stored access/refresh deadlines before returning credentials. They do not establish native locking or atomicity. A deliberately failed after hook withheld body credentials while leaving the old refresh consumed and partially updated orphan rows. Preserve that result: production design must contain these orphans, define reconnect/recovery and final response/header checks, and never describe separate writes as a global rollback or automatically replay an uncertain refresh.

These are implementation gates owned by the integration stream; no new decision or credentials are requested from Daniel for local proof. This design establishes direction, not blanket approval to enable OAuth endpoints.

## Google-session provenance prerequisite

This bounded prerequisite may be implemented without installing MCP packages or enabling any connector endpoint. Add nullable `session.google_authenticated_at`, exposed privately to the SDK as a non-input additional date field. Existing rows remain null. Keep the marker outside public DTOs. A database trigger must reject any change to the marker on UPDATE, including null-to-date backfill, while allowing ordinary session updates and deletion.

Populate it only within the original session INSERT from the real `session.create.before` hook after successful configured Google idToken authentication. The current private HTTP adapter fixes the provider to Google after consuming its challenge, and the pinned SDK reaches session creation only after provider verification succeeds. Require that exact supported `/sign-in/social` idToken control flow and configured Google provider; an arbitrary submitted provider string alone is insufficient. Absent context, magic-link, direct session creation, unsupported flows and recreation without fresh verified Google authentication remain unmarked. Force caller-supplied marker values away. Never derive or backfill the marker from an account link, email verification, session age or an old session.

Use the actual supported additional-field plumbing so the marker and session are one insert; do not substitute an after-hook second write. Browser authorization must continue to accept existing unmarked and magic-link sessions unchanged. MCP eligibility will later require this marker under the same live session lock, in addition to all staff/delegation checks; the marker by itself grants nothing.

Acceptance requires actual SDK/Drizzle/PGlite insertion and failure tests with explicitly stubbed Google verification, rejection and magic-link paths, attempted caller marker injection, immutable-field enforcement, normal session update/delete/recreation, unchanged cookie role/tenant behavior and typecheck/repository protection. Stubbed verification is not a claim of real Google cryptography. Native migration/constraint acceptance and independent auth review remain required before production apply/deployment. Preserve the existing schema24 material approvals and frozen activation evidence; this prerequisite performs no production operation.

## Client, login and consent

### Pending selection and persistence checkpoint

The real-library pre-consent proof establishes application-owned Node `AsyncLocalStorage` around each genuine `auth.handler(Request)` call. The SDK's reference callback retains the request-local opaque selection across awaits and interleaved requests; the selected reference survives actual consent/code/opaque-token persistence. It also establishes that reference resolution precedes `shouldRedirect` on the missing-selection path. Therefore prepare a pending selection **outside** the SDK authorization call; that callback cannot bootstrap a missing selection. The proof's memory map, magic-link identities and permissive client setup confer no portal authority.

The next bounded implementation is a dormant, tenant-isolated `mcp_delegation` table, before provider installation or transport. One server-generated UUID identifies one immutable staff/session selection and later serves as the provider reference. Store tenant, actual user/session, membership/grant and their positive revision snapshots; restrict role to admin/tutor. Composite FKs must bind the same user, membership, grant and role, using the existing keys. Session deletion cascades the selection so an orphan provider credential cannot recover it. There is deliberately no provider-consent FK in this checkpoint: provider tables do not yet exist, and their deletion/lock order remains a separate review. An exact stored consent ID will still be mandatory in every live authorization check.

Store only a unique SHA-256 pending-cookie hash and SHA-256 authorization-request fingerprint, fixed `portal:read` scope, exact canonical resource, bounded nonempty client ID, creation time, selection deadline, hard deadline, nullable authorized time/consent ID and nullable revocation time. Never store raw browser cookies, access/refresh tokens, OAuth query bodies, email, remote metadata or a serialized actor. The pending secret is an unpredictable server-generated capability, not the UUID. Authority bindings, hashes, fixed policy and deadlines are immutable. All instants must be finite; selection deadline is after creation and at most ten minutes later, no later than the hard deadline. Hard deadline cannot exceed the originating session's current expiry at insertion. This stored deadline never grows if the browser session later rolls forward.

Every insert starts pending and unrevoked. Authorization time and nonempty exact consent ID transition together from null once, before the live selection/hard deadline; repeating the identical pair is a no-op, never a replacement or renewed deadline. Revocation transitions once from null to a finite timestamp and cannot clear or change. A revoked row cannot become authorized. Database triggers/column grants must enforce these rules even when a caller bypasses a future service. Runtime has tenant-scoped SELECT/INSERT and only the narrow UPDATE columns required for these transitions and row locks; no DELETE, ownership, bypass-RLS or broader role grants. Use ENABLE and FORCE RLS with the existing transaction-local tenant setting. Cleanup is a later explicit owner operation, not a runtime deletion capability.

Use 1–255 octets for client/consent IDs, exactly equal to their trimmed value and without ASCII control characters. Creation cannot be in the future at insertion, and the originating session must then be unexpired. On first authorization require the database clock before both deadlines and creation<=authorization<=current clock. On first revocation require creation<=revocation<=current clock; do not permit first authorization and first revocation in one update. Triggers run with invoker privileges, never new elevated/security-definer authority. Schema-qualify security-sensitive relation lookups, including `public.session`; a fixed function search path must not let a restricted caller's temporary relation shadow the originating-session check. Include that concrete negative test. SQL checks bindings, positive snapshots and the live session deadline; the later app service must independently lock/recheck Google provenance, verified user, tenant/member/grant enabled state and exact revision equality. Duplicating those authority rules into this dormant storage layer is not this checkpoint.

This table is evidence storage, not a consent implementation. SQL acceptance must prove cross-tenant/actor/role rejection, pending insertion, deadline and transition constraints, immutable fields, normal revocation, session cascade, rollback and restricted-role permissions on real PostgreSQL as well as focused PGlite tests. It must preserve existing schema24 material rows and earlier migrations. Migration0024 and this follow-on migration remain unapplied to production; no column-dependent deployment may precede their reviewed application.

The subsequent HTTP slice must bound initial untrusted authorization proposals and use a server-fixed continuation, actual signed browser identity, Google provenance and live staff grant checks before creating the pending selection. Explicitly choose the displayed staff mode; never silently broaden to another grant. Require same-origin/CSRF protection for browser state-changing actions, exact client/callback/resource/scope/PKCE policy, and SDK verification of signed continuations. Request-local parsing supplies correlation/rejection only. Missing, overwritten, stale or another session's cookie fails closed with a restart path; no seamless shared-cookie multi-tab claim. A pre-code hook must compare the SDK-validated request fingerprint, real session/user/reference and exact consent, then bind the row. A failed later SDK code insert may leave an expiring authorized orphan; that row alone is never a credential. Exact code retry, refresh failure recovery, live provider row locking and the final JSON response fence remain separate acceptance gates.

Start with one server-preregistered public hosted-Cowork client. Its only callback is exactly `https://claude.ai/api/mcp/auth_callback`; require authorization code and S256 PKCE, with token authentication method `none`. The connection instructions may supply a public client ID, never a shared client secret. Disable unreviewed dynamic registration and client-metadata fetching, and advertise only capabilities actually exposed. Claude Code loopback callbacks and guessed published-identity metadata URLs are outside this slice.

Google login proves identity, not delegation. Consent must show the server-owned client identity, CRC resource and read scope to a currently eligible staff member. Parent/student-only accounts cannot consent to staff access. Continuation state must be bounded, expiring and server-validated; no arbitrary redirect or client-supplied tenant/role. The consent view is a separate frontend contract to coordinate with the UX stream, not a new navigation project.

Initial scope is `portal:read`. Use a15-minute access lifetime and rotated refresh credentials bounded by the originating real auth session's expiry. A refresh cannot extend that session or revive revoked consent. Exact provider configuration and replay behavior must be proven before enabling refresh. Do not invent unsupported plugin options or an independent token protocol.

## Authentication to live portal authority

Create a separate server-only verified MCP evidence boundary. It must validate the presented token's issuer, audience/resource, expiry and read scope, and recheck current provider token/client/consent state. Missing or invalid bearer must not fall back to a browser cookie. No token in query strings, logs, error details or tool results.

Bind the delegation to an actual Better Auth user and originating session, canonical tenant, membership and consenting staff grant/revisions through server-owned persisted evidence. Session expiry/sign-out, delegation/client/consent revocation, disabled identity/tenant/membership/grant and applicable relationship removal must prevent subsequent access despite an otherwise unexpired token. A changed authority revision requires renewed evidence rather than silently increasing the connection's authority. The precise provider hook and durable mapping must be established from actual APIs before schema/handler implementation. Missing mapping fails closed.

Never synthesize cookies, Origin, session IDs or role claims to enter `createVerifiedIdentityAccess`. Its cookie contract remains intact. Factor only genuinely shared live-record/role logic into an internal boundary, preserving its lock order and tenant/RLS behavior. MCP evidence must carry a real server-verified identity and be revalidated inside the authorized transaction. Keep caller-controlled data distinct from proof constructors.

Authorization follows the existing race contract: revocation that wins the relevant authorization locks denies access; expiry is checked again after awaited work before projecting a private response. Preserve the existing final-response checks and generic foreign/unrelated denials. Do not promise impossible instantaneous revocation of already delivered data.

Use the supported opaque active-token boundary described above, followed by live portal/consent checks. Its genuine server-only SDK context avoids a separate introspection credential. A public Cowork client must never be repurposed as a confidential introspection caller. Offline JWT verification is outside the selected path.

## Domain and response boundaries

`list_students` uses the live access service: tenant roster for admin, assigned students only for tutors. Bound pagination and result size. It must not expose the admin roster serializer wholesale.

`get_student` requires a current student-read relationship for that student and tenant. Return a closed staff preparation projection: stable portal student ID, display/Hebrew names, ceremony date, service slot/kind and assigned reading references, limited to fields the existing authority permits. No full emails, household phone/address, credentials, sessions, grants, guest links, recording/media capabilities, private prayer bodies or unapproved summary publication. Raw Maven facts are not this response type.

Tool arguments cannot select tenant, actor, role, email identity, SQL or an arbitrary API URL. Student IDs are lookup keys, not authority. Unsupported writes remain unregistered. Do not promote the pure Maven decoder/planner into an apply capability or silently establish identity from names, dates or household data.
