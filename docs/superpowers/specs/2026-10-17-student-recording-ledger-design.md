## Root architecture decision and bounded deliverable

Implement a persistent **student-recording metadata ledger**, selected-mode authorization, closed list/submit/deletion-request HTTP adapters and synthetic integration tests. No upload, decoder, byte delivery, storage provider, physical deletion worker, notification transport, frontend or production migration is included. A metadata response is never playback authority, and requesting deletion is not a claim that physical deletion finished.

Use new local migration0020 after released0019. Preserve historical migrations and release operators. Claude owns the calendar UI and human reference-index tooling in separate checkouts; neither stream's files belong to this assignment. Student recordings are student-level in this first ledger: do not claim an association with a verse or silently bind to a regenerated assignment-verse UUID. Later capture UI may add reviewed material labels; reference playback still requires its separate exact current-reading contract.

### Persistence and immutable capture identity

Add `student_recording` with opaque UUID id, tenant/student composite FK, opaque server-allocated asset UUID, lowercase SHA256 content identity, verified media type/byte length/duration, state, revision, creation instant, submission instant and deletion-request instant. Asset UUID is globally unique and **is not a path, URL, upload token or playback capability**. The actual provider mapping is future server-only work. No file name, user-supplied title, uploader identity or text is stored in this slice.

Persist only `private`, `submitted`, `deleting`. Valid paths are private revision1 → submitted revision2 → deleting revision3, or private1 → deleting2. Deleting is irreversible and is omitted from every list. A future trusted physical-cleanup adapter will confirm removal and delete the ledger row; this slice has no completion endpoint or method and makes no tombstone-retention claim. Media/asset/hash/student/tenant/id/creation identity never changes. Native CHECKs and invoker triggers enforce valid state/revision/timestamp combinations and legal transitions, including immutable submission time and preserved submission time during deletion. No-op rows remain identical; arbitrary version bumps or reset-to-private fail.

Apply FORCE RLS and existing tenant context, narrow runtime SELECT/INSERT/UPDATE grants only, composite tenant/student integrity, bounded media and existing timestamp conventions. An INSERT trigger must require private/revision1/NULL submission and deletion instants: valid-state CHECKs alone must not permit direct submitted/deleting inserts. No runtime DELETE grant before the separately reviewed cleanup worker. Extend the existing closed audit action list for explicit service creation, actual submission and actual deletion request only. Audit details contain only opaque recording id and selected mode, never media facts, storage identity, capture time or private content. Retries/no-ops do not add audits. Automatic ceremony-retention transitions add no recording audit in this slice; do not fabricate an actor/mode in the SQL trigger. The existing ceremony-edit audit stays unchanged.

### Trusted registration seam; no client creation route

Provide a separate server-only registration factory for a future trusted capture pipeline, under fresh own-student or exact linked-child `practice-write` authority. Its closed internal descriptor contains server-allocated asset id, content SHA and independently verified media facts; syntactic validation is not proof that bytes were decoded. **The actual runtime-composed object must omit registration and its descriptor**, not merely hide it behind a TypeScript type or an unimplemented HTTP route. Never accept registration from a request body or describe this as a finished upload. The future processor must check actual bytes/container/codec/duration and exact capture ownership before calling it.

One retained immutable asset can register once. An exact authorized same-student/asset/media/hash retry may return its current private/submitted record without mutation/audit; mismatched binding/content or deleting state fails generically. Cross-student/tenant collisions never disclose the other record. No retry can reset submission or recreate a retained deleting asset. This is not permanent deduplication after future physical cleanup removes the ledger row: the future processor must reject a deleted/consumed capture receipt rather than recreate it. Future storage must preserve immutable asset identity; user-supplied storage locators are never accepted.

### Authority, lifecycle and projections

Reuse existing `createPracticeService(...).withPracticeCapability` with literal `read` or `practice-write` for student/linked-child operations. Tutor/admin list reads reuse `withStudentCapability` with an explicit operation/mode restriction. Base parent mode always fails before recording lookup; do not infer permission from overlapping roles. Only own-student or exact linked-child practice may submit or request deletion. Tutor/admin have no mutation operation in this slice and never see private recordings.

Always bind selected student, tenant and recording, and use the existing tenant → user/session/membership/grant → student → relationship/context → recording lock order. Reads lock only visible rows; writes lock the exact recording and compare expected revision atomically. All current-authority/real-time expiry AND fresh recording-retention checks repeat after awaited SQL/uniqueness/row/audit operations and before return, including list/cursor reads and registration/submission replay/no-op paths. A deadline crossing during a wait cannot expose submitted metadata or return a successful submission/registration. A submitted record cannot be unsubmitted. Submit/delete competing at the same initial revision have exactly one winner; the loser conflicts rather than obtaining magic deletion priority. Once deleting, submission can never revive it. Never retain an earlier proof across a sibling switch.

Metadata lists return at most50 records, with one-extra-row pagination and an opaque recording-id cursor. Resolve the cursor under the same visible student/mode/state/retention filter; unknown/foreign/private-for-staff/deleting cursors fail identically. Internally sort student/child lists by creation instant/id and staff lists by submission instant/id; never encode hidden instants into the cursor. Deleted/stale cursors require an explicit list refresh, not a write/retry.

Student/child projection: id, revision, private/submitted state, verified media descriptor, Chicago date recorded and optional Chicago date submitted. Tutor/admin projection: id, revision, submitted state, verified media descriptor and Chicago date submitted only. No exact creation timestamps, source actor/context/mode, asset/hash/URLs, private counts or hidden-state flags. Recording duration is a media fact for eventual playback, not practice-time reporting or lesson accounting. List responses never manufacture practice events or change progress. No reference/generated kind enters this table or API.

### Retention and rescheduling

Use a fresh trusted instant and America/Chicago calendar dates, inclusive at the one-year anniversary, with Gregorian Feb29 clamping; support valid ceremony9999's year10000 anniversary as the deployed practice-calendar implementation already does. The older pure policy's unrepresentable string boundary must not silently reject a valid roster student or guess an expiry. Reuse reviewed calendar arithmetic deliberately; no historical0018 edits.

All private and submitted records become unreadable/unsubmittable when due. Registration and submission after the overall anniversary are refused (local microphone capture is outside this server ledger). Own-student/child deletion requests remain allowed when a record is due, with fresh authority and an exact expected revision; an already deleting record is a no-op only at its current revision and adds no audit. Staff still see no due/deleting metadata. A ceremony-date invoker trigger, after the student lock, uses actual post-wait time and both OLD and NEW ceremony dates: any still-private or submitted record overdue under either date becomes permanently deleting, in the same transaction as the date update. Private records take revision1→2 and retain NULL submission time; submitted records take revision2→3 and preserve submission time. A postponement cannot revive overdue audio. Preserve existing practice-history retention and roster audit behavior; do not expose recording changes through the roster response.

No physical deletion is claimed. Production use requires a bounded trusted cleanup worker and approved storage. Background cleanup must later work even after user/session/student access is revoked; it must not require an active student session. Future app-controlled offline copies must honor the same anniversary through the reviewed expiry/lease contract.

### HTTP integration boundary

Closed endpoints follow existing `/api/students/:studentId/...` routing: `GET recordings?mode=...` with optional `afterId`; `POST recordings/:recordingId/submit` and `/delete` with exactly mode/expectedRevision. Origin/CSRF and exact practice-context transport follow existing request/capability checks, unique closed queries, bounded JSON/deadlines and private no-store responses. No client-selectable internal callback, create/register, complete-delete, provider callback, byte/range route or raw record export. Unknown/stale/foreign recording failures use existing generic safe denial/conflict semantics without partial private responses. Mutation receipts contain id/revision/state only. The router may be wired locally, but no provider or production operation is authorized by this contract.
