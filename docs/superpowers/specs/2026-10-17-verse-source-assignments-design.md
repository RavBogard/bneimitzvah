# Versioned citation sets for an assigned verse

## Settled decisions (Daniel, binding)

Tutors and rabbis can assign sources to a student's own verses. Students and delegated linked-child practice can read them. A citation assignment is not approval of generated content, permission to reproduce an edition, a congregation default or a new clergy role. Keep human reference playback and the flowing Hebrew reading intact. No source bodies, transliteration, chatbot, generated voices, recording work, invitations or mail in this milestone.

## Stream and data

Use an immutable FULL-VALUE citation-set version stream keyed by tenant, student, stable reading assignment ID, reading revision and canonical target verse. A new reading revision starts an empty version0 stream; no old citations silently reactivate even when a verse survives or returns. Preserve old history without exposing it as current student work. Do not FK to transient assignment_verse IDs, which are recreated on reading changes.

Each committed version stores a closed, copied, deterministically ID-sorted set of at most32 citations, with provider link ID, source ref, complete indexTitle, category and short nullable en/he labels under the accepted metadata field bounds. No caller snapshot, source body, edition rights flag, approval flag, URL destination or arbitrary JSON field. The32-item selected-set cap is an application bound, not a restriction on the4096-entry discovery catalog. Maximum escaped metadata fits a128KiB snapshot/complete private response budget; enforce actual bytes as well as counts. The current empty set is version0, not a fabricated persisted row.

Record tenant/student/stable assignment/reading revision/verse, actor membership/user/grant and staff role, expected/base version, next version, actor-scoped mutation UUID, exact request digest, timestamp and immutable citation snapshot. Follow existing tenant/student/assignment/membership/grant composite FK, forced tenant RLS, runtime SELECT/INSERT-only, immutable UPDATE/DELETE and atomic audit patterns. Explicitly extend the closed audit action constraint. RELEASE migration0021 is next; never import parked recording migrations. Native review must prove constraints and privileges, not only application checks.

## Explicit staff mutation, one request

Add a narrow source-write capability with the same admin/assigned-tutor and cookie-origin privilege pattern as note-write; do not widen parent/student/child-practice or change other capabilities. Fresh means ordinary live per-request authorization, not a15-minute recent-login gate: preserve the existing StudentCapability fresh:false behavior and add no reauthentication screen. Reads use existing read access, including explicit linked-child context. Every operation verifies the current confirmed reading ID/revision, exact canonical verse vector and target membership under the established authority/reading lock order, with real expiry checks after waits.

The write intent supplies current selection, target verse, expected set version, unique mutation UUID, desired unique source-ID set and optional catalogHash. Inputs are strictly closed and snapshotted before awaits; IDs are sorted for the digest. Bound the request body to16KiB and the complete private response to128KiB. Do not accept client citation metadata, provider URLs or work titles.

Use one HTTP write request with preflight/public-I/O/final-transaction phases, rather than an extra signed prepare/confirm protocol:

1. Fresh source-write authority transaction checks actual target/reading, live time, exact committed receipt and expected head. Capture the original actor/session/membership/grant/student/relationship/reading bindings and current immutable set. No-op identical sets are rejected as no-change without a version/audit. Exact committed replay is considered before no-op/head checks.
2. Retain stored snapshots for surviving IDs. If new IDs are added, require a valid supplied catalogHash, fetch related metadata for the captured canonical verse outside SQL, validate the accepted closed catalog and its full digest, and resolve EVERY added ID server-side. No client metadata adoption. Removal-only and clear operations perform no provider I/O. No source text or version API. Stage source failure/catalog change/missing candidate as enums; do not let them hide final authority loss.
3. A fresh source-write transaction using the original copied request compares all original bindings, current reading/verse and expected head before adopting resolved metadata. Authority/staleness/conflict take precedence over public lookup outcomes. Check abort/time before writing and after uniqueness/head waits. Insert one full-value next version and audit atomically. Expiry, abort or audit failure rolls both back. No DB transaction spans provider I/O; no late authority lock upgrade.

Provider hashes detect changes and are not write authority. Retained stored citations are not refreshed from a changed catalog incidentally. A changed candidate under the same provider ID requires explicit removal/re-add with a fresh selection, not silent replacement. The metadata reader remains fixed-host/stateless/bounded; do not introduce a global private cache or assume process concurrency bounds.

## Receipts, races and uncertain outcomes

The request digest binds the complete canonical intent: selection/kind/assignment/revision/verse, mode, expected version, desired IDs and supplied catalogHash. The receipt namespace is tenant/student/actor user/mutation UUID. Exact replay under fresh compatible staff authority returns ONE original committed snapshot plus the currentLatestVersion INTEGER, with no new audit. Do not return two full snapshots under the128KiB cap; a fresh read retrieves the current set. Changed intent or incompatible authority cannot adopt a receipt. An absent/head race is resolved by unique next-version/receipt constraints, never first-wins payload adoption.

Root settled compatibility after independent design review: the receipt namespace plus the same persisted actor membership ID, role grant ID and staff mode, under fresh current source-write/current-stream authority. A later valid session and later incidental authority/student revisions do not invalidate reading/replaying that committed intent. Do not require an expired historical cookie/session. This is distinct from a potentially inserting request's phase comparison: freeze and match its original tenant/origin/user/session ID and expiry, membership ID/revision, grant ID/revision/mode, student ID/revision, tutor relationship ID/revision (admin null), and full reading identity/revision/kind/canonical vector/target. The final phase always uses that request's original copied headers.

On unknown COMMIT, never automatically generate a new UUID, refresh expectedVersion or rebase the desired set. Provide authorized receipt reconciliation for the exact original intent. A found matching receipt confirms the committed result. Missing receipt is unconfirmed, not proof that an in-flight original request cannot still commit. Any controlled retry must retain the exact original UUID/intent and be proven safe by database uniqueness/CAS; this is logical transactional deduplication, not a claim of physical work quiescence. Native tests must cover pending originals, lost acknowledgements, same/different intents, concurrent updates and authority changes. Root must resolve any remaining receipt ambiguity before implementation.

The independent review accepts a controlled identical-intent retry: it reruns the full two-phase protocol with its own fresh binding, while both unique stream-next-version and actor-mutation constraints plus exact raced-receipt comparison prevent a second logical commit. A read with no receipt remains unconfirmed. No automatic payload/catalogHash/version/UUID substitution or new authority adoption is permitted.

After final authority/binding verification, check the exact compatible receipt again BEFORE current-head/no-op/public-error handling: the original can commit during a retry's delayed or failed metadata lookup. A matching receipt returns its original committed snapshot/latest-version integer despite that lookup outcome. After an INSERT uniqueness wait, compare the raced receipt exactly; never adopt an unrelated head or payload.

V1 reconciliation is current-stream-only: verify the actual current reading revision and target as for writes. Reading drift returns stale/unconfirmed; it does not expose an old stream's historical receipt or claim that an old write was absent. Historical reconciliation is deferred, not silently simulated.

## Interface and composition boundary

Add an internal service/data layer plus strict private/no-store HTTP read/write/reconciliation endpoints following existing student-work dispatch style. A read returns only the current stream's version and closed citations with the existing small authority/reading envelope. A write/replay exposes committed and latest versions distinctly. Use fixed errors/statuses without provider detail. The exact route/body DTOs are finalized during design review before edits. Runtime and offline/native fixtures compose actual services; no live fallback in tests. No UI in this backend milestone.

Settled routes: GET and POST `/api/students/:id/source-assignments`; POST `/api/students/:id/source-assignments/receipt`. GET allows only `mode`, `kind`, `assignmentId`, `assignmentRevision` and canonical `verseRef` as strict query keys. POSTs use an empty query and closed body containing those same selection/verse fields plus `expectedVersion`, `mutationId`, unique `sourceIds`, and optional `catalogHash`; student identity comes only from the path, never query/body. GET rejects bodies/transfer encoding/nonzero length. Mutations use the existing cookie-origin guard. Same-set no-change is a fixed409 without inserting a version/audit/receipt; exact existing receipt replay is checked first. Missing receipt yields an explicit unconfirmed outcome, not absent. All errors and successful/replay/current responses remain bounded private/no-store.

Expose and reuse an internal closed full-catalog normalization/digest helper from discovery without changing its existing hash serialization or page outputs. Resolve additions directly from that validated full snapshot; do not call410 paged requests or duplicate a subtly different digest algorithm.
