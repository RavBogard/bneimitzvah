## Identity, roles and active context

`user` is one real mailbox identity, globally managed by Better Auth. `student` is a congregation-owned learner record and need not have an auth account. A parent contact is contact information, never proof of access. Never create one auth user per sibling using the same mailbox, synthesize child email aliases, or turn a parent magic link into a direct student session.

Approved architecture: one membership per `(tenant_id, user_id)` plus separately revocable role-grant rows. A parent+tutor selects one active mode; permissions are evaluated for that mode rather than unioned. The cantor flag belongs to the tutor grant and adds no administrative permissions. Role and tenant claims do not belong in client-editable Better Auth profile fields. Self-profile editing permits display name/avatar only; identity email changes and account merges are disabled in 1.0 until an explicit verified recovery flow exists. An admin changes authority by revoking and issuing grants, never by allowing user profile updates to rewrite role claims.

Application context is a separate server-owned record, not an impersonated Better Auth session:

```
actorUserId + authSessionId + hostTenantId + actorMembershipId
  + activeRoleGrantId + mode + optional actingStudentId + optional guardianId
```

Modes: `admin`, `tutor`, `parent`, `student`, `child-practice`. The first four require the matching active grant. Own-student mode also requires an active student-identity link. Child-practice requires an active parent grant AND guardian relationship with `practice_enabled=true`; `actingStudentId` identifies the learner while `actorUserId` remains the guardian. Linking a guardian through the reviewed admin workflow defaults `practice_enabled=true`, fulfilling Daniel's confirmed child-entry behavior; an admin can suspend access by revocation.

Parent mode exposes linked children's read-only views. A deliberate “Practice as [child]” POST creates a short-lived context for that one child; “Return to parent view” and sibling switches create a new context and revoke the old one in that browser tab. Child-practice permits only student practice capabilities, such as that child's translation drafts and later recording/submission operations. It never grants roster, invitation, reading assignment, tutor-note or approval authority. The student's name and “Practicing as … / signed in through parent” remain visible, with a clear exit on all screen sizes. Separate pages use stable book/chapter/verse references for Zoom discussion.

**Approved per-tab implementation:** an opaque random 256-bit context handle, hashed in the database and held in `sessionStorage`, sent in `X-Practice-Context` on private data/action requests; never in URLs, logs, referrers or share links. The host-only HttpOnly auth cookie is still required, so the context handle alone cannot authenticate. Private context-sensitive content loads through authorized handlers after the shell, avoiding a session-wide active-child cookie that could silently redirect another tab's draft to a sibling. Server actions use the same handle as untrusted input and call the same authorization service. A context expires after 60 minutes and cannot outlive its auth session. Reload validates the stored handle; new/duplicated tabs may require fresh selection. Any mechanism change returns to Astra's architecture review and must preserve session binding, explicit switching and multi-tab safety.

Each action names its target student explicitly and must match the context target. Every read and write reloads the active session, membership, role grant, student status and relevant guardian/identity/tutor relationship. Revocation denies the next request even if a context row or browser page remains. Disable a student to deny practice without deleting history. Expiry, logout, role revoke, guardian revoke, account unlink and student disable invalidate applicable contexts; proactive context revocation complements, never replaces, live relationship checks. Aborted requests and revision tokens prevent a response or autosave started under one child from applying after a switch. Concurrent revoke/write transactions lock the governing grant/relationship rows consistently: if revocation commits first, no subsequent write can succeed; an already-authorized write committing before revocation is ordered before it in the audit.

## Database constraints

Use text tenant IDs (`crc` for the launch tenant), UUID application entity identifiers, and Better Auth's generated identifier types for its tables. Every tenant-owned entity has `tenant_id NOT NULL REFERENCES tenant(id)`, an identity unique on `(tenant_id,id)` (or composite primary key), and immutable tenant ownership. Every relationship to another tenant-owned entity is a composite foreign key including `tenant_id`. An ID-only FK plus an application filter is insufficient. Global auth-user/session references are the explicit exception, accompanied by tenant membership checks. Prefer RESTRICT/NO ACTION for identities and history; revoke/disable instead of cascading away evidence.

Global tables grant no tenant access themselves. Confirm unique normalized auth email semantics with Google and magic links in the spike. |

Partial unique `(tenant_id,membership_id,role) WHERE revoked_at IS NULL`. Immutable role/member/tenant; revoke/regrant. Add unique `(tenant_id,id,role)` for typed references below. |

Role-specific relationship FKs can use a constant checked `role` column referencing `(tenant_id,role_grant_id,role)`; do not rely on a database CHECK containing a cross-table query. A revoked grant leaves FK-valid history but fails live authorization. Reinstating a membership does not revive revoked grants or contexts.

For subsequent phases, use the same tenant/composite rule for source defaults, source assignments, summaries, notes, translation versions, recordings and aggregate play counts. `translation_draft` versions are append-only with unique `(tenant_id,student_id,verse_ref,version)` allocated transactionally. Records of student work carry actor and acting-student attribution. Auth/session/verification tables, public text/lexical caches and global chant assets are explicitly global; none may contain a student link disguised as a global cache key. Do not implement recording retention or global chant release tables by inference from this auth spec.

Drizzle supports database CHECKs, composite keys and `foreignKey({ columns, foreignColumns })`; its application relations do not replace database constraints. Review generated SQL for every tuple FK and partial index and execute it on real Postgres. [Drizzle constraints](https://orm.drizzle.team/docs/indexes-constraints).

## Host resolution and request boundary

Resolve a host before auth initiation, callback handling or tenant data. Parse a single valid authority; normalize DNS case and reject userinfo, comma-separated values, malformed ports, unexpected forwarded-host values and ambiguous hosts. Use the deployment platform's trusted request host only; arbitrary `X-Forwarded-Host` supplied by a caller must not override it. Preserve the validated origin/port for local mappings. Unknown/unmapped hosts fail closed before sign-in or data access; never default to CRC.

The approved canonical production auth origin is `https://bneimitzvah.centralreform.org`. The existing `https://bneimitzvah.vercel.app` remains an infrastructure placeholder until DNS/provider setup is ready; it is not an authenticated alias. Pending custom-domain DNS must not silently create another authenticated origin. Configure provider callbacks for the canonical origin. Preview gets one exact deployment origin at a time from trusted deployment configuration, its own explicit mapping to a synthetic CRC tenant/database, and a separate auth configuration/secret. Local mappings are exact `localhost:3000` and `127.0.0.1:3100` (or the tested ports), enabled only in local/test environments. No wildcard Vercel origins, suffix matching, localhost allowance in production, or client-written mapping rows.

Create auth configuration only from validated configured origins; do not infer its base URL from arbitrary headers. OAuth/magic-link redirects are fixed relative destinations or same-origin allowlisted paths, never caller-provided external URLs. Retain Better Auth state/PKCE/origin protections; do not disable origin/CSRF checks. Host-only Secure, HttpOnly cookies in deployed HTTPS environments, no shared parent-domain cookie. Explicit trusted origins are supported; the library warns against disabling origin checks or leaving localhost trusted in production. [Better Auth security](https://better-auth.com/docs/reference/security).

All Route Handlers AND Server Actions independently call a server-only authorization service. Middleware and hidden buttons are navigation aids. Inputs never set `tenant_id`, `actor`, role, guardian, publication status or assignment author directly. Lookup by `(resolvedTenantId, targetId)` then test the relevant live relationship; filter every join by tenant. Return indistinguishable 404s for unavailable/foreign object IDs, 401 for no session, 403 for disallowed actions on known authorized views. Do not return SQL/FK/provider error detail. Mutations require same-origin/CSRF protection, validated input and an audit event in the same transaction. Private responses use no-store/private caching; no shared Next.js cache of session-dependent payloads.

Only `src/server/data/` accesses tenant tables; auth adapter and reviewed migration/owner scripts are narrow exceptions. UI, API and future MCP call capability functions such as `readStudent(context, studentId)`, `setReading(context, studentId, expectedRevision, input)` and `appendTranslation(context, studentId, verseRef, expectedVersion, text)`. These are proposed application functions, not Better Auth SDK APIs. Import-boundary tests prevent bypassing the data layer.

## Invitations, email verification and recovery

Approved architecture: invitation acceptance is a separate authenticated POST, not a “first email match makes a membership” side effect. It requires the secret invitation token AND a currently verified auth email matching the immutable normalized invite email AND the current mapped tenant. Trim and case-normalize consistently; do not remove plus tags or Gmail dots. Invitation metadata, client roles and auth callback query strings are untrusted. Knowing an email or authenticating on Google gives no roster access.

Issue a cryptographically random 256-bit invitation token; store only its hash. Approved validity: 72 hours. Inviter must be an authorized admin, and any student target must already belong to this tenant. A role/target change revokes and reissues; never edit an existing link into stronger authority. Redeem in a transaction with a conditional update or row lock checking expiry, revoked and accepted state; create membership/grant/relation and the audit event atomically. Two concurrent redeemers cannot create two grants. A replay returns a generic already-handled/invalid result and never changes authority; an existing authorized member can navigate normally after sign-in. Resend revokes the old invite before issuing a replacement, with an auditable send-failure state if delivery fails.

Landing GET does not accept an invite, protecting against email-link scanners. Exchange the token into a short-lived, host-bound pending-invitation cookie and redirect to a clean URL before OAuth. No raw token persists in localStorage or analytics. Set no-referrer and no-store on token landing/callback paths; disable third-party scripts there. After sign-in, show the intended relationship and require acceptance. Avoid exposing family names before authentication. Do not log request query strings on these paths in app or deployment diagnostics.

Multiple sibling invitations to one parent mailbox all resolve to one parent identity; each grants only its named guardian link. A student invite requires an individual verified student mailbox; if the supplied contact equals a guardian mailbox, route the admin to guardian access instead. If an existing parent identity is the invite recipient, do not silently add a student identity to it. Admin review must correct a mistaken invitation or use guardian practice. Email addresses are private even in denied responses. Unknown magic-link requests return the same generic delivery response; a new authenticated account without an accepted invite gets only an “ask your congregation administrator” screen, no student data.

Implementation policy permits global auth-only accounts without memberships, avoiding an unverified custom signup filter inside provider internals; rate-limit requests and prune inactive auth-only accounts through a separately reviewed retention task. Use database-backed rate limiting supported by the pinned config rather than per-instance memory alone. Application invitations also have per-actor/recipient throttles. Choose and document routine rate-limit parameters during the compatibility spike; they need no new Daniel approval. Rate-limit email identifiers using keyed hashes; do not log mailbox values. Do not claim that the plugin's email/password enumeration protections automatically cover a custom invitation workflow.

Do not support self-service family-link or identity-email changes in this milestone. An admin may revoke/reissue a guardian invitation after verifying the request through existing congregation practice. Duplicate identity merges need a reviewed recovery workflow; never merge by editable name or an unverified email claim. Any auth email change invalidates contexts and requires all affected links to be reviewed; the disabled endpoint must be tested directly, not just hidden.

## Application scoping plus tenant RLS

**Approved architecture:** application capability checks plus database tenant RLS from the first migration. RLS is a backstop against omitted tenant predicates, not a replacement for student/guardian/tutor authorization or protection against a compromised runtime credential.

Use a dedicated runtime Postgres role without owner/superuser/BYPASSRLS privileges. Migration credentials are separate and unavailable to browser handlers. Enable and force RLS on tenant content/relationship tables, with matching `USING` and `WITH CHECK` conditions:

```sql
tenant_id = nullif(current_setting('app.tenant_id', true), '')
```

Missing tenant context yields no allowed rows. Policy lookup for the small `tenant_host` directory is separate: runtime can resolve an exact host mapping but cannot mutate it, and the mapping never exposes contacts. Global auth tables use a separately constrained auth database interface, not tenant RLS. Do not give a tenant table an “all rows” auth-adapter exemption.

For each capability transaction, derive tenant from the trusted host and execute parameterized `SELECT set_config('app.tenant_id', $1, true)` on that transaction's client before any tenant query. Audit actor/mode can also be transaction-local values but must be derived from validated session/context. Pass that transaction handle through all data operations and commit/rollback before releasing it; never set session-wide tenant state on a shared pool or call an unrelated `pool.query` inside the transaction. Bind relationship checks, mutation and audit in that transaction. PostgreSQL documents transaction-local configuration and warns that owners/BYPASSRLS bypass policies. [Configuration functions](https://www.postgresql.org/docs/current/functions-admin.html#FUNCTIONS-ADMIN-SET), [RLS behavior](https://www.postgresql.org/docs/current/ddl-rowsecurity.html).

Neon uses PgBouncer transaction pooling; ordinary session `SET` state is not persistent between transactions. Its HTTP driver offers non-interactive batches; `Pool`/`Client` over WebSockets supports interactive transactions. Recommendation: Node runtime with the interactive Neon client and Drizzle's corresponding driver for invitation acceptance, context validation and multi-step writes; verify exact adapter transaction APIs in the compatibility spike. The HTTP transaction batch could support a bounded RLS query batch, but do not claim the HTTP driver supports an awaited Drizzle transaction callback. [Neon driver](https://neon.com/docs/serverless/serverless-driver), [pooling limitations](https://neon.com/docs/connect/connection-pooling).

Use a direct migration connection, per Neon's guidance. Run RLS tests as the actual restricted runtime role on a disposable local/CI Postgres, not as migration owner. Prove both missing-context denial and tenant A/B interleaving, including rollback then pool reuse. PGlite covers most domain/constraint tests but cannot establish remote connection-pool isolation. No new Neon account or paid project is created by writing this spec. Application-only scoping does not satisfy this approved design; any deviation requires Astra's architecture review and independent reviewer acceptance.

Haftarah and blessings are supported kinds without requiring Phase 3 text UI now. Keep CRC customs marked to-confirm where the mission has not settled them.

An own-account student sees only their learner shell. Sibling names are never exposed by email search before verified sign-in and accepted linking.
6. CSV import: admin only; bounded file size and row count (proposed 1 MB/500 rows), required-field validation, preview of valid/errors before transactional confirmation, normalized dates/contact validation, and explicit duplicate confirmation. Never merge learners by shared parent mailbox/name. CSV content is neither logged nor committed; no automatic mail on upload/preview. Confirming an invitation action is separate from importing contacts.

No final portal visual design is implied. Build accessible functional shells for Daniel; preserve the code-first design workflow. Data constraints and capability tests can land before external provider credentials are available.

## Settled architecture decisions (Astra, 2026-10-15)

1. One membership per user/tenant, separate revocable role grants and composite tenant relationships; roles cannot be edited through self-service profile fields.
2. Per-tab opaque session-bound child context, live relationship checks on every action, narrow practice capabilities, 60-minute context lifetime and explicit parent+tutor mode separation.
3. Application capabilities plus FORCE tenant RLS, nonowner/no-BYPASSRLS runtime role and transaction-local context. The interactive Neon/Drizzle path must pass the compatibility spike before implementation proceeds.
4. Canonical production auth origin `https://bneimitzvah.centralreform.org`; the Vercel hostname remains the infrastructure placeholder, with no authenticated alias. Preview/local use exact synthetic environment mappings only.
5. Verified same-email linking conditional on SDK evidence; separate invitation-token plus verified-email POST acceptance, 72-hour invitations and no membership from email match alone.
6. Routine fresh-session and rate-limit parameters are documented implementation defaults, not additional Daniel approval gates. Astra routes bounded implementation assignments and independent adversarial review. This architecture review does not substitute for that security review.

The initial implementation spike must resolve only the SDK boundaries before feature work: pinned CLI/schema compatibility, the adapter's interactive transaction support, Google/magic-link verified-email behavior and linking order, a real DB-backed session/revocation round trip, fresh-session enforcement, database-backed rate limiting, and the isolated browser harness mechanism. None has been implemented or reported passing by this research assignment.
