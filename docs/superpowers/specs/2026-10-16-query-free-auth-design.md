## Problem and recommendation

The hosting-log addendum in `docs/planning/2026-10-15-kickoff/PROVIDER-SECURITY-REVIEW.md` records a harmless canary whose native Vercel request metadata retained synthetic `token`, `code` and `state` query values. Application logging suppression worked, but cannot remove the hosting copy. Rejecting a query after ingress also cannot erase that copy.

Use fragment landing pages plus explicit same-origin body POSTs for email links and invitations. Use Google's Sign in with Google button in popup/callback mode, with a server-created, browser-bound, single-use nonce challenge and a same-origin ID-token body POST. Continue using Better Auth 1.7.10 for identity verification, account policy and session creation. Never mount its unrestricted HTTP handler.

The objective is that every app-owned network request URL and redirect is free of bearer credentials, authorization codes and auth state. Google and the mail provider necessarily handle their own sign-in/mail data; this design does not certify their internal logging. Browser extensions, compromised mailboxes and same-origin script compromise remain outside the transport fix.

## Public contract

All paths below are proposed names to be implemented together. No endpoint accepts URL search parameters, caller redirect destinations, provider claims or practice contexts. Existing exact incoming-host resolution runs before any credential adapter.

| Public surface | Allowed behavior |
| --- | --- |
| `GET /auth/email#token=…` | Serve a minimal confirmation page; the fragment is never part of the HTTP request. No token redemption on GET. |
| `POST /api/auth/email/confirm` | Closed JSON `{ token }`; confirm a captured magic token through the server-local SDK verification path. |
| `GET /invitations/open#token=…` | Serve the same minimal landing mechanism with invitation-specific copy. No cookie exchange or invitation mutation on GET. |
| `POST /api/invitations/open` | Closed JSON `{ token }`; seal the pending invitation cookie, return a fixed next destination. Does not accept/redeem the invitation. |
| `POST /api/auth/google/challenge` | Closed JSON `{}`; create the short-lived browser-bound Google challenge described below. |
| `POST /api/auth/sign-in/social` | Closed JSON `{ credential, challengeId, csrfToken }`; Google only, no public SDK-shaped `idToken` or nonce input. |
| Existing magic-link request/sign-out/session/invitation review and acceptance routes | Preserve their current closed contracts, adjusted only where they refer to the new sign-in result. |

Retire public `GET /api/auth/magic-link/verify` and `GET /api/auth/callback/google`, including the query-code OAuth start branch. Return a fixed refusal without echoing query data or redirecting it elsewhere. Do not offer a legacy-link query-to-fragment converter: the secret has already crossed ingress. Old outstanding email links must be reissued using the new format after deployment. Prior Google redirect-URI console entries may remain temporarily as configuration history; the app must not use them.

Every body mutation requires the resolved exact `Origin`, `Sec-Fetch-Site: same-origin` when supplied, strict JSON content type, bounded body parsing and absent URL query. This preserves `requireCookieMutation` and the existing same-origin fetch/CORS boundary as CSRF protection. Google's additional challenge-bound CSRF secret is mandatory. No endpoint permits credentialed cross-origin CORS. Responses are private/no-store with fixed errors; no arbitrary diagnostics, provider JSON or input reflection.

## Email and invitation fragment landings

Use a dedicated tiny HTML route response for each landing, rather than routing the fragment through React state, a Next router, server actions, hydration props or a general page wrapper. The first synchronous script copies and validates the bounded exact fragment into a lexical variable, then immediately calls `history.replaceState(null, "", location.pathname)` on success and failure. Only one canonical token parameter is allowed; reject duplicates, extras, malformed encoding, search parameters and oversized fragments. Magic tokens retain the pinned 32-letter format; invitation tokens retain the canonical 32-byte/43-character base64url format.

Render an ordinary keyboard-accessible button labelled “Continue signing in” or “Review invitation.” Its handler sends the in-memory token in the appropriate JSON POST only after explicit activation. No automatic redeem effect, form auto-submit, focus handler, prefetch, image URL or GET performs the exchange. Disable concurrent submissions. Treat expired/invalid links with one fixed explanation and a route to request/reopen a link. A mail scanner following GETs cannot consume either token. Arbitrary scanners that emulate a person and click buttons cannot be categorically excluded.

The landing contains no Google library, analytics, third-party asset, service worker registration or reporting endpoint. Use private/no-store, `Referrer-Policy: no-referrer`, `X-Content-Type-Options: nosniff`, no framing, and a narrow CSP for the reviewed inline script/style (hash or response nonce), `connect-src 'self'`, `form-action 'self'` and `base-uri 'none'`. Do not emit CSP reports containing the original document URL. Clear token references on completion, expiry, pagehide or exit; JavaScript cannot promise physical memory erasure. Reload/back-forward restoration must not trigger a retry or recover a token from storage. Reopening the original email is the recovery path. Never put the token in local/session storage, IndexedDB, DOM attributes, history state, error text or telemetry. Browser URL visibility before the first script executes cannot be eliminated; immediate history replacement minimizes its lifetime.

After success use `location.replace` with a fixed server-approved local destination. Fragment validation or History API failure never falls back to a query URL. If JavaScript is unavailable, explain that opening the link in a JavaScript-enabled browser is required; do not redeem it on GET.

### Magic-link SDK bridge

Keep Better Auth's five-minute expiry, hashed stored token and atomic single use. At issuance the existing SDK callback supplies both its internal URL and token. Validate the internal generated URL against the pinned path, token equality and current closed callback set, then construct a new canonical outward URL containing only `/auth/email#token=…`. That SDK URL is an in-process value, never sent as a link, network request, redirect or diagnostic. Change mail transport validation to accept only the new outward shape. No identity or callback destination appears in the fragment.

On confirm, derive the success destination from the current valid pending-invitation cookie (`/invitations/accept`) or `/`; derive error destinations on the server. Construct the SDK's GET verification Request only in memory and call `runtime.auth.handler` directly. Never call `fetch`, follow an SDK redirect or expose that internal URL. Using the handler rather than an unreviewed direct `auth.api` invocation preserves handler-level database throttling and middleware. Retain the closed SDK header reconstruction and synthetic rate-limit bucket; do not trust forwarded IP headers.

Project the SDK response into a small `{ ok: true, next: "/" | "/invitations/accept" }` result, or fixed failure. Preserve `appendSdkCookies` validation and separate Set-Cookie fields; cancel the SDK body and never return its session token, user object, error parameters or Location verbatim. Validate the internal Location against the established local allowlist. Preserve expiry/replay under real PostgreSQL contention; do not replace the SDK token store or consumption logic.

### Invitation exchange and acceptance

Construct issued/resend invitation URLs as `/invitations/open#token=…`; update both service construction and canonical mail validation. Convert the current `pendingInvitations.exchange` GET into a POST body exchange after host/origin/body checks. Keep AES-GCM, purpose/origin/environment binding, ten-minute lifetime, HttpOnly SameSite=Lax cookie, Secure/__Host in production, duplicate-cookie rejection and fixed errors.

The exchange stores only the existing sealed pending cookie and returns `{ ok: true, next: "/invitations/accept" }`. Review remains read-only; the existing separate acceptance POST still checks its review binding, verified mailbox, current tenant, grant/relationship eligibility, revocation/expiry, locks and one-time acceptance. Possessing a fragment or staging cookie creates neither a role nor membership. Concurrent acceptance and stale review protections stay intact. Pending detection for Google moves to the challenge/confirmation adapter as specified next.

## Google challenge and ID-token adapter

Google documents a callback receiving the ID token in popup mode, a `nonce` initialization field and a separate redirect mode. Use the callback mode and the provider-rendered button, not One Tap or automatic sign-in. [Google JavaScript API reference](https://developers.google.com/identity/gsi/web/reference/js-reference)

1. On the sign-in view, POST the empty challenge request after the exact-host/mutation checks. Generate independent cryptographically random 32-byte values for challenge ID, nonce and CSRF secret. Bind them to an independent random browser-binding cookie. Reuse an existing well-formed binding cookie for simultaneous tabs; otherwise set it with HttpOnly, SameSite=Lax, Secure/__Host in production, Path=/, no Domain and a bounded ten-minute lifetime. It is a login-attempt binding, never an identity or authority. Never use a caller cookie value as a nonce, CSRF secret, SQL key or redirect.
2. Store a five-minute challenge in the existing global auth `verification` table through a small application-owned repository, avoiding a new infrastructure service or migration. Derive the exact primary key from a fixed `portal-google:v1:` prefix plus the validated random challenge ID. Derive a separate identifier with a purpose-separated HMAC of the browser binding, challenge ID, environment and canonical origin. Store a versioned closed value with the server nonce, CSRF hash, canonical origin and an allowed return destination derived from the pending-invitation cookie. Store no Google credential, email, user claims or session token in this challenge.
3. Return only `{ challengeId, nonce, csrfToken, clientId, expiresAt }`. The client ID is public configuration. Keep the other values in closure/ref memory; never URLs, storage, UI text or logs. Issue throttling must cover challenge creation itself with the existing database-backed fixed-origin bucket and a bounded per-binding budget; the pinned SDK's social-sign-in throttle alone does not protect this new route. Clean up only expired application-prefixed challenges in bounded batches. No caller-selected identifier or arbitrary row operation is exposed.
4. Load `https://accounts.google.com/gsi/client` only on the clean sign-in view. Initialize once per prepared page with this exact configured client ID, server nonce, `ux_mode: "popup"`, `auto_select: false` and a callback. Render the official Google button only after preparation. Do not set `login_uri`, call `prompt()`, or use the OAuth authorization-code client. Expiry/cancel/failure offers a clean preparation/reload; never reuse a consumed challenge or fall back to the old query callback. Disable/unmount expired and duplicate attempt controls. Popup creation stays attached to the user's button activation.
5. The callback submits only the credential string, challenge ID and CSRF secret to the public social endpoint. Bound the credential size (for example 16 KiB within the existing request ceiling), reject other provider inputs, reject missing/duplicate cookies and require the exact Origin/Fetch Metadata boundary. The request must not supply nonce, access/refresh token, identity/profile, scope, email, callback or account-link instruction.
6. Within a database transaction, lock exactly the derived application challenge row, require its identifier to match the browser binding, compare the CSRF hash in constant time, validate version/origin/destination/expiry, then delete it and commit. Only one contender may obtain its server nonce. Different-tab challenge rows remain independent; no in-process replay map or stateless signed cookie qualifies. Missing/expired/mismatched/consumed challenges never reach Better Auth. A consumed attempt stays consumed if verification or networking subsequently fails; the user prepares a new attempt.
7. Call Better Auth locally using an internal POST to `/api/auth/sign-in/social`, with `{ provider: "google", idToken: { token: credential, nonce: storedNonce }, callbackURL: storedDestination }` and the reviewed SDK headers. No browser nonce is forwarded. Require a canonical three-part JWT with an RS256 protected-header algorithm before SDK invocation; this is an additive format/algorithm restriction, not identity validation. Do not write a custom token verifier, override `verifyIdToken`, trust decoded profile claims or introduce a user-info network shortcut.
8. On successful SDK status copy only validated cookies and return fixed `{ ok: true, next }`. **Discard the SDK JSON:** the pinned ID-token branch returns the session token and user. Preserve the existing `accountLinking` settings (`trustedProviders: []`, `allowDifferentEmails: false`), including verified same-email magic-link ↔ Google identity reuse; reject unverified/different-email linking and do not change memberships. Keep disabled password/profile mutation routes and existing access/refresh token encryption; do not claim the stored ID-token field is encrypted. Unexpected SDK redirect/status fails closed. Authentication still composes with live application capability checks after sign-in.

Challenge-table isolation is a review requirement: app reads/consumes use exact derived primary key **and** exact purpose-bound identifier, never the supplied ID directly. SDK magic-link identifiers use `magic-link:`; the app prefix cannot collide with them. No app cleanup touches unprefixed rows. The inspected pinned `findVerificationValue` cleanup deletes rows only where `expiresAt < now`; it may remove expired challenge rows, which is safe. Prove that boundary against the actual adapter, including live challenge rows. Treat malformed stored values as fixed failure without dumping them.

The binding cookie may remain until its short expiry so one successful tab does not invalidate another tab's outstanding attempt. On acknowledged logout expire the browser-binding cookie and discard UI attempt state behind a generation barrier, including late GIS callbacks. An old unconsumed challenge then fails with the browser's current cookies. This cannot cancel a POST already in flight with a captured cookie, and does not promise global login/logout race linearization. Refresh/timeout handling must not turn an uncertain response into an automatic credential replay.

### Pinned implementation evidence and limits

`package.json` pins Better Auth to **1.7.10**. `node_modules/better-auth/dist/api/routes/sign-in.mjs` invokes `verifyProviderIdToken` before Google's `getUserInfo`, then applies `handleOAuthUserInfo`, sets session cookies and returns a JSON session token. The active verifier is `node_modules/@better-auth/core/dist/oauth2/verify-id-token.mjs`; it checks issuer, audience, signature, time bounds and optional provider claims. It checks nonce only when a nonempty nonce argument is supplied. Thus caller-provided nonce, or a valid ID token by itself, cannot establish browser intent or one-time use.

Google's configuration in `node_modules/@better-auth/core/dist/social-providers/google.mjs` supplies Google's issuers, configured client ID as audience, one-hour maximum token age and Google JWKS retrieval/import. It does not set the generic verifier's `algorithms` array; the generic fallback derives an algorithm from the protected header. The server's RS256 precheck explicitly narrows that surface without replacing cryptographic verification. The similarly named exported `verifyGoogleIdToken` helper is not the active sign-in branch and must not be cited as proof of this route's behavior.

`node_modules/better-auth/dist/plugins/magic-link/index.mjs` stores hashed tokens, uses the SDK atomic verification consumer and sets session cookies. `node_modules/better-auth/dist/db/internal-adapter.mjs` checks consumed verification expiry. These are source findings, not a new observed provider round trip. Tests must exercise the actual pinned handler and real adapter, not only stubbed SDK responses.
