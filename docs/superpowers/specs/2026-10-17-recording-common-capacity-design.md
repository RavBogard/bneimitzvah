## Existing facts and exact guarantee

Receipt service B serializes admissions through the immutable tenant recording_admission mutex and reads primary liabilities. The existing student recording registrar's two insertion paths do not join that gate; B's native test demonstrates this honestly. Both production source calls to data.insert/data.insertWithId are in recordings/registration.ts. The ordinary service mutates existing immutable-size rows only. Runtime has direct SQL privileges and trusted code can always issue raw SQL; this slice establishes an invariant across the reviewed application writers, not against a database administrator or compromised arbitrary SQL client.

Keep the existing accepted admission limits. An actual NEW legacy ledger row increases its student's and tenant's immutable audio bytes, logical takes and original identity count, so it must serialize and satisfy those post-increase caps. It does not create a receipt/pipeline/slot or a receipt admission-rate fact: do not invent actor attribution for historical ledger rows, apply receipt rates twice, or call this an all-provider-operation rate limit. Receipt active/rate decisions remain B's receipt-admission policy. All ledger rows, including deleting rows, remain charged. Receipt audio/logical liabilities remain independently charged; no same-ID/asset subtraction or implicit consumption. Marker charge stays separate and retained. Newly reserved receipt IDs/assets cannot be adopted through the legacy registrar.

## Selected bounded change

Add one internal common capacity module shared by receipt admission and legacy registration, reusing current primary aggregate facts and fixed bigint arithmetic. Preserve schema0021/0020 and auth/tenancy sanitizers. No duplicated stored counters, new SQL role/trigger, runtime feature flag or expiry/compaction policy is needed. Extract the existing receipt-limit constants/predicate only as necessary to keep one definition; keep B's receipt active/rate behavior exact.

Acquire the existing tenant mutex inside the existing fresh user authority transaction BEFORE any registrar ledger lookup/insert and BEFORE invoking withRegistrationAuthority's caller callback. The callback already exposes a trusted SQL scope; acquiring the gate only inside registerVerified would permit caller ledger locks before admission and introduce an avoidable inversion. Keep the established authority student/session/context locks first, then admission, then at most one actual matching ledger, then any head/slot locks. Do not add later student/session acquisition, absent-row lock or multi-head processing.

Under the mutex, distinguish an exact freshly authorized idempotent replay from a new insertion. Preserve existing asset-based retry, original-ID behavior, descriptor/state conflicts, create audit-once and callback poison/drain/lifetime rules. A nonoverlapping matching existing row does not increase liability and may replay even if historical totals already exceed capacity. A mismatch remains a closed conflict. A colliding reserved receipt ID or asset is refused EVEN if the existing legacy row otherwise matches an exact replay; collision refusal wins over capacity exemption. Current B has no legitimate ledger finalizer, so there is no consumption exception in this slice.

The implicit legacy insertion currently generates its UUID inside data.insert, too late for a reservation-ID check. Preserve asset replay first using the existing row's actual ID. For a genuinely new row, choose exactly ONE planned ledger UUID under the mutex, check that ID and the asset against reservations, and pass it explicitly into low-level insertion. The original-ID API uses its supplied validated ID instead. Remove the unused internally generating wrapper if needed; no post-insert adoption, regenerated UUID or second-key escape after collision/unknown acknowledgement is permitted.

For a new row, sample database actual clock after waits, read primary receipt/slot/ledger aggregates, and test the exact projected byte/take/identity additions for both student and tenant. Never convert bigint to a lossy number. All predicates must succeed before insert/audit; recheck existing authority freshness after each await and before/after callback settlement as today. Limit denial has a new closed private exact-identity signal translated only outside the unchanged auth sanitizer; preserve401/403/404/conflict behavior and do not reclassify arbitrary DB/audit errors. No raw provider/actor data in errors.

The low-level insert helpers must have no unreviewed production caller bypass: keep them used only through the guarded registrar and add a narrow callsite regression or equally clear internal restriction. Do not claim that TypeScript/module conventions revoke arbitrary SQL privileges. Future receipt finalization will need a separately reviewed atomic consumed-receipt/ledger/asset/verified-length accounting contract; do not add such an API now or prematurely single-charge overlapping rows.
