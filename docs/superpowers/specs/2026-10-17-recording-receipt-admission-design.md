## Three additive tables, exact selected v1 shapes

Root accepts these names and shapes for this slice. All identifiers/timestamps/revisions and JSON-free fixed columns receive CHECK/NOT NULL constraints as described. FORCE RLS, PUBLIC revocation and tenant-scoped runtime policy follow current tables; no new SECURITY DEFINER function or authority GUC. No tokens, handles, URLs, audio, names or provider errors are stored. INSERT triggers enforce initial states, not just application defaults. No runtime DELETE privilege or cascades that forget identity/history.

### recording_admission

- `tenant_id text PRIMARY KEY REFERENCES tenant(id)`. No unused revision/counter columns.
- One immutable mutex identity per tenant, created with ON CONFLICT DO NOTHING, then locked FOR UPDATE before any aggregate-sensitive receipt mutation. It holds no duplicated quota counters. A missing-row insert race must settle before aggregate reads; RLS never allows another tenant's mutex. Runtime cannot retarget/delete it. Row creation itself grants no admission.

### recording_receipt

- Identity: `id uuid PRIMARY KEY`, `tenant_id text`, `student_id uuid`, `request_id uuid`, `original_recording_id uuid UNIQUE`, `asset_id uuid UNIQUE`, `store_generation text` fixed by trusted server configuration. UNIQUE(tenant_id,student_id,request_id); UNIQUE(tenant_id,id); composite FK(tenant_id,student_id) to student. New UUIDs are server generated; caller supplies only request UUID/declaration/selected student via existing service selection. Original ID is reserved but has NO ledger FK until a row exists. A later collision with any existing ledger identity refuses, never adopts it.
- Immutable authorization snapshot: `actor_user_id text`, `auth_session_id text`, `membership_id uuid`, `membership_authority_revision integer`, `role_grant_id uuid`, `role_grant_revision integer`, `mode text CHECK IN('student','child-practice')`, `relationship_id uuid NOT NULL`, nullable `relationship_revision integer` (student_identity for own-student, guardian for child-practice), nullable `context_id uuid`/`context_authority_revision integer`/`context_student_revision integer`; `student_revision integer`; `session_expires_at timestamptz`, nullable `context_expires_at timestamptz`. These align with auth-schema user/session text IDs and tenant-schema membership/grant/relationship/context UUIDs. Every NONNULL revision is positive; snapshot expiries are finite and later than admitted_at, and child context expiry is no later than session expiry. Historical snapshot columns have no cascading FKs to deletable session/context/user rows. Student mode requires all context columns NULL, the current student_identity relationship ID and relationship_revision IS NULL: current lockStudentRelationship returns that exact ID with revision:null, and student_identity has NO revision column. Child mode requires positive guardian relationship_revision and its complete context tuple. Do not fabricate a student-identity revision or change existing authority/schema. context_student_revision is the locked current student revision projected into contextView, not a separately stored context revision. Preserve the exact student identity ID and freshly lock/check its active binding plus existing membership/grant revisions on every operation. Snapshot never substitutes for freshly locking current authority.
- Immutable declaration: `declared_bytes integer CHECK BETWEEN46 AND28800044 AND declared_bytes%2=0`; `slot_count integer CHECK BETWEEN1 AND28 AND slot_count=(declared_bytes+1048575)/1048576`; `admitted_at timestamptz` finite, database actual-clock supplied. Header46 is the minimum supported positive-frame canonical WAV size; no claim of canonical bytes at admission.
- Lifecycle: `state text IN('receiving','retiring','terminal')`, `revision bigint>0`, nullable finite `retiring_at`/`terminal_at`, nullable `terminal_reason` with ONLY first-slice value 'never-opened'. Initial receiving/rev1, no terminal/released facts. Receiving->retiring->terminal only, consecutive revisions; no transition back. Terminal requires every slot's proven never-opened closure. Later verifying/registered/retired-R states are NOT implemented in this slice.
- Date projection: `retention_ceremony_date date NOT NULL` (matching current student.ceremony_date), nullable `retention_latched_at timestamptz`. It is a current projected date, NOT immutable authority or an excuse to extend user/claim lifetimes. Any nonnull latch is immutable once set. Use existing shared due helper; an absolute retention deadline can be added later only with identical reviewed arithmetic. No unselected receiving/claim timeout is invented now.
- Liability: `logical_take_released boolean NOT NULL DEFAULT false`, initial false. In this slice it can become true only in the same terminal commit after every slot qualifies never-opened. Original identity and marker liabilities are never released. Original actor/student/admittedAt rate facts never change/expire by a date edit. No explicit fault pool is implemented now, so dates cannot add fault membership by state classification.

### recording_receipt_slot

- Immutable identity: `(tenant_id,receipt_id,slot_index) PRIMARY KEY`, FK(tenant_id,receipt_id) to receipt, `slot_index integer` zero-based0..27, `object_key text UNIQUE`. Proposed exact key: `recordings/v1/<lowercase asset UUID>/chunk-<two decimal index digits>` (00..27), derived by one internal function. Tenant/student/contact IDs never appear. Store generation is separately fixed on the parent. No caller-provided path; freeze this format with root now and do not silently retarget it for later transport. Key never reused/adopted/deleted, including terminal state.
- `expected_bytes integer`: for index<slot_count-1 exactly1048576, final exactly declared_bytes-index*1048576; positive/even<=1048576. Parent-dependent index/count/length checks require insert/update validation trigger, not an unenforced CHECK subquery. Admission inserts ALL expected rows atomically; no later slot insertion/deletion/reindexing.
- `revision bigint>0`, `state IN('reserved','prepared','opened','retiring','never-opened')`; `ever_upload_opened boolean NOT NULL DEFAULT false`, never true->false. Initial reserved/rev1/false. `audio_liability_released boolean NOT NULL DEFAULT false`; only true on never-opened with false opening history in this slice. `retiring` alone releases NOTHING.
- Nullable write-once `body_sha256 text` lowercase64hex, `permit_etag text` bounded strong quoted printable ASCII<=256/no CRLF/no weak W/; nullable `open_operation_id uuid` and finite `opened_at`. Body hash represents a future server-buffer hash of exactly expected_bytes, not a client assertion or whole-WAV verification. First-slice preparation is trusted internal/test composition only: no external caller/provider facts can enter through a route. No confirmed stored B/R ETag or verified-media field is claimed now.
- `prepared` requires body hash+A; `opened` requires those + ever=true + operationID/time; `retiring` preserves them/history; `never-opened` requires ever=false, released=true and no opening operation/time. A/P may be unknown on never-opened. Unique open_operation_id when present. A/hash may be set once before opening, never replaced; no key reset or new P lifecycle after unknown response.

Receipt/slot immutable triggers prohibit all identity/declaration/binding rewrites; transition checks prohibit caller-created terminal/opened INSERTs and true->false rollback by ordinary UPDATE. Runtime grants permit admission/preparation/opening and staging retiring only; they do NOT permit terminal_reason, terminal_at, logical_take_released or audio_liability_released mutation. First-slice terminal CAS is a trusted data primitive exercised through a restricted synthetic maintenance scope in local tests; no production maintenance execution path/grant/login is activated. Actual session_user cleanup scope and minimal privileges must be accepted before any production worker can execute it. Owner/role compromise is outside ordinary runtime protection.

## Deferred completeness and exact transition matrix

A receiving head MUST NOT commit without its complete expected slot set. Add deferred constraint triggers, DEFERRABLE INITIALLY DEFERRED, on receipt INSERT/relevant UPDATE and slot INSERT/UPDATE/DELETE; all revalidate the affected immutable head at COMMIT, including any privileged direct SQL path. Application insertion order remains head then all slots inside one transaction; do not use a CHECK subquery or an immediate count that rejects this valid transient state. At validation exactly slot_count rows with unique contiguous indices0..slot_count-1 must exist; every expected length matches the fixed declaration formula, every index is in range, and SUM(expected_bytes)=declared_bytes. A missing/extra/replaced row or NULL charged fact fails COMMIT. Runtime cannot DELETE either table; immutable row identities prohibit delete/recreate as a supported operation. INSERT defaults alone never establish these invariants.

Cross-row terminal completeness is checked by the same deferred validation: head state=terminal IFF head logical_take_released=true IFF ALL of the complete slots are never-opened, ever_upload_opened=false and audio_liability_released=true. In this first slice a nonterminal head may have NO never-opened/released slots: closure releases every qualifying slot and logical take together in ONE transaction, not an independently committed partial release. Slot released IFF never-opened; all other slot states require released=false. No vacuous ALL over zero rows, SQL NULL/UNKNOWN predicate or state-filtered aggregate can evade these constraints. Terminal reason/time are nonnull IFF terminal (reason exactly never-opened); retiring_at is nonnull IFF retiring/terminal. At COMMIT a receiving head has only reserved/prepared/opened slots, a retiring head has only retiring slots (preserving each opening bit), and a terminal head has only never-opened slots. Transient head/slot staging during the transaction is permitted, not a committed mixed lifecycle. All charged/opening booleans are explicitly NOT NULL, checked on INSERT and UPDATE. Hash+A are either both NULL or both present; prepared/opened require present. Opening operation/time are nonnull IFF ever=true, including retiring descendants. Use explicit IS NULL/IS NOT NULL and null-safe predicates; a CHECK evaluating UNKNOWN must never stand in for these state invariants.

Exact head matrix (unchanged immutable columns omitted):

| From | To | Permitted changed facts |
|---|---|---|
| receiving | receiving | Date projection to a not-yet-due current ceremony only; no liability/latch release. |
| receiving | retiring | First retiring_at; date projection/first retention latch when date-driven; liabilities unchanged. |
| retiring | retiring | Date projection and first retention_latched_at if due now; preserve original retiring_at and every charged fact. |
| retiring | terminal | Trusted never-opened closure only: terminal time/reason and logical release, with complete cross-row slot closure. |
| terminal | terminal | Date projection/first retention latch only; immutable terminal identity/reason/times/release/provenance remain unchanged. |

Any actual permitted head change increments revision by EXACTLY1. A fully identical row is an idempotent no-op with unchanged revision; revision-only increments and every unlisted edge/change fail. Slot preparation/opening changes only the slot revision; it does not independently bump the head. A due date cannot leave a receiving head receiving: the same transaction latches it retiring. Once retention_latched_at exists, it is never rewritten/cleared. Terminal or already-retiring dates do not reset retiring_at/terminal_at.

Exact slot edges: reserved->prepared sets hash+A once; prepared->opened sets true+operationID+openedAt once; reserved/prepared/opened->retiring preserves every existing hash/A/opening fact; retiring->never-opened is maintenance-only, requires ever=false/no opening ID/time and sets audio release=true. It succeeds only with the head/all-slot deferred terminal completeness above. Every actual slot edge increments revision EXACTLY1. Same-state slot changes are forbidden except an entirely identical idempotent no-op with unchanged revision; date projection has no slot date field, so already-retiring/never-opened slots remain untouched. No prepared->reserved, opened->prepared, reopening, reset or same-state fact replacement. Head/slot lifecycle reversal is never a date projection. Runtime INSERT must be receiving/reserved initial states, false release/opening booleans and NULL terminal/opening/preparation facts; runtime UPDATE grants omit terminal/release columns, and triggers still enforce the matrix for any privileged test operation.

## Admission serialization and exact quotas

These are serialized RECEIPT ADMISSION decisions over freshly observed PRIMARY ledger/receipt rows, not a universal cap against unchanged legacy writers. Current recordings/registration.ts/data.insertWithId can INSERT ledger rows WITHOUT this mutex or quota checks; concurrent legacy registration can therefore exceed the observed aggregate cap after an admission reads it. The provider-disabled first slice leaves that registrar UNCHANGED and makes no contrary guarantee. Before any receipt route/provider enablement or concurrent ledger creator/finalizer activation, every increasing ledger/receipt writer MUST join the common serialization AND enforce the same post-increase capacity policy. Merely adding a mutex without checking capacity is insufficient. This is an explicit ACTIVATION BLOCKER, not a request to modify legacy registration in this slice.

Within those scoped admissions use fresh PRIMARY rows after the tenant mutex; no read replica/cache or state/deadline/enabled-user filter changes charged liability. Use bigint arithmetic for sums/caps. Limits proposed here reproduce root's selected engineering bounds, not a bill guarantee:

- active:2/student AND2/(tenant,originating user),128/tenant across all sessions/roles. Count receipt state=receiving. Retiring/terminal is no longer active; this is explicitly NOT a bound on still-live remote requests.
- admitted rate:4/rolling hour and8/rolling24h independently per student AND tenant-user;200/hour512/rolling24h tenant. Count every successfully committed receipt admission, regardless later state. Use one freshly sampled database clock after waits and half-open windows admitted_at>now-window AND admitted_at<=now. An exact idempotent replay consumes no additional rate; rejected transaction consumes none. Transport ingress-attempt throttles are future work, not fabricated rate entries.
- audio liability:10GiB/student,256GiB/tenant. For each receipt sum slot expected_bytes WHERE audio_liability_released=false; admission initially equals declared_bytes. ALL existing student_recording rows count full immutable byte_length, including deleting rows, PLUS receipt slot liabilities. This first slice never creates a ledger row, so there is no legitimate receipt/ledger overlap to deduplicate. Do NOT subtract a ledger merely because its ID happens to equal a reservation: reservation is not receipt consumption. A future finalization contract must atomically bind consumed receipt to the exact ledger+asset+verified declared length before introducing a single-charge join; it cannot switch to a lower/higher accounting basis or silently undercount a legacy collision.
- logical takes:1000/student,20000/tenant. Each receipt with logical_take_released=false counts1, not28; EVERY existing ledger row counts1 even if deleting. Future consumed-link deduplication is outside this slice. No existing legacy ledger row is retroactively marked released/adopted.
- original IDs:4096/student,65536/tenant, including ALL receipt original IDs (terminal too) + the distinct union of ledger IDs, so an unexpected collision cannot hide a permanent identity. Reserved ID/asset collisions against existing ledger fail admission instead of adoption; existing row liabilities still count conservatively. Retention/date changes/compaction do not reduce this count in this contract.
- markers: reserve conservative64 bytes PER immutable slot from admission, forever in this slice, independently of released audio/logical charge. Count and report this internally as a separate liability; original-ID bound and28 slots make it finite. It is not included deceptively in audio-byte sums or a provider billing claim.

Under mutex check POST-admission candidate sums/counts over that observed baseline, then insert head+all slots; overflow/SQL/audit/auth/final freshness failure rolls back everything. Legacy existing usage above a cap refuses new work but is not mutated. Each aggregate uses exact tenant/student/actor predicates; no cross-tenant user lock/counter. New date commits may only yield equal charged sums or equal/lower active count; a stale higher active count may refuse harmlessly.

## Internal operations, errors and outer settlement

`admit(request, selection, {requestId,declaredBytes})`: strict closed validation/no echo, existing recording authority first, mutex second, then lookup request key. For existing receipt require exact immutable declaration AND original full session/mode/authority/context/student snapshot; run fresh authority before replay. Same request/binding returns same immutable reservation even if retiring/terminal ONLY if the existing allowDue=false fresh authority gate still passes, with nonresumable classification; expired/revoked/due authority denies before replay, and it never revives/reopens. Different declaration/binding returns closed conflict; foreign/nonexistent lookups remain quiet404 after authorization. New login/context cannot adopt it. Generate IDs only for a genuinely new insertion; permanent namespace resolves concurrent duplicates.

`prepareSlot(...)`: fresh same authority, mutex, receipt then slot ascending; exact expected revisions/live state. Write once server-computed hash+A and increment revision. No provider action, register, stored claim or dispatch permission. After a retirement winner, late P completion is refused. Uncertain P completion does not synthesize A.

`openSlot(...)`: fresh same authority, mutex, receipt+slot, same snapshot/hash+A/revisions. Atomic false->true/opened with new operationID and exact outer transaction settlement. Only the TOP-LEVEL method, after awaited authority Promise has fulfilled, may return an internal single-use committed-opening result to a future sender. It is absent from runtime/HTTP and is not accepted from a caller as proof. No caller callback, UPDATE RETURNING, nested transaction/savepoint, scheduled promise, finally handler or after-rollback continuation can release it. No I/O can be attached inside the callback. No actual sender exists in this slice.

Opening and terminal closure serialize on the SAME durable slot identity, not a cached head flag. If cleanup wins, later prepare/open CAS fails with zero dispatch permission. If open commits first, closure refuses never-opened and full possible-audio charge remains, even if no sender ever ran. A true bit never resets because a claim/session expires. A date latch is checked again after waits and before successful return.

`closeNeverOpened(headId, expected revisions)`: only for an already retiring eligible head, mutex then existing ledger if any, receipt then all slots ascending. At most ONE logical head per transaction. Lock actual primary rows and require the deferred complete slot-set/terminal consistency checks; every slot false and no ambiguous/adopted history; close all slots/head terminal and release their audio/logical liabilities atomically. Retain immutable key/ID/provenance/marker/rate facts. No HEAD404/absence/lease outcome is consulted or claimed; possible fixed31-byte P residue is permitted and unplayable. If ANY slot true, this first slice cannot terminalize/release the head; it remains retiring/charged for the future proven R path. Runtime cannot invoke this maintenance transition.

Every top-level operation returns success ONLY after confirmed outer COMMIT. Any thrown database/connection/commit error is unavailable/unknown, never success/released/not-created. Admission uncertainty reconciles SAME requestUUID after fresh authority; opening uncertainty returns NO permission and never constructs U. A later reconciler may observe the durable true bit but must NOT blindly issue/reissue U on that observation: sender ownership/replay decisions await the future dispatch contract, while cleanup conservatively retains audio liability. No new key/UUID to escape uncertainty. Unknown terminal COMMIT is reconciled on the same tombstone before acknowledging release; primary aggregates always derive whichever transaction actually committed.

Preserve existing AccessDenied401/403/404. Closed conflict/limit errors can use private exact-identity AccessDenied-compatible bridge signals translated OUTSIDE authority, as the registrar does; do not edit auth sanitizers or classify arbitrary DB/audit/AccessDenied errors as conflicts. No receipt/provider/actor information in errors. Admission is not recording.create: it creates NO student_recording or user recording audit. Existing audits stay unchanged until separate audited finalization; maintenance/date changes never fabricate a user actor.

## Date projection and exact lock paths

Runtime order stays existing tenant->user->session->membership->grant->student SHARE->relationship->child context, THEN admission->existing ledger (only if present)->receipt->slots ascending. A callback cannot acquire authority/student locks after mutex or upgrade student. First-slice receipts have no ledger; future absent-ledger first registration is the narrow exception: student SHARE->admission->receipt/slots->INSERT reserved ID, never lock absence or subsequently acquire some present ledger row. Later present-ledger work locks ledger before receipt.

Date UPDATE holds student exclusive. Existing0020 recording_ceremony_retention trigger first updates ALL affected ledger rows in its existing plan-dependent order; an additive receipt projection trigger must run AFTER it (explicit lexical trigger-name ordering tested). Then project retention_ceremony_date for receipts and latch retiring/head+slots when OLD OR NEW due at clock_timestamp AFTER waits. Preserve existing submitted/private ledger behavior. No admission direct/indirect; no terminalization, release, compaction, claim opening/clearing, charged fact/hash/key mutation or rate/fault reclassification. Latch survives future->past->future in one committed transaction; rollback reverts all changes. Projecting a later date never clears latch or revives prepared/opened work.

Maintenance transaction is admission->ONE existing ledger if any->ONE receipt->its slots; NEVER then student/user/session or another head/ledger. Selection before transaction is only an unlocked hint. The internal maintenance transaction wrapper binds one head and rejects a second; do not expose arbitrary transaction callbacks that can process a second head. This is a service invariant plus native demonstrated ordering, not a claim that an unconstrained owner SQL client cannot construct a deadlock. No worker schedule/production role is enabled. Multiple ticks/heads require separate commits and reacquired admission. Date transaction may process multiple heads but never returns to ledger after starting receipt locks, so the one-head worker cannot form the known L1/R1->L2 vs L2->L1 cycle.
